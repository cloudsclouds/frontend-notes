# 计算机网络

## 1. 常见的HTTP请求方法
- GET：用于请求获取资源。
- POST：用于提交数据，通常用于创建或修改资源。
- PUT：用于更新资源。
- DELETE：用于删除资源。
- HEAD：类似于GET，但只请求头部。
- OPTIONS：用于获取支持的请求方法或查询服务器支持的选项。
- PATCH：用于部分更新资源。

### 1.1 GET和POST的请求的区别
GET：
- 用于从服务器获取数据。
- 参数附加在 URL 中，因此数据长度有限，有 URL 长度限制。
- 速度较快，因为数据直接在 URL 中传输，适合查询操作。
- 安全性较低，参数可能暴露在 URL 上。

POST：
- 用于向服务器发送数据。
- 参数通过请求体传输，没有长度限制。
- 相对安全，参数不会直接暴露在 URL 上。
- 处理速度比 GET 略慢，因为涉及请求体数据传输。

## 2. HTTP 1.0、1.1、2.1、http3+UDP
### 2.1 如何区分
HTTP/1.0 和 1.1 是通过请求行中的版本号区分的；
HTTP/2 和 HTTP/3 是在连接建立阶段通过协议协商来确定，比如 HTTP/2 通过 TLS 的 ALPN 协商为 h2，而 HTTP/3 基于 QUIC（UDP），在握手阶段就确定协议，同时可以通过 Alt-Svc 响应头告知客户端支持 h3。

### 2.2 详解
http 1.0：每次请求都要需要创建新的TCP连接，请求完成之后断开连接。

HTTP/1.1：
1. 支持长连接，即TCP连接上可以串行传送多个HTTP请求和响应。
2. 支持请求流水线，可以同时并行发送多个请求，但服务器必须按请求顺序返回响应。
3. 引入了更多的缓存控制策略，如Cache-control 和 etag等缓存控制字段。
4. 仍然存在队头阻塞问题，即一个请求被阻塞，其他请求也会被阻塞。

HTTP/2：
- 多路复用：一个 TCP 连接可以并行处理多个请求，解决队头阻塞问题。
- 头部压缩：使用 HPACK 算法压缩请求头，节省带宽。
- 服务器推送：指在客户端请求一个资源时，服务器可以主动将相关资源一并发送给客户端，属于单向优化机制。（而 WebSocket 是一种独立协议，建立连接后支持客户端和服务器之间的双向实时通信）

HTTP/2无法解决的问题：
- TCP 的固有问题：虽然解决了应用层的队头阻塞，但由于底层 TCP 仍然基于单个连接，存在 TCP 队头阻塞问题，特别是在高延迟和丢包场景下。TCP 层队头阻塞来自 TCP 的按序交付要求，丢包会阻塞整个连接。
- 连接建立时的延迟：TCP 握手依然存在延迟。

HTTP/3 + UDP：
- UDP 没有 TCP 的队头阻塞问题，通过使用 QUIC 协议实现的 HTTP/3 能避免TCP连接中的队头阻塞，允许多个流在一个 UDP 连接中并行传输。
- 更低的连接延迟：QUIC 通过 0-RTT 连接重用，减少了连接建立的延迟。
- 更好的移动网络支持：由于 UDP 是无连接的，适合移动网络中频繁切换网络的情况。

### 2.3 QUIC 为什么还能保证可靠性？
UDP 本身是不可靠的，但可以在应用层通过引入序列号、ACK 确认、超时重传、滑动窗口等机制来实现可靠传输。这些机制本质上类似于 TCP 的实现，例如通过序列号保证顺序，通过 ACK 和重传保证数据不丢失，通过窗口机制提高传输效率。

## 3. HTTP 和 HTTPS 的区别：
HTTPS 是在 HTTP 基础上加了 TLS/SSL 加密层的安全通信协议。
通过 TLS 协议，先用非对称加密安全地协商出一个对称密钥，然后用这个密钥进行高效加密通信，同时通过证书机制保证服务器身份可信，防止访问伪造网站；
还用完整性校验防止数据在传输过程中被篡改。

1. 客户端发起请求
2. 服务端返回：证书（含公钥）
3. 客户端：
- 验证证书（CA 签名）
- 生成一个 随机对称密钥（pre-master secret）
- 用服务器公钥加密发送给服务器

4. 服务端：用私钥解密，拿到对称密钥，双方开始用 对称加密通信

## 4. HTTP 状态码
- 1xx（信息性状态码）：表示请求已被接收，继续处理。
- 2xx（成功状态码）：表示请求已成功处理。
- 3xx（重定向状态码）：表示请求需要进一步的操作（如跳转）。
  - 301 Moved Permanently：请求的资源已经 永久移动 到新的 URL，以后所有请求都应该访问新的地址
  - 302 Found：请求的资源 临时 位于新的 URL，但以后可能还会恢复原地址。SSO 一般使用 302 重定向。因为登录跳转属于临时跳转：用户未登录时跳到认证中心，认证成功后再跳回业务系统。
  - 304：客户端之前请求过该资源，并且已经缓存了，服务器判断 资源自上次访问后没有改变，所以告诉浏览器直接使用本地缓存，不需要重新下载。
- 4xx（客户端错误状态码）：表示请求有错误，由客户端引起。
  - 例如：400 Bad Request、404 Not Found、403 Forbidden
- 5xx（服务器错误状态码）：表示服务器在处理请求时发生错误。
  - 例如：500 Internal Server Error、502 Bad Gateway

## 5. 与缓存相关的HTTP请求头有哪些
浏览器缓存的本质是通过复用已下载的资源，避免重复请求，其核心机制分为强缓存和协商缓存两类。
1. 发送请求前，浏览器先查找强缓存是否命中：
  1. 命中 → 直接返回缓存资源（状态码 200, from cache）
  2. 未命中 → 进入协商缓存阶段
2. 协商缓存阶段：
  1. 浏览器携带标识询问服务器资源是否变更；
  2. 若未变更 → 返回 304 Not Modified；
  3. 若变更 → 返回 200 并更新缓存副本。

- 强缓存：浏览器在缓存有效期内 直接使用本地缓存，不发请求到服务器，由服务器通过响应头控制，关键 HTTP 头有两个：
  - Expires（ HTTP/1.0）： 服务器返回资源的 “过期时间”（绝对时间，如 Wed, 21 Oct 2025 07:28:00 GMT），在此之前不会再向服务器请求。
  - Cache-Control（ HTTP/1.1）： 通过 “相对时间” 和更灵活的缓存控制，优先级高于 Expires，比如 max-age 指定缓存时间，no-store 不使用强缓存，每次请求都必须进入协商缓存流程（让服务器判断是否复用缓存）等。如 Cache-Control: max-age=31536000, public

- 协商缓存：需服务器判断是否复用缓存：浏览器会向服务器发送请求，通过 ETag 或 Last-Modified 判断资源是否变化；没变化返回 304，有变化才返回新资源。
  - Last-Modified / If-Modified-Since（HTTP/1.0）：通过最后修改时间判断是否更新。如果资源未变，服务器返回 304 Not Modified，复用本地缓存，节省带宽。
  - ETag / If-None-Match（HTTP/1.1）：由服务器生成文件内容的唯一标识，通过资源唯一标识判断内容是否变化。

### 5.1 如何让应用正确使用缓存
1. 强缓存：静态资源（JS / CSS / 图片）文件名哈希（如`main.abc123.js`）
```js
location /static/ {
    add_header Cache-Control "max-age=31536000, immutable";
}
```

2. 动态接口数据：对接口数据使用协商缓存保证实时性。
```js
Cache-Control: no-store
```

### 5.2 Content-Type 和 Accept 区别？
`Content-Type` 表示请求体的格式，`Accept` 表示期望服务器返回的格式。

## 7. 浏览器从输入 URL 到页面渲染完成的过程
1. 浏览器处理 URL，并先检查强缓存 / 协商缓存。
2. 未命中缓存时，进行 DNS 解析，拿到目标 IP。
3. 建立 TCP 连接；如果是 HTTPS，还会进行 TLS 握手。
4. 发送 HTTP 请求，服务器返回状态码、响应头和响应体。
5. 如果返回的是 HTML，浏览器会创建或复用渲染进程，把文档交给渲染流程继续处理。

### 7.1 DNS解析的过程
1. 浏览器缓存：首先查看浏览器的DNS缓存中是否有该域名的解析记录。
2. 操作系统缓存（含 hosts）：如果浏览器没有缓存，再查看操作系统的DNS缓存。
3. 本地DNS服务器查询：如果操作系统缓存中也没有，查询配置的本地DNS服务器。
4. 递归查询：本地DNS服务器首先向根域名服务器查询，根服务器知道顶级域（TLD）服务器的地址。
5. 顶级/TLD服务器：根域名服务器返回TLD服务器的地址，本地DNS服务器向TLD服务器查询（如.com、.cn）。
6. 权威DNS服务器：TLD服务器返回最终域名的权威DNS服务器地址，本地DNS服务器向权威DNS服务器查询该域名的IP地址。
7. 返回结果：解析完成后，本地DNS服务器将结果返回给客户端， 最终浏览器拿到 IP 并进行后续连接。

## 8. 跨域与同源策略
同源要求三个部分完全一致：协议、域名、端口号。只要有一个不一样，就是跨域。
同源策略是浏览器的一种安全机制，限制从一个源加载的脚本去读另一个源的响应，防止 CSRF 攻击和用户登录状态下的数据被恶意网站窃取。

同源策略限制的是读取响应而不是发送请求。请求会正常到达服务器，服务器也会返回结果，但浏览器发现目标源和当前页面不同源时，会拦截响应，不允许 JavaScript 获取返回数据。

CORS 跨域资源共享。浏览器会根据相应头判断是否允许跨域读取。一些响应头包括：
- Access-Control-Allow-Origin: 允许的源
- Access-Control-Allow-Methods: 允许的方法（GET，POST，HEAD）
- Access-Control-Allow-Headers: 允许的自定义请求头
- Access-Control-Allow-Credentials: 是否允许携带 cookie
  
当请求使用了非简单请求方法或自定义了header，或 content-type 非简单类型时，浏览器会发送预检请求（OPTIONS），服务器返回 CORS 相关响应头，浏览器看到这些头时，就允许跨域读取响应数据。

简单请求不会触发预检请求，但服务器仍然需要返回 CORS 相关响应头，否则浏览器会拦截响应，前端无法获取数据。

跨域解决方案
1. 服务端正确配置 CORS 响应头
后端在响应头中配置 Access-Control-Allow-Origin、Access-Control-Allow-Methods、Access-Control-Allow-Headers、Access-Control-Allow-Credentials，允许指定域名、访问方法、请求头、是否允许携带 cookie，前端不用做任何修改。
  
2. 前端代理到同源
在开发阶段，使用构建工具的 dev-server，将跨域请求代理到同源的本地 dev-server，再由 dev-server 转发请求到目标服务器，服务器之间没有跨域。

3. Nginx 反向代理
在生产环境中，用 Nginx 反向代理层统一转发请求，前端调用同域 Nginx 的接口，Nginx 把接口路径转发到后端服务，对前端透明，前端感觉就是同源。

4. JSONP（老方案，只支持 GET）：利用 script 标签不受跨域限制的特点。前端传一个回调函数名，后端返回函数调用包裹的数据。
```HTML
<script src="https://api.example.com/user?callback=handleResponse"></script>
```

后端收到请求后，不是返回 JSON 数据，而是返回一段 JS 代码，比如：
```HTML
handleResponse({ name: "Ying", age: 22 });
```

5. WebSocket：通过WebSocket协议进行跨域通信。WebSocket 通过在 HTTP 握手后升级为 TCP 长连接 协议 `Connection: Upgrade` `101 Switching Protocols`，在同一个连接上允许客户端和服务器独立、同时发送数据，从而实现真正的全双工通信。

## 9. TCP三次握手与四次挥手
三次握手（建立连接）：
1. SYN：客户端向服务器发送一个SYN包（同步序列号，用于建立连接），表示请求建立连接，并发送自己的初始序列号x。
2. SYN-ACK：服务器收到SYN包后，回复SYN-ACK包， 表示同意建立连接，并告知ACK 确认包x+1，自己的初始序列号y。
3. ACK：客户端收到SYN-ACK包后，回复ACK包 y+1 给服务器，表示确认收到了服务器的响应。  客户端进入 ESTABLISHED 状态，服务器收到这个 ACK 后也进入 ESTABLISHED 状态。

### 9.1 为什么是三次而不是两次？
- 因为需要双向确认（客户端能发，服务器能收；服务器能发，客户端也能收）。
- 两次握手无法确保服务器的 SYN+ACK 包是否被客户端成功接收，可能导致“半连接”问题（服务器以为连接建立了，客户端却没收到，资源被浪费）。

四次挥手（断开连接）：
1. FIN：客户端发送FIN包，表示 自己已经没有数据要发送了，请求关闭客户端 。
2. ACK：服务器收到FIN包后，回复ACK包。 表示“我知道你要关闭了，但我还可能有数据要发”。
3. FIN： 当服务器也发送完所有数据后，向客户端发送 FIN 包 ， 请求关闭服务器 。
4. ACK：客户端收到服务器的FIN包后，回复ACK包， 客户端等待一段时间（2MSL）后彻底关闭，服务器收到这个 ACK 后直接关闭连接（CLOSED）。

### 9.2 为什么要四次？
- 因为 TCP 是全双工协议，断开连接必须由双方分别发出 FIN 并得到确认。
- 服务器在收到客户端的 FIN 时，可能还有数据没发完，因此不能和 ACK 合并发送，导致需要分两步完成（ACK + FIN）（第二次挥手+第三次挥手）。
- 假设服务器在第二次挥手时，把 ACK 和 FIN 合并，即客户端发 FIN → 服务器直接回 FIN+ACK → 客户端回 ACK。这样确实只用了三次，但前提是 服务器在收到客户端 FIN 时，自己已经没有数据要发了。在实际 TCP 通信中，这种情况不一定满足，所以 TCP 协议设计时，将 ACK 和 FIN 分开，保证可靠传输。

### 9.3 TIME_WAIT 的意义
- 确保客户端发送的最后一个 ACK 能被服务器收到；
- 避免旧连接的数据包在网络中延迟，影响新的连接（防止“延迟的重复分组”）。

## 10. 非对称加密和对称加密的过程
- 对称加密是指加密和解密使用相同的密钥。这意味着发送方和接收方需要共享同一个密钥来加解密数据。
- 非对称加密使用一对密钥——公钥和私钥。公钥和私钥是配对的，公钥用于加密，私钥用于解密。

1. 密钥生成：每个用户都有一对密钥：公钥和私钥。公钥是公开的，任何人都可以知道；而私钥是保密的，仅由用户自己持有。
2. 加密：发送方使用接收方的公钥对明文进行加密。由于公钥是公开的，任何人都可以用公钥加密数据，但只能用对应的私钥解密。
3. 数据传输：加密后的密文通过网络传输给接收方。
4. 解密：接收方使用自己的私钥对密文进行解密，恢复出原始的明文数据。只有拥有私钥的人才能解密数据，即使是用公钥加密的密文。

## 11. 网络模型
1. OSI 七层模型（理论模型），从下到上依次是：
物理层：传输比特流（0 和 1），定义物理接口、传输媒介、电压、速率等
数据链路层：建立可靠的链路，进行帧传输、错误检测和流量控制，比如：以太网、MAC 地址、交换机
网络层：选择路径，实现不同网络之间的互联（路由），比如：路由器
传输层：端到端通信，保证数据可靠传输，比如：TCP（可靠）、UDP（不可靠）
会话层：建立、管理和终止会话
表示层：数据格式转换、加密/解密、压缩
应用层：直接为用户提供服务，比如：HTTP、FTP、SMTP、DNS

## 12. TCP vs UDP
1. 连接方式
- TCP
  - 面向连接：通信前必须先建立连接（三次握手），结束时四次挥手
  - 保证双方“握手成功”后才能传输数据
- UDP
  - 无连接：直接发送数据，不需要建立连接
  - 没有握手过程，发送快但不可靠

2. 可靠性
- TCP
  - 可靠传输：保证数据按顺序到达，丢包会重传
  - 提供流量控制和拥塞控制
- UDP
  - 不可靠传输：不保证数据顺序，也不重传
  - 发送速度快，但可能丢包或乱序

3. 传输方式
- TCP
  - 面向 字节流
  - 数据被拆分成数据段，接收方按顺序重组
- UDP
  - 面向 报文
  - 一次发送一个完整数据包，包大小有限制（一般 ≤ 64 KB）

4. 应用场景
- TCP
  - 对可靠性要求高的场景：网页浏览（HTTP/HTTPS）、文件传输（FTP）、邮件（SMTP）
- UDP
  - 对速度和实时性要求高、可容忍少量丢包的场景：视频会议、在线游戏、DNS 查询、VoIP

## 13. 前端安全
1. XSS 是跨站脚本攻击，攻击者通过注入恶意 JS 代码，在用户浏览器执行，可能窃取 Cookie、篡改 DOM 或劫持操作。

防护方法包括：
- 输出编码：对用户输入进行 HTML/JS/URL 转义，避免直接 innerHTML，浏览器不会把转义后的字符当作可执行代码，从而防止执行恶意 JS。
- CSP 通过限制资源加载来源，本质是“白名单机制”，限制脚本来源，从浏览器层面阻止 XSS 执行。
- Cookie 设置为 HttpOnly

2. CSRF 利用用户在浏览器的登录状态（Cookie、Token），在第三方网站或脚本中发起伪造请求，从而执行用户未授权的操作（如转账、修改密码）。
前端防护方法：
- 使用 CSRF Token：请求携带服务端生成的 token，服务端校验。
- SameSite Cookie：限制第三方站点不能发送 Cookie。

## 14. JWT
JWT 是一种自包含的 JSON Web Token，用于客户端和服务器之间的身份认证。

它由 Header、Payload 和 Signature 组成。
- Header（头部）：描述 token 类型和签名算法
- Payload（负载）：存放声明，如用户 ID、过期时间、权限
- Signature（签名）：用 Header + Payload + Secret 生成 ，用于验证 token 是否被篡改

登录成功后服务器生成 JWT 并返回给客户端(通常放在 `Authorization: Bearer <token>` 或 localStorage / cookie)，客户端每次请求带上 token，服务器通过Base64 解码 Header 和 Payload、签名验证和验证过期时间校验来识别用户身份。

JWT 的优点是无状态、易于分布式扩展，但 Payload 信息不加密，敏感信息不能放在里面，需要注意签名算法和过期策略。

### 14.1 Jwt vs cookie+session
Cookie + Session 是“服务端存状态”（分布式需要共享 session，如 Redis），JWT 是“客户端存状态”。

无状态机制：
- JWT 自带用户信息和权限
- 服务端无需存储 session，方便 分布式/微服务
- 安全依赖于 Secret 或 私钥（RSA/ECDSA）

1. Cookie + Session
风险：CSRF（跨站请求伪造）
解决：SameSite、CSRF Token

2. JWT
风险：XSS（token 被偷）；token 一旦泄露 → 可直接使用
解决：
- 不存 localStorage（推荐 httpOnly cookie）
- 设置过期时间（exp）
- 使用 refresh token
