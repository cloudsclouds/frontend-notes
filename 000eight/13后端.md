## 1. 数据库基础
### 1.1 索引是什么，为什么索引能加速查询？
索引是数据库里的“检索目录”。没有索引时，数据库往往需要全表扫描；有索引后，可以先在索引结构里快速定位，再回表取数据，查询效率会提升。
MySQL 里最常见的是 B+ 树索引。

### 1.2 B+ 树的结构和特点
B+ 树是一种多叉平衡查找树，一个节点可以有很多子节点，树的高度会比较低，查一次数据要走的层数就少，对磁盘 I/O 更友好。

它有几个关键特点：
- 非叶子节点不存完整数据，只存索引键和子节点指针。
- 真正的数据记录主要放在叶子节点。
- 所有叶子节点按大小顺序连接起来，形成一个有序链表。

假设有一张用户表，对 age 建了索引。
B+ 树最上面是根节点，比如记录几个范围边界：18、30、50。
如果查询 age = 26，数据库会先看根节点，发现 26 落在 18 ~ 30 这个区间，就往对应子节点走。
到了下一层，再继续缩小范围，最后定位到叶子节点，找到对应数据。

### 1.3 `EXPLAIN` 是什么，怎么看执行计划？
`EXPLAIN` 用来查看 SQL 的执行计划，帮助判断查询是否走了索引、扫描了多少行、有没有用到临时表或文件排序。

重点关注：
- `type`：查询类型，是否高效
- `key`：实际使用了哪个索引
- `rows`：预估扫描行数
- `extra`：有没有出现临时表、文件排序、覆盖索引等额外信息

如果一个 SQL 明明建了索引但还是慢，通常就会先用 `EXPLAIN` 看它到底有没有走到预期索引。

### 1.4 什么是覆盖索引和回表？
如果查询需要的字段都在索引里，就可以直接从索引拿到结果，不需要再回主表找数据，减少了一次回表操作。

比如有联合索引 `(name, age)`，如果查询是：
`select name, age from user where name = 'Tom'`
那有机会直接从索引返回结果。

但如果查询是：
`select name, age, address from user where name = 'Tom'`
而 `address` 不在索引里，那数据库通常还要再去主表取一次数据，这个过程就叫回表。

### 1.5 什么情况下索引可能失效？
常见失效场景：
- 在索引列上做函数、计算、类型转换
- 使用前置模糊查询，比如 `like '%abc'`
- 联合索引没有遵守最左前缀原则
- 条件里对索引列使用 `!=`、`not in`、`is not null` 等，优化器可能不走索引
- 数据区分度太低，优化器判断全表扫描更划算

索引失效很多时候不是完全“失效”了，而是优化器判断走索引收益不高，所以最终没有选择索引。

### 1.6 什么是最左前缀？
联合索引会优先从最左边的字段开始匹配，所以查询条件最好从联合索引的最左列开始写，否则索引利用率会下降。

比如有联合索引 `(a, b, c)`：
- `where a = 1` 可以用
- `where a = 1 and b = 2` 可以用
- `where a = 1 and b = 2 and c = 3` 可以用
- `where b = 2 and c = 3` 就不能很好利用这个联合索引

### 1.7 数据库的分库分表是什么？
当单表数据量太大、单库压力太高时，就会做拆分。
- 分表：把一张大表拆成多张表，比如按用户 ID、时间范围等拆分
- 分库：把数据拆到多个数据库实例里，分散存储和查询压力

它解决容量和吞吐问题，但也会带来复杂度，比如跨库查询、分页困难、事务复杂、全局 ID 设计、数据迁移和运维成本都会上升。

### 1.8 数据库的读写分离是什么？
读写分离就是让数据库的读操作和写操作分别在不同的数据库实例上进行。
- 读库：只负责读操作，不负责写操作
- 写库：只负责写操作，不负责读操作

分担读压力，但会引入主从复制延迟问题。也就是刚写入的数据，马上去读库查询，可能还读不到。

### 1.9 事务是什么，为什么需要事务？
事务可以理解成一组操作，要么都成功，要么都失败，不会只执行一半。它主要用来保证数据一致性。

事务常说的 ACID 是：
- 原子性：要么全成功，要么全失败
- 一致性：事务前后数据状态要正确
- 隔离性：并发事务之间尽量互不干扰
- 持久性：事务提交后，结果要被可靠保存

### 1.10 常见事务隔离级别是什么？
常见隔离级别有四种：
- 读未提交：事务之间几乎没有隔离，一个事务改了但还没提交，另一个事务就能直接读到。
- 读已提交：解决了脏读，只能保证“只能读到别人已经提交的数据”，但不能保证同一事务里前后两次读取结果一致。
- 可重复读：解决了脏读和不可重复读，但无法解决幻读。
- 串行化：解决了所有并发问题，但性能最差，相当于串行执行。

它们本质上是在性能和一致性之间做平衡，用来解决并发读写时的几个典型问题：
- 脏读：读到了别人还没提交的数据
- 不可重复读：同一事务里两次读同一条数据，结果不一样
- 幻读：同一事务里两次按条件查询，结果条数不一样

MySQL InnoDB 默认隔离级别是 可重复读。事务隔离级别底层主要靠锁和 MVCC 来实现。
- MVCC：多版本并发控制，通过版本链和回滚指针实现，每个事务读取数据时，都会生成一个快照，事务结束时，会删除该快照。
- undo log：事务回滚时，会生成一个 undo log，用于回滚事务。
读已提交通过 MVCC 让事务只能看到别人已提交的数据，所以能解决脏读；
可重复读在此基础上让同一事务始终读取同一份快照，后面一直沿用这份快照，所以能解决不可重复读；
在 MySQL InnoDB 里，还会结合间隙锁和 next-key lock 来尽量避免幻读；
串行化则是通过更强的锁或直接串行执行，把并发问题彻底压住，但性能最差。

### 1.11 数据库的乐观锁和悲观锁是什么？
乐观锁和悲观锁是两种不同的锁机制，用于解决并发问题。
乐观锁：假设不会发生冲突，只在更新时检查是否被修改。适合读多写少的场景。
悲观锁：假设会发生冲突，每次操作都加锁，适合写多读少的场景。

乐观锁常见做法是用 `version` 字段或更新时间戳，更新时带上旧版本条件；悲观锁常见是 `select ... for update`。

### 1.12 慢查询优化
慢查询优化是数据库优化中的重要一环。
常见优化方法有：
- 使用索引
- 避免全表扫描
- 避免使用函数、计算、类型转换
- 避免使用前置模糊查询
- 减少不必要的返回字段，避免 `select *`
- 大分页场景避免直接 `limit offset` 扫太深
- 合理拆分复杂查询，避免过多 `join`
- 看执行计划，确认问题到底出在扫描、排序、回表还是锁等待

### 1.13 分页性能问题
小数据量时普通 `page + pageSize` 没问题，但在大表深分页时，`limit 100000, 20` 这类 SQL 性能会明显变差。

常见优化思路有：
- 大数据量优先考虑基于主键或时间的游标分页
- 对导出、报表这类场景走异步任务，不要走实时大分页接口
- 前端做虚拟列表、懒加载、无限滚动，避免一次渲染太多 DOM

## 2. SpringBoot
SpringBoot 是 Spring 框架的扩展，用于简化 Spring 应用的开发，提供了自动配置、快速开发、简化配置、内嵌容器等特性。

### 2.1 SpringBoot 的自动配置是什么？
它会根据项目依赖、配置文件和约定，自动装配基础能力。比如引入 Web 相关依赖后，就会自动准备好 Web 容器和 MVC 基础配置；引入数据库依赖后，也会自动装配数据源和相关组件。

### 2.2 SpringBoot 的依赖注入、模块化？
依赖注入：对象不是自己手动 `new`，而是交给 Spring 容器管理，再通过构造函数、注解等方式注入到需要的地方。
模块化：成按业务或能力拆分，比如用户模块、订单模块、权限模块、支付模块，每个模块有自己的 `controller`、`service`、`repository`。

### 2.3 SpringBoot 常见注解有哪些？
- `@SpringBootApplication`：SpringBoot 启动类的核心注解
- `@RestController`：定义接口控制器
- `@RequestMapping`、`@GetMapping`、`@PostMapping`：定义路由
- `@Service`、`@Component`、`@Repository`：标记不同层级的 Bean
- `@Autowired`：自动注入依赖
- `@Configuration`、`@Bean`：手动配置 Bean
- `@Value`、`@ConfigurationProperties`：读取配置
- `@Transactional`：声明事务

### 2.4 `@SpringBootApplication` 做了什么？
它其实是一个组合注解，核心上包含三部分：
- `@SpringBootConfiguration`：声明这是一个配置类
- `@EnableAutoConfiguration`：开启自动配置
- `@ComponentScan`：扫描当前包及子包下的组件

### 2.5 Bean 是什么？Spring 容器在做什么？
Bean：交给 Spring 管理的对象，Spring 容器负责创建这些对象、管理它们的生命周期、处理依赖关系，并在需要时把它们注入到其他对象里。

### 2.6 `@Autowired` 和构造器注入怎么理解？
`@Autowired` 是自动注入依赖的常见方式，不过现在更推荐构造器注入，因为依赖关系更明确，也更方便单元测试。

### 2.7 SpringBoot 一个请求的基本流程是什么？
一个请求大致会经历这条链路：

1. 请求先到 Controller
2. Controller 接收参数并调用 Service
3. Service 处理业务逻辑
4. Service 再调用 Repository / DAO 访问数据库
5. 数据返回后逐层往上返回
6. 最后 Controller 把结果封装成响应返回给前端

如果有拦截器、过滤器、鉴权、日志、异常处理，也会插在这条链路的前后。

### 2.8 SpringBoot 项目一般怎么分层？
最常见的是这几层：
- `controller`：接收请求、返回响应
- `service`：写业务逻辑
- `repository` / `dao`：访问数据库
- `entity` / `model`：数据对象
- `config`：配置类
- `dto` / `vo`：参数对象和返回对象

### 2.9 SpringBoot 中事务一般怎么用？
在 Service 层的方法上加 `@Transactional`，表示这组数据库操作要么一起成功，要么一起失败。

### 2.10 SpringBoot 如何做统一异常处理？
用 `@ControllerAdvice` 和 `@ExceptionHandler` 来统一拦截异常，返回错误码、错误信息，而不是每个接口都手写一遍 `try-catch`。

### 2.11 SpringBoot 如何读取配置？
`@Value` 适合读取单个配置项，`@ConfigurationProperties` 更适合一组相关配置，结构化更强，也更适合复杂项目。

## 3. Redis 了解吗？
Redis 是一个高性能的 key-value 存储系统，常用于缓存、消息队列、计数器等场景。
Redis 速度快的原因：内存存储、数据结构简单、单线程模型减少竞争、I/O 多路复用。

### 3.1 Redis 的常见数据结构
1. 字符串：最基础的数据结构，支持读写、过期、计数。适用场景：用户会话存储、接口限流、计数器、临时缓存数据。
2. 哈希：适合存储结构化数据，可单独修改单个字段。适用场景：用户信息、AI任务参数、工作流配置等对象型数据存储。
3. 列表：有序可重复的链表结构，支持头尾读写。适用场景：消息队列、任务排队、操作日志有序存储。
4. 集合：无序不可重复，支持交集、并集运算。适用场景：用户权限去重、AI模型标签筛选、资源唯一性校验。
5. 有序集合：基于分值排序、不可重复。适用场景：任务优先级排序、用户排行榜、热点资源排序。

### 3.2 Redis 缓存接口数据、登录状态存储、分布式锁
- 缓存接口数据：把热点接口结果先放到 Redis，下次优先读缓存，减少数据库压力。像首页配置、推荐位、商品详情、用户基础信息都很常见。
- 登录状态存储：服务端把 session、token 黑名单、验证码状态、登录态信息放到 Redis，适合多实例共享。
- 分布式锁：多个服务实例并发处理同一资源时，可以用 Redis 做互斥控制，比如防止重复下单、重复发奖、重复执行任务。
分布式锁不能只停留在“`setnx` 一把梭”，还要考虑过期时间、误删别人的锁、续期、幂等和业务兜底。

### 3.3 Redis 的持久化机制
Redis 虽然主要是内存数据库，但也有持久化机制，避免服务重启后数据全丢。
常见有两种：
- RDB：按时间点做快照，恢复速度快，但可能丢最后一段时间的数据
- AOF：把写命令追加记录下来，数据更完整，但文件会更大，恢复也更慢一些

有些场景会同时开启两者，在恢复速度和数据安全之间做平衡。

### 3.4 Redis 的缓存淘汰策略，如何设计缓存更新机制？
缓存淘汰策略是指内存满了以后，Redis 按什么规则删数据。常见会有：
- `noeviction`：不淘汰，直接报错
- `allkeys-lru`：在所有 key 里淘汰最近最少使用的
- `volatile-lru`：只在设置了过期时间的 key 里淘汰最近最少使用的
- 还有 LFU、随机淘汰、按 TTL 淘汰等策略

缓存更新机制常见几种思路：
- Cache Aside：先更新数据库，再删除缓存；下次读取时再回填缓存
- 读穿透回源：缓存没有就查数据库，再写回缓存
- 定时刷新：适合配置类、榜单类数据
- 消息通知更新：数据库变更后发消息通知其他服务刷新缓存

### 3.5 Redis 的缓存雪崩、缓存穿透、缓存击穿
缓存雪崩：大量缓存 key 在同一时间失效，或者 Redis 整体不可用，导致原本应该走缓存的请求一下子全部回源到数据库，数据库压力瞬间暴涨，严重时可能拖垮整个系统。
常见应对：
- 给过期时间加随机值，避免同一时刻集中过期：比如原本统一设置 30 分钟，可以改成 30 分钟 + 随机 1~5 分钟，把失效时间打散，避免同一时刻大量 key 一起过期。
- 热点数据预热：在系统启动、活动开始前，提前把热点数据加载到缓存里，避免一上来大量请求都先打数据库。
- 多级缓存：比如本地缓存 + Redis 缓存。即使 Redis 短暂抖动，本地缓存还能先挡住一部分流量。
- 限流、熔断、降级：如果缓存挂了，不能让所有请求无限制冲击数据库。可以在应用层限流，只放一部分请求回源；必要时直接返回兜底数据、默认页、稍后重试提示。
- 提高 Redis 可用性：比如主从、哨兵、集群，避免 Redis 单点故障直接引发全站雪崩。

缓存穿透：请求查询的数据根本不存在，所以缓存里没有，数据库里也没有。结果每次请求都会穿过缓存直接打到数据库，如果有人恶意高频请求这些不存在的数据，就会给数据库带来很大压力。
常见应对：
- 缓存空对象：如果数据库查出来不存在，也把这个“空结果”缓存起来，比如缓存一个空值并设置较短过期时间。
- 布隆过滤器：可以提前判断一个 key “大概率存在”还是“肯定不存在”。如果过滤器判断某个 id 根本不存在，就直接拦截，不再访问 Redis 和数据库。
- 参数校验，拦掉明显非法请求：比如 id 不能小于 0，不能是特殊字符等。
- 接口限流和风控：如果某个 IP 或用户频繁请求不存在的数据，要做限流、验证码、风控拦截，防止恶意攻击。

缓存击穿：某一个非常热点的 key 在失效瞬间，被大量并发请求同时访问，导致这些请求一起回源数据库，把数据库瞬间打爆。
它和雪崩的区别是：
- 雪崩：很多 key 一起失效
- 击穿：一个热点 key 失效，但这个 key 的访问量特别大
常见应对：
- 热点 key 永不过期
- 逻辑过期：缓存里保留数据本身，同时记录一个“逻辑过期时间”。请求来了即使发现过期，也先返回旧数据，再异步触发缓存刷新。
- 互斥锁：当缓存失效时，只允许一个线程去查数据库并重建缓存，其他线程等待或者快速失败。
- 后台异步刷新：如果某个 key 访问量特别大，可以单独开一个后台线程异步刷新缓存，避免每次都阻塞主线程。
- 请求合并：多个相同请求在应用层合并成一次回源操作，减少数据库压力。

## 4. 异步&消息队列
### 4.1 消息队列是什么，核心是哪几个部分
消息队列：系统之间传递消息的中间层。生产者把消息发到队列，消费者异步处理。它的核心价值是解耦、削峰、异步。

核心部分：
- 生产者：发送消息的一方
- Broker：负责接收、存储、投递消息的中间件
- 队列或主题：消息暂存的位置
- 消费者：消费消息的一方
- 消费成功后会返回 Ack，表示这条消息已经处理完成
- 消费失败后一般会进入重试流程，多次失败后进入死信队列
- 监控和告警用来观察消息堆积、消费失败、重试异常等情况

### 4.2 消息队列的典型场景
典型场景：
- 下单后异步发短信、发邮件、发站内信
- 秒杀、抢购这类流量突增场景，先进入队列削峰
- AI 任务排队，比如图片生成、文本分析、音视频处理

### 4.3 为什么不用同步？
因为很多场景如果全部同步做，会带来几个问题：
- 耗时长，用户要一直等
- 强耦合，一个下游挂了，上游也跟着失败
- 突发流量会直接把系统压垮
- 非核心链路会拖慢核心链路

### 4.4 如何保证消息不会丢
严格来说，消息系统里很难做到绝对不丢，更多是尽量把丢失概率降到足够低，且可追踪、可补偿。

常见保障手段：
- 生产者发送确认，确保消息真的到达 Broker
- Broker 持久化，避免重启后消息消失
- 消费者手动 ack，处理成功后再确认消费
- 消费失败重试，超过次数进入死信队列
- 业务侧做幂等，防止重复消费带来副作用
- 关键链路配合本地消息表、事务消息或补偿机制

## 5. 部署 & 运行环境
### 5.1 Linux 基本命令
- `ls`、`cd`、`pwd`：查看和切换目录
- `mkdir`、`rm`、`cp`、`mv`：目录和文件操作

### 5.2 进程管理（pm2）

- 启动服务
- 守护进程，服务挂了自动拉起
- 查看日志
- 多进程部署
- 零停机重启

常见命令：
- `pm2 start app.js`
- `pm2 list`
- `pm2 logs`
- `pm2 restart app`
- `pm2 stop app`

## 6. 日志&监控
### 6.1 请求日志
请求日志主要记录接口调用链路，比如：
- 请求路径
- 请求参数摘要
- 响应状态码
- 耗时
- traceId 或 requestId
- 用户 ID、设备信息、环境信息

### 6.2 错误日志
错误日志用于记录异常信息，便于定位故障。服务端常记录：
- 错误时间
- 错误堆栈
- 请求上下文
- 机器和实例信息
- traceId

### 6.3 监控指标 QPS、错误率、响应时间
QPS：每秒请求数，反映系统吞吐量。
错误率：失败请求占比，反映系统稳定性。
响应时间：接口处理耗时，常看平均值、P95、P99。

除了这三个，还常看：
- CPU、内存、磁盘、网络
- 容器重启次数
- 数据库连接数
- 缓存命中率
- 消息堆积量
- 页面白屏率、JS 错误率
- Web Vitals，比如 LCP、INP、CLS
