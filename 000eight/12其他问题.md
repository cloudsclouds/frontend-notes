# 其他高频问题
## 1. 如何实现无感刷新？双 token 机制是怎么做的？

无感刷新本质上是用 `Access Token + Refresh Token` 配合实现登录态续期。
一般来说，`Access Token` 有效期比较短，比如 15 分钟，用来访问业务接口；`Refresh Token` 有效期比较长，比如 7 天，用来在 `Access Token` 过期时换发新的 `Access Token`。

前端通常会在请求拦截器里带上 `Access Token`。如果接口返回 `401`，说明当前 token 失效了，这时候前端会拿 `Refresh Token` 去调用刷新接口。刷新成功后，更新本地 token，再把刚才失败的请求重试一次，用户侧就感知不到这个过程，所以叫无感刷新。

这里有一个关键点是并发控制。如果同一时刻很多请求都返回 `401`，不能每个请求都去刷新一次，否则会造成重复刷新。通常会加一个 `isRefreshing` 锁，并把后续失败请求放进队列，等刷新成功后统一重放。


## 2. 前端开发中常见的设计模式有哪些？举个例子
常见的设计模式有观察者模式、单例模式、工厂模式、适配器模式和装饰器模式。

观察者模式：是一对多的依赖关系，也就是一个对象状态变化后，依赖它的对象都会收到通知。
实际开发中常用于事件监听和订阅发布机制。往框架层说，Vue 的响应式更新、Redux 的订阅机制，也都属于这一类思路。

单例模式：确保一个类只有一个实例，并提供全局访问点。
例子有全局状态管理对象，比如Redux / Vuex 的项目里有一个全局 `store`，所有页面共享它；前端路由管理器，整个应用通常只有一个 router 实例。

工厂模式：把对象创建过程封装起来，使用者不需要关心创建细节。
比如封装一个 `createMessage(type)`，根据 `success`、`error`、`warning` 返回不同风格的消息组件；再比如封装请求库实例，根据环境创建不同配置的请求对象。

适配器模式：用于解决两个接口不兼容的问题，通过适配器将一个接口转换成另一个接口。
例子有后端字段不统一，比如一个接口返回 `avatar`，另一个接口返回 `avatarUrl`，会在数据进入页面前做一层转换，统一适配成组件认识的字段。

装饰器模式：是在不改原对象核心结构的前提下，动态增强它的能力。常用于插件化扩展、增强对象能力。
例子有 React 早期的 HOC 给组件增加权限、埋点、日志能力。或者给提交函数包一层防抖、节流或 loading 控制。


## 3. 微前端是什么？适合什么场景？
微前端是一种前端架构思想，是把一个大型前端应用拆成多个可独立演进的子应用。主应用负责路由分发、权限、公共能力和壳子，子应用负责自己的页面和业务逻辑。

它比较适合几类场景。第一是团队规模比较大，不同业务线要并行开发；第二是发布节奏不一致，希望各子系统独立上线；第三是历史系统包袱比较重，希望做增量重构，让新旧系统并存。

如果只是一个中小型项目，团队也不大，业务耦合又很高，那一般不建议强行上微前端，因为它会引入额外的接入、隔离、通信和运维复杂度。

### 3.1 微前端和 SPA、MPA 的区别是什么？
SPA 是单页应用，应用启动时加载一个 HTML，后续通过前端路由和 JS 动态更新页面内容，而不是每次跳转都整页刷新。用户体验比较流畅，但是项目做大以后容易变成单体巨石，首屏资源压力更大、SEO 不友好。

MPA 是多个页面分别独立，天然隔离会更强，但是页面切换通常要重新加载，体验和协作效率一般。

微前端可以理解成介于两者之间。它保留了单页应用的交互体验，同时尽量做到模块级独立，让不同团队能独立开发、独立部署。

### 3.2 `qiankun` 和 `single-spa` 在做什么？
“`single-spa` 更像一个微前端基础框架，它是根据路由匹配子应用，并管理子应用的生命周期，比如 `bootstrap`、`mount` 和 `unmount`。

`qiankun` 可以理解成在 `single-spa` 之上的增强方案。它除了做生命周期管理，还补充了样式隔离、JS 沙箱、资源加载等能力，所以在真实业务里会更完整一些。

### 3.3 为什么微前端一定会遇到隔离问题？
因为多个子应用虽然业务上独立，但运行时通常共用同一个浏览器环境，也就是同一个 `window`、`document`、事件循环和页面容器。

在这种情况下，子应用之间天然会互相影响，比如 CSS 冲突、全局变量污染、事件没有清理、弹窗挂载到 `body` 后样式错乱，甚至卸载后还残留副作用。

所以微前端真正的难点是让多个模块在一个页面里安全共存。
JS 隔离的目标是三件事：第一，子应用运行时尽量不要污染主应用；第二，子应用卸载后尽量恢复现场；第三，多个子应用切换时状态不要串掉。

### 3.3 微前端里的样式隔离是怎么做的？
`qiankun` 里常见有两类思路。

第一类是 `shadow DOM`。它的优点是浏览器原生隔离，效果比较强；缺点是隔离太彻底，很多依赖全局样式和 `body` 挂载的浮层组件会比较麻烦。

第二类是选择器作用域前缀，也就是给子应用样式统一加一个容器范围，比如加 `data-qiankun` 这样的标识。这种方式更轻量，兼容性也更好，但不属于真正的浏览器级隔离，对浮层类场景支持一般。

真实项目里还要结合 `CSS Modules`、`scoped style`、BEM、组件边界和团队规范一起做。

### 3.4 为什么说样式隔离不是银弹？
很多问题并不是给选择器加前缀就能彻底解决。

最典型的是弹窗、下拉框、气泡这些组件，它们经常会通过 Portal 挂到 `body` 下，这时候它已经脱离了子应用容器，作用域样式可能就覆盖不到。

另外，如果团队里存在大量全局样式、第三方组件库样式改写、或者 `body` 级别的主题样式，单靠隔离机制也很难完全兜住。

### 3.5 微前端沙箱机制是怎么理解的？
沙箱可以理解成给每个子应用提供一个相对独立的运行环境，让它看起来像在操作全局对象，但实际上很多读写都会被代理和控制。

常见思路有三种
第一种是快照沙箱，也就是子应用启动前先记录一份 `window` 状态，卸载时再恢复。它简单直观，但性能一般，也不适合多应用并存。

第二种是单应用代理沙箱，重点记录某个子应用修改了哪些全局属性，卸载时只回滚这些改动。它比快照更轻，但仍然是在改真实 `window`。

第三种是多应用代理沙箱，也就是给每个子应用一个独立的代理层。子应用读写的是自己的虚拟全局对象，而不是直接碰真实 `window`。这种方式更适合真实微前端场景，也是我认为更主流的思路。” 

### 3.6 `iframe` 和微前端怎么选？
如果我从取舍上讲，`iframe` 的优势是天然隔离，CSS 和 JS 基本不会互相污染，接入成本也低，所以它适合强隔离、弱交互的场景，比如嵌入第三方系统。

但它的问题也很明显，比如通信不方便、路由体验割裂、滚动和弹窗处理麻烦、登录态共享和样式统一都比较差，整体像一个嵌套网页。

微前端的优势是更接近一个完整产品体验，子应用之间能共享路由、登录态、公共能力和埋点体系，更适合多个内部业务系统的统一整合。

### 3.7 微前端子应用之间怎么通信？
主应用给子应用传参，可以直接走 `props`。
多个子应用共享全局状态，可以通过公共状态管理层。
跨页面或跨上下文通信，可以用 `CustomEvent`、`postMessage`、`localStorage + storage` 事件，或者 `BroadcastChannel`。

通信设计不要一上来就做成子应用直接互相调用接口或者方法，这样耦合会越来越高。更好的做法是把通信协议收敛到主应用或者公共层，让消息格式稳定、可追踪、可回收，这样后面治理成本会低很多。

## 4. 前端埋点一般怎么做？
前端埋点本质上是采集用户行为和页面状态，再上报到分析平台。常见会分成曝光埋点、点击埋点、性能埋点和异常埋点。

第一种是在业务代码里手动埋点，比如在点击事件里调用上报函数；在页面中手动加入 JavaScript 埋点逻辑，用 `fetch` 或 `XMLHttpRequest` 上报；
第二种是在组件层或者路由层做统一封装；
第三种是接入第三方分析平台。

如果我来设计，我会尽量把埋点能力收敛到统一 SDK，包括公共字段、事件规范、重试策略、批量上报和采样控制。

## 5. 定时器每隔一秒用 Promise 发送请求的风险

1. 频繁请求会明显增加服务端负载。
2. 如果请求耗时大于 1 秒，可能发生请求堆积。
3. 会额外消耗网络带宽，影响整体性能。
4. 极端情况下可能被误判为攻击流量。

## 6. 两个页面之间怎么通信？
两个页面之间通信要先看是不是同源、是不是同标签页。

1. URL 参数传递：适合页面跳转时顺带带参数。
2. `localStorage`：同源页面之间可共享数据。
3. `sessionStorage`：同会话内共享，但标签页隔离更明显。
4. Cookie：适合小量状态共享，但不适合复杂通信。
5. `postMessage`：适合跨域窗口、父子页面通信，浏览器原生支持的跨窗口通信方式。
6. `BroadcastChannel`：适合同源多标签页实时同步状态。

### 6.1 页面 1 和页面 2 怎么同步播放歌曲？

把当前播放歌曲、播放进度、播放状态这些信息抽象成共享状态，然后通过跨页面通信机制广播出去。

如果是同源多标签页，会优先考虑 `BroadcastChannel`，因为它语义比较直接，多个页面都能订阅同一个频道。如果要兼容性更强，也可以用 `localStorage + storage` 事件。

如果页面之间是父子窗口或者跨域窗口，那就可以用 `postMessage`。

## 7. 分页请求乱序怎么解决？
分页请求乱序的核心问题是，后发出的请求不一定后回来，旧请求响应可能会把新状态覆盖掉。

解决思路我一般答两种。第一种是为每次请求生成递增的 `requestId`，只有当前最新的请求结果才允许落库，旧请求即使回来也丢弃。第二种是用 `AbortController` 直接取消上一次未完成请求，避免旧请求继续占用资源。

## 8. SPA 首屏怎么优化？
如果结合“输入 URL 到页面显示”的过程来拆，可以这样答：

1. URL 输入后到发起请求前
- DNS 解析可以通过 DNS 预解析、DNS 缓存优化。
- 此外还可以用浏览器缓存资源。

2. 服务端处理和返回 HTML
- 服务端可以做 SSR、缓存 HTML、边缘渲染，降低首字节时间。
- 接口聚合、服务端缓存、数据库索引优化，可以减少后端处理耗时。

3. 浏览器解析 HTML 和下载资源
- 精简首屏 HTML，避免无关内容进入首屏。
- 拆分 JS，首屏只下发当前路由必须的代码。
- 图片、字体、第三方脚本延迟加载。
- 对关键脚本、关键字体使用 `preload`，对后续页面资源使用 `prefetch`。

4. 浏览器执行 JS 和渲染页面
- 减少大包和长任务，避免主线程阻塞。
- 通过懒加载、按需 hydration、虚拟列表减少首屏执行压力。
- 降低首屏组件层级和无意义副作用，减少首次渲染成本。
- 骨架屏、占位图、渐进式渲染提升用户主观体验。

5. 页面可交互后的持续优化
- 长列表做虚拟滚动。
- 图片懒加载。
- 请求并行化，避免串行 waterfall。
- 做好缓存复用，减少二次访问成本。

### 8.1 静态资源一般怎么存储？

- 直接放在服务器文件系统；
- 放 CDN，让资源尽量靠近用户；
- 放对象存储，比如 S3 这类服务，再通过 CDN 分发。
- 浏览器缓存 / 代理缓存：进一步减少重复请求。

### 8.2 性能优化的指标
1. FCP `First Contentful Paint`
- 表示页面第一次渲染出文本、图片、SVG、非白屏内容的时间。
- 它反映的是“用户什么时候第一次看到内容”。

2. LCP `Largest Contentful Paint`
- 表示首屏最大内容元素渲染完成的时间，通常是大图、主标题、大块文本。
- 它更能反映用户感知到的主内容加载速度，是当前最重要的首屏体验指标之一。

3. CLS `Cumulative Layout Shift`
- 表示页面在加载过程中发生布局抖动的程度。
- 典型问题是图片没预留尺寸、异步内容插入、字体切换导致页面跳动。

4. INP `Interaction to Next Paint`
- 衡量用户发生一次交互之后，到页面完成下一次可见绘制之间的延迟。
- 它反映的是“用户点了之后页面多久有反应”。
- 如果 INP 不好，通常要去看主线程是不是被长任务阻塞了、事件回调是不是太重、同步计算是不是太多。

5. TTFB `Time to First Byte`
- 表示从发起请求到收到服务端首字节的时间。
- 它更多反映网络链路、CDN、服务端处理速度和 SSR 性能。

6. TBT `Total Blocking Time`
- 表示页面从开始加载到可交互阶段，主线程被长任务阻塞的总时长。
- 它和 JS 包过大、同步执行任务过多关系很大。

面试里如果要一句话总结，我会说：
- FCP / LCP 看内容出来得快不快
- CLS 看页面稳不稳
- INP 看交互响应快不快
- TTFB 看服务端和网络首包快不快
- TBT 看主线程有没有被 JS 阻塞

### 8.3 Lighthouse Performance 应该怎么理解？
把 Lighthouse Performance 理解成围绕用户加载体验建立的一套指标体系。它是看从内容什么时候出现、页面什么时候能交互、交互过程中会不会卡、布局会不会抖动，来综合衡量页面质量。

## 9. 浏览器常见内核有哪些？
常见浏览器内核主要有 `Blink`、`WebKit`、`Gecko` 和历史上的 `Trident`。

Chrome、Edge、Opera 现在主要是 `Blink`，Safari 是 `WebKit`，Firefox 是 `Gecko`，而老版本 IE 使用的是 `Trident`。

### 9.1 浏览器的关键渲染路径是什么？
关键渲染路径可以理解成浏览器把 HTML、CSS、JS 一步步变成屏幕上像素的过程。

核心流程一般是：
1. 解析 HTML，构建 DOM 树。
2. 解析 CSS，构建 CSSOM 树。
3. 合并 DOM 和 CSSOM，生成渲染树。
4. 布局，计算元素位置和尺寸。
5. 绘制，把颜色、文字、边框、图片填充成像素。
6. 合成，把多个图层合并后显示到屏幕上。

面试里可以顺带补一句：
- 改宽高、位置这类属性，容易触发回流
- 改颜色、背景，通常只触发重绘
- 改 `transform`、`opacity`，通常只走合成层，性能更好

### 9.3 浏览器为什么采用多进程架构？
核心原因是单进程浏览器会有三个问题：不稳定、不流畅、不安全。

- 不稳定：一个页面或插件崩溃，整个浏览器都可能崩。
- 不流畅：某个页面的死循环脚本可能把整个浏览器卡死。
- 不安全：所有能力都在一个进程里，隔离性差。

多进程架构下：
- 一个标签页崩溃，通常只影响自己的渲染进程
- 页面脚本卡住，不会把所有标签页都拖死
- 配合沙箱机制，渲染进程拿不到敏感系统资源，更安全

### 9.4 渲染进程里有哪些核心线程？
1. GUI 渲染线程
- 负责解析 HTML、CSS，构建 DOM、CSSOM、渲染树，做布局和绘制。
- 它和 JS 引擎线程互斥，JS 执行太久会阻塞渲染。

2. JS 引擎线程
- 负责解析和执行 JavaScript。
- 一个渲染进程通常只有一个 JS 主线程。

3. 定时器线程
- 负责 `setTimeout`、`setInterval` 的计时。
- 到时间后，把对应回调推进任务队列。

4. 事件触发线程
- 负责把异步事件的回调放入任务队列，等待 JS 主线程空闲时执行。

5. 网络请求相关线程
- 负责处理异步请求，比如 `fetch`、`XMLHttpRequest`，请求完成后再通知事件系统。

## 10. 一个列表接口怎么设计？
考虑第一是分页，比如 `page`、`pageSize` 或者游标分页；
第二是排序，比如 `sortKey` 和 `order`；
第三是筛选条件，比如关键词、状态、时间范围；
第四是字段裁剪，避免过度返回；
第五是错误码和响应结构规范化。

### 10.1 为什么接口会慢？
接口慢我一般会从前后两侧拆开看。

后端和数据库层面，常见原因包括没有索引导致全表扫描、`join` 过多、返回字段过多、数据量大但没有分页、缓存没命中、下游服务慢等。

前端侧也有可能让人误以为接口慢，比如重复请求、串行请求过多、弱网环境、资源阻塞或者拿到数据后的前端计算太重。

具体要结合链路日志、网络面板和接口耗时拆分来定位。

## 11. 服务端架构你会怎么理解？
理解基础链路
一个典型请求链路可以抽象成：客户端先访问 CDN，动态请求再经过网关，进入具体服务，最后访问数据库或缓存。

CDN 负责静态资源分发和缓存，网关负责鉴权、限流和路由转发，服务层负责业务逻辑，数据库负责持久化，缓存和消息队列则经常用来做性能和解耦。

### 11.1 服务稳定性和降级方案怎么理解？
如果项目从纯 CSR 变成 SSR，那稳定性复杂度会明显上升，因为除了静态资源服务，还多了一层 Node 渲染服务。

这时候我会从两层去设计降级。
第一层是整体降级，也就是当 Node 渲染服务不可用时，通过网关或者配置把页面整体切回 CSR，保证服务可用。
第二层是单次请求降级，也就是某次 SSR 过程中接口报错或渲染异常时，不让整站挂掉，而是让当前请求回退到客户端渲染或者错误兜底页。

## 11.2 高并发场景你会怎么答？比如秒杀
如果问秒杀场景，我会先说明前端能做的事情和服务端要做的事情。

前端能做的是基础限流和体验优化，比如按钮防重、请求节流、排队提示、库存状态及时反馈，避免无意义流量打满后端。

服务端层面通常要做限流、缓存库存、消息队列削峰、异步下单和数据一致性控制。

## 12. 如何聊项目重构收益？
具体可以从构建时间、发布效率、首屏性能、稳定性、可维护性、接手成本这些维度来讲。
像把 Webpack 迁移到 Vite，如果流水线时间下降了 50%，这就是非常具体的收益；如果组件边界更清晰、依赖升级更顺畅、线上问题定位更快，这些也都属于重构价值。

## 13. 数据库基础前端需要懂到什么程度？
### 13.1 索引是什么，为什么索引能加速查询？
索引可以理解成数据库里的一套“快速查找目录”，类似书的目录。没有索引时，数据库可能需要全表扫描；有索引后，就可以更快定位到目标数据。

像 MySQL 里常见是 B+ 树索引，它能把查找复杂度从大范围扫描变成有序查找，所以查询会快很多。

### 13.2 什么情况下索引可能失效？
常见失效场景有：
- 在索引列上做函数、计算、类型转换
- 使用前置模糊查询，比如 `like '%abc'`
- 联合索引没有遵守最左前缀原则
- 条件里对索引列使用 `!=`、`not in`、`is not null` 等，优化器可能不走索引
- 数据区分度太低，优化器判断全表扫描更划算

### 13.3 什么是最左前缀？
联合索引会优先从最左边的字段开始匹配，所以查询条件最好从联合索引的最左列开始写，否则索引利用率会下降。

### 13.4 数据库的分库分表是什么？
当单表数据量太大、单库压力太高时，就会做拆分。
- 分表：把一张大表拆成多张表，比如按用户 ID、时间范围拆
- 分库：把数据拆到多个数据库实例里，分散存储和查询压力
