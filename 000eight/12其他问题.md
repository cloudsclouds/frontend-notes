# 其他高频问题
## 1. 如何实现无感刷新？双 token 机制是怎么做的？
无感刷新：用 `Access Token + Refresh Token`，实现登录态续期。
`Access Token` 有效期比较短，比如 15 分钟，用来访问业务接口；
`Refresh Token` 有效期比较长，比如 7 天，用来在 `Access Token` 过期时换发新的 `Access Token`。

前端在请求拦截器里带上 `Access Token`。如果接口返回 `401`，说明当前 token 失效了，这时候前端会拿 `Refresh Token` 去调用刷新接口。刷新成功后，更新本地 token，再把刚才失败的请求重试一次，用户侧就感知不到这个过程，所以叫无感刷新。

这里有一个关键点是并发控制。如果同一时刻很多请求都返回 `401`，不能每个请求都去刷新一次，否则会造成重复刷新。通常会加一个 `isRefreshing` 锁，并把后续失败请求放进队列，等刷新成功后统一重放。

## 2. 前端开发中常见的设计模式有哪些？
观察者模式：是一对多的依赖关系，一个对象状态变化后，所有依赖它的对象都会收到通知。
实际开发中常用于事件监听和订阅发布机制。框架层面，Vue 的响应式更新、Redux 的订阅机制，也属于这一类思路。

单例模式：确保一个类只有一个实例，并提供全局访问点。
例子有全局状态管理对象，比如 `Vuex` 的项目里有一个全局 `store`，所有页面共享它；前端路由管理器，整个应用通常只有一个 `router` 实例。

工厂模式：把对象创建过程封装起来，使用者不需要关心创建细节。
比如封装一个 `createMessage(type)`，根据 `success`、`error`、`warning` 返回不同风格的消息组件；再比如封装请求库实例，根据环境创建不同配置的请求对象。

适配器模式：用于解决两个接口不兼容的问题，通过适配器将一个接口转换成另一个接口。
例子有后端字段不统一，比如一个接口返回 `avatar`，另一个接口返回 `avatarUrl`，会在数据进入页面前做一层转换，统一适配成组件认识的字段。

装饰器模式：是在不改原对象核心结构的前提下，动态增强它的能力。常用于插件化扩展、增强对象能力。
例子有 React 早期的 HOC 给组件增加权限、埋点、日志能力。或者给提交函数包一层防抖、节流或 loading 控制。

## 3. 微前端是什么？适合什么场景？
微前端是一种前端架构思想，是把一个大型前端应用拆成多个可独立演进的子应用。主应用负责路由分发、权限、公共能力和壳子，子应用负责自己的页面和业务逻辑。

它比较适合团队规模比较大，不同业务线要并行开发；发布节奏不一致，希望各子系统独立上线；历史系统包袱比较重，希望做增量重构，让新旧系统并存。

如果只是一个中小型项目，团队也不大，业务耦合又很高，那一般不建议强行上微前端，因为它会引入额外的接入、隔离、通信和运维复杂度。

### 3.1 微前端和 SPA、MPA 的区别是什么？
SPA：单页应用，应用启动时加载一个 HTML，后续通过前端路由和 JS 动态更新页面内容，而不是每次跳转都整页刷新。用户体验比较流畅，但是项目做大以后容易变成单体巨石，首屏资源压力更大、SEO 不友好。

MPA：多个页面分别独立，天然隔离会更强，但是页面切换通常要重新加载，体验和协作效率一般。

微前端：介于两者之间。它保留了单页应用的交互体验，同时尽量做到模块级独立，让不同团队能独立开发、独立部署。

### 3.2 `qiankun` 和 `single-spa` 在做什么？
`single-spa`：更像一个微前端基础框架，它是根据路由匹配子应用，并管理子应用的生命周期，比如 `bootstrap`、`mount` 和 `unmount`。

`qiankun`：在 `single-spa` 之上的增强方案。它除了做生命周期管理，还补充了样式隔离、JS 沙箱、资源加载等能力。

### 3.3 为什么微前端一定会遇到隔离问题？
因为多个子应用虽然业务上独立，但运行时通常共用同一个浏览器环境，也就是同一个 `window`、`document`、事件循环和页面容器。

在这种情况下，子应用之间天然会互相影响，比如 CSS 冲突、全局变量污染、事件没有清理、弹窗挂载到 `body` 后样式错乱，甚至卸载后还残留副作用。

所以微前端的难点是让多个模块在一个页面里安全共存。

JS 隔离的目标是三件事：第一，子应用运行时尽量不要污染主应用；第二，子应用卸载后尽量恢复现场；第三，多个子应用切换时状态不要串掉。

### 3.4 微前端里的样式隔离是怎么做的？
`qiankun` 里常见有两类思路。

第一类是 `shadow DOM`。它的优点是浏览器原生隔离，效果比较强；缺点是隔离太彻底，很多依赖全局样式和 `body` 挂载的浮层组件会比较麻烦。

第二类是选择器作用域前缀，也就是给子应用样式统一加一个容器范围，比如加 `data-qiankun` 这样的标识。这种方式更轻量，兼容性也更好，但不属于真正的浏览器级隔离，对浮层类场景支持一般。

真实项目里还要结合 `CSS Modules`、`scoped style`、BEM、组件边界和团队规范一起做。

### 3.5 为什么说样式隔离不是银弹？
很多问题并不是给选择器加前缀就能彻底解决。

最典型的是弹窗、下拉框、气泡这些组件，它们经常会通过 Portal 挂到 `body` 下，这时候它已经脱离了子应用容器，作用域样式可能就覆盖不到。

另外，如果团队里存在大量全局样式、第三方组件库样式改写、或者 `body` 级别的主题样式，单靠隔离机制也很难完全兜住。

### 3.6 微前端沙箱机制是怎么理解的？
沙箱可以理解成给每个子应用提供一个相对独立的运行环境，让它看起来像在操作全局对象，但实际上很多读写都会被代理和控制。

常见思路有三种
第一种是快照沙箱，也就是子应用启动前先记录一份 `window` 状态，卸载时再恢复。它简单直观，但性能一般，也不适合多应用并存。

第二种是单应用代理沙箱，重点记录某个子应用修改了哪些全局属性，卸载时只回滚这些改动。它比快照更轻，但仍然是在改真实 `window`。

第三种是多应用代理沙箱，也就是给每个子应用一个独立的代理层。子应用读写的是自己的虚拟全局对象，而不是直接碰真实 `window`。这种方式更适合真实微前端场景。

### 3.7 `iframe` 和微前端怎么选？
`iframe` 的优势是天然隔离，CSS 和 JS 基本不会互相污染，接入成本也低，所以它适合强隔离、弱交互的场景，比如嵌入第三方系统。

但它的问题也很明显，比如通信不方便、路由体验割裂、滚动和弹窗处理麻烦、登录态共享和样式统一都比较差。

微前端的优势是更接近一个完整产品体验，子应用之间能共享路由、登录态、公共能力和埋点体系，更适合多个内部业务系统的统一整合。

### 3.8 微前端子应用之间怎么通信？
主应用给子应用传参，可以直接走 `props`。
多个子应用共享全局状态，可以通过公共状态管理层。
跨页面或跨上下文通信，可以用 `CustomEvent`、`postMessage`、`localStorage + storage` 事件，或者 `BroadcastChannel`。

通信设计不要一上来就做成子应用直接互相调用接口或者方法，这样耦合会越来越高。
更好的做法是把通信协议收敛到主应用或者公共层，让消息格式稳定、可追踪、可回收。

## 4. 前端埋点一般怎么做？
前端埋点本质上是采集用户行为和页面状态，再上报到分析平台。常见会分成曝光埋点、点击埋点、性能埋点和异常埋点。

第一种是在业务代码里手动埋点，比如在点击事件里调用上报函数；在页面中手动加入 JavaScript 埋点逻辑，用 `fetch` 或 `XMLHttpRequest` 上报；
第二种是在组件层或者路由层做统一封装；
第三种是接入第三方分析平台。

我会尽量把埋点能力收敛到统一 SDK，包括公共字段、事件规范、重试策略、批量上报和采样控制。

## 5. 定时器每隔一秒用 Promise 发送请求的风险

1. 频繁请求会明显增加服务端负载。
2. 如果请求耗时大于 1 秒，可能发生请求堆积。
3. 会额外消耗网络带宽，影响整体性能。
4. 极端情况下可能被误判为攻击流量。

## 6. 两个页面之间怎么通信？
两个页面之间通信要先看是不是同源、是不是同标签页。

1. URL 参数传递：适合页面跳转时顺带带参数。
2. `localStorage`：同源页面之间可共享数据。
3. `sessionStorage`：同会话内共享，但标签页隔离更明显。
4. `Cookie`：适合小量状态共享，但不适合复杂通信。
5. `postMessage`：适合跨域窗口、父子页面通信，浏览器原生支持的跨窗口通信方式。
6. `BroadcastChannel`：适合同源多标签页实时同步状态。

### 6.1 页面 1 和页面 2 怎么同步播放歌曲？
把当前播放歌曲、播放进度、播放状态这些信息抽象成共享状态，然后通过跨页面通信机制广播出去。

如果是同源多标签页，会优先考虑 `BroadcastChannel`，因为它语义比较直接，多个页面都能订阅同一个频道。如果要兼容性更强，也可以用 `localStorage + storage` 事件。

如果页面之间是父子窗口或者跨域窗口，那就可以用 `postMessage`。

## 7. 分页请求乱序怎么解决？（并发请求问题）
分页请求乱序的核心问题是，后发出的请求不一定后回来，旧请求响应可能会把新状态覆盖掉，这是一个竞态问题。

解决思路一般有两种。
第一种是为每次请求生成递增的 `requestId`，只有当前最新的请求结果才允许落库，旧请求即使回来也丢弃。
第二种是用 `AbortController` 直接取消上一次未完成请求，避免旧请求继续占用资源。
这两种方式都是通过控制请求的顺序来解决竞态问题。

## 8. 浏览器常见内核有哪些？
常见浏览器内核主要有 `Blink`、`WebKit`、`Gecko` 和历史上的 `Trident`。

Chrome、Edge、Opera 现在主要是 `Blink`，Safari 是 `WebKit`，Firefox 是 `Gecko`，而老版本 IE 使用的是 `Trident`。

### 8.1 浏览器的关键渲染路径是什么？
核心流程一般是：
1. 解析 HTML，构建 DOM 树。
2. 解析 CSS，构建 CSSOM 树。
3. 合并 DOM 和 CSSOM，生成渲染树。
4. 布局，计算元素位置和尺寸。
5. 绘制，把颜色、文字、边框、图片填充成像素。
6. 合成，把多个图层合并后显示到屏幕上。

- 改宽高、位置这类属性，容易触发回流
- 改颜色、背景，通常只触发重绘
- 改 `transform`、`opacity`，通常只走合成层，由 GPU 负责图层变换和透明度计算，因此动画更加流畅，性能更好。

### 8.2 浏览器为什么采用多进程架构？
核心原因是单进程浏览器会有三个问题：

- 不稳定：一个页面或插件崩溃，整个浏览器都可能崩溃。
- 不流畅：某个页面的死循环脚本可能把整个浏览器卡死。
- 不安全：所有能力都在一个进程里，隔离性差。

多进程架构下：
- 一个标签页崩溃，通常只影响自己的渲染进程
- 页面脚本卡住，不会把所有标签页都拖死
- 配合沙箱机制，渲染进程拿不到敏感系统资源，更安全

### 8.3 渲染进程里有哪些核心线程？
1. GUI 渲染线程
- 负责解析 HTML、CSS，构建 DOM、CSSOM、渲染树，做布局和绘制。
- 它和 JS 引擎线程互斥，JS 执行太久会阻塞渲染。

2. JS 引擎线程
- 负责解析和执行 JavaScript。
- 一个渲染进程通常只有一个 JS 主线程。

3. 定时器线程
- 负责 `setTimeout`、`setInterval` 的计时。
- 到时间后，把对应回调推进任务队列。

4. 事件触发线程
- 负责把异步事件的回调放入任务队列，等待 JS 主线程空闲时执行。

5. 网络请求相关线程
- 负责处理异步请求，比如 `fetch`、`XMLHttpRequest`，请求完成后再通知事件系统。

## 9. 一个列表接口怎么设计？
考虑：
分页，比如 `page`、`pageSize` 或者游标分页；
排序，比如 `sortKey` 和 `order`；
筛选条件，比如关键词、状态、时间范围；
字段裁剪，避免过度返回；
错误码和响应结构规范化。

### 9.1 为什么接口会慢？
后端和数据库层面，常见原因包括没有索引导致全表扫描、`join` 过多、返回字段过多、数据量大但没有分页、缓存没命中、下游服务慢等。

前端侧也有可能让人误以为接口慢，比如重复请求、串行请求过多、弱网环境、资源阻塞或者拿到数据后的前端计算太重。

具体要结合链路日志、网络面板和接口耗时拆分来定位。

## 10. 服务端架构怎么理解？
一个典型请求链路可以抽象成：客户端先访问 CDN，动态请求再经过网关，进入具体服务，最后访问数据库或缓存。

- CDN 负责静态资源分发和缓存
- 网关负责鉴权、限流和路由转发
- 服务层负责业务逻辑
- 数据库负责持久化
- 缓存和消息队列则用来做性能和解耦

### 10.1 服务稳定性和降级方案怎么理解？
如果项目从纯 CSR 变成 SSR，那稳定性复杂度会明显上升，因为除了静态资源服务，还多了一层 Node 渲染服务。

这时候从两层去设计降级。
- 第一层是整体降级，也就是当 Node 渲染服务不可用时，通过网关或者配置把页面整体切回 CSR，保证服务可用。
- 第二层是单次请求降级，也就是某次 SSR 过程中接口报错或渲染异常时，不让整站挂掉，而是让当前请求回退到客户端渲染或者错误兜底页。

## 11. Node 中如何处理高并发？
Node 适合高并发，它基于单线程 + 事件循环(Event Loop) + 非阻塞I/O。
虽然 JS 主线程是单线程，但在处理数据库、网络请求、文件读写这类 I/O 操作时，不会阻塞等待，而是先把任务交给底层系统或线程池处理，主线程继续处理其他请求，等结果返回后再执行回调，所以 Node 特别适合 I/O 密集型高并发场景。

比如一个请求里要查数据库：
- Node 收到请求
- 发起数据库查询
- 查询过程中主线程不等待，继续处理别的请求
- 数据库结果回来后，再执行对应回调
所以 Node 的并发本质是“很多请求交替推进”，不是“一个请求一个线程”。

### 11.1 Node.js 不擅长什么？
不擅长 CPU 密集型任务，例如：视频转码、图像处理、大量数学计算、AI训练。
因为JS主线程只有一个，如果计算时间太长，其他请求都要等待，导致系统卡顿。

### 11.2 Node.js 遇到大量计算任务怎么办？
1. worker_threads（工作线程）
把计算任务丢给其他线程执行，主线程负责接收请求，工作线程负责计算，计算完成后把结果返回给主线程。
```js
const { Worker } = require('worker_threads')
const worker = new Worker('./worker.js')
```

2. cluster 或多进程
Node 默认只能使用单核 CPU，生产环境通常使用 cluster 创建多个进程，充分利用服务器多核资源，提高并发处理能力。
```js
const cluster = require('cluster')
cluster.fork()
cluster.on('exit', (worker, code, signal) => {
  console.log(`worker ${worker.process.pid} died`)
})
```
cluster.fork() 会启动一个新进程，cluster.on('exit') 会监听进程退出事件，避免单个进程崩溃影响整个应用。

3. 消息队列
对于耗时较长的任务，可以先将任务写入消息队列，由消费者异步处理，从而提高接口响应速度和系统稳定性。

4. 独立计算服务
对于特别复杂的计算任务，可以拆分为独立服务，例如使用 Python、Java 等语言专门处理计算逻辑，Node 仅负责接口层和业务编排。

## 12. Node.js 的事件循环
Node.js 的事件循环分为 timers、pending callbacks、idle/prepare、poll、check 和 close callbacks 六个阶段，其中 poll 阶段负责处理大多数 I/O 回调，是事件循环的核心。每个阶段执行结束后都会优先处理微任务队列，而 process.nextTick 的优先级又高于 Promise.then。Node.js 通过事件循环和非阻塞 I/O 实现高并发，当 I/O 操作完成后，对应回调会被放入事件循环等待执行，从而实现单线程下处理大量连接。

### 12.1 Event Loop 六个阶段
Node.js 每轮循环大致会经历：timers、pending callbacks、idle/prepare、poll、check、close callbacks。

1. timers
执行：setTimeout()、setInterval()

2. pending callbacks
执行：上一轮循环中被延迟执行的系统级回调
例如：TCP错误、Socket异常、部分系统I/O回调

3. idle / prepare
Node内部使用

4. poll
负责：获取新的I/O事件、执行绝大多数I/O回调
例如：fs.readFile()、mysql.query()、网络请求
这些回调最终大多数都会在 poll 阶段执行。

5. check
执行：setImmediate()

6. close callbacks
执行：socket.on('close')，连接关闭后的回调。

### 12.2 微任务什么时候执行？
Node.js 中：
一轮循环结束再统一执行微任务
每个阶段执行结束都会清空微任务队列，包括：Promise.then()、queueMicrotask()、process.nextTick()

### 12.3 process.nextTick 为什么特殊？
Node.js 有两个微任务队列：nextTick队列和Promise微任务队列
执行优先级：nextTick > Promise

process.nextTick 是 Node.js 提供的一个特殊任务队列，用于在当前调用栈执行完成后立即执行回调。Node.js 会在每个事件循环阶段结束后优先清空 nextTick 队列，然后再处理 Promise 微任务队列。它常用于延迟执行一些初始化逻辑或内部模块调度，但如果递归使用可能导致事件循环被长期占用，从而影响其他异步任务执行。

### 12.4 poll 和 check 谁先执行？
setTimeout(()=>{ console.log('timeout') },0)
setImmediate(()=>{ console.log('immediate') })
结果：不一定
原因：事件循环进入 poll 阶段时：如果 poll 队列为空并且存在 setImmediate，可能直接进入 check
输出：timeout immediate
某些情况下：timeout immediate
因此顺序不稳定。


## 13. Nest 中有用过哪些中间件？手写过哪些中间件？
Nest 里的中间件本质上和 Express 类似，运行在路由处理前，适合做请求级通用逻辑，比如日志、鉴权、上下文注入、限流前置处理。

1. 日志中间件
- 记录请求方法、路径、耗时、状态码、requestId

2. 鉴权中间件
- 解析 `token`、读取用户信息、做基础身份校验

3. 跨域中间件
- 一般直接用 `app.enableCors()`，也可自己扩展头信息

4. 代理信任和真实 IP 处理
- 部署在 Nginx / 网关后时读取 `x-forwarded-for`

5. 请求体大小限制、压缩、静态资源
- 这些很多会直接用 Express 生态的现成中间件

### 13.1 中间件、Guard、Interceptor 的区别
1. Middleware
最早执行，适合做通用预处理，比如日志、requestId、原始 token 解析。

2. Guard
更适合做权限判断，决定“这个请求能不能进控制器”。

3. Interceptor
更适合包裹请求响应流程，比如统一响应格式、耗时统计、缓存、日志增强。

如果是“登录态校验并决定能不能访问”，我更倾向放到 Guard；
如果是“给请求挂一个 userId、traceId”，我会放中间件；
如果是“统一包装返回结构”，我会放 Interceptor。

### 13.2 手写过哪些中间件？
比较常见的是这几类：

1. 请求日志中间件
```ts
import { Injectable, NestMiddleware } from '@nestjs/common'
import { NextFunction, Request, Response } from 'express'

@Injectable()
export class LoggerMiddleware implements NestMiddleware {
  use(req: Request, res: Response, next: NextFunction) {
    const start = Date.now()

    res.on('finish', () => {
      const duration = Date.now() - start
      console.log(`${req.method} ${req.originalUrl} ${res.statusCode} - ${duration}ms`)
    })

    next()
  }
}
```

2. `requestId` 中间件
给每个请求挂一个唯一 id，方便串联日志、接口、消息队列和错误排查。

```ts
import { Injectable, NestMiddleware } from '@nestjs/common'
import { randomUUID } from 'crypto'
import { NextFunction, Request, Response } from 'express'

@Injectable()
export class RequestIdMiddleware implements NestMiddleware {
  use(req: Request, res: Response, next: NextFunction) {
    const requestId = req.headers['x-request-id'] || randomUUID()
    req['requestId'] = requestId
    res.setHeader('x-request-id', String(requestId))
    next()
  }
}
```

3. 简单鉴权中间件
只做 token 提取和基础解析，真正权限判断交给 Guard。

```ts
import { Injectable, NestMiddleware, UnauthorizedException } from '@nestjs/common'
import { NextFunction, Request, Response } from 'express'

@Injectable()
export class AuthMiddleware implements NestMiddleware {
  use(req: Request, res: Response, next: NextFunction) {
    const authorization = req.headers.authorization

    if (!authorization) {
      throw new UnauthorizedException('Missing token')
    }

    req['token'] = authorization.replace('Bearer ', '')
    next()
  }
}
```

### 13.3 Nest 中间件怎么注册？
一般是在模块里实现 `NestModule`，通过 `configure` 注册。

```ts
import { MiddlewareConsumer, Module, NestModule, RequestMethod } from '@nestjs/common'

@Module({})
export class AppModule implements NestModule {
  configure(consumer: MiddlewareConsumer) {
    consumer
      .apply(LoggerMiddleware, RequestIdMiddleware)
      .forRoutes({ path: '*', method: RequestMethod.ALL })
  }
}
```

## 14. Sequelize 如何使用？如何在线上环境做数据迁移？
`Sequelize` 是 Node 里常见的 ORM，用来把表、字段、关联关系映射成 JS / TS 对象，方便做 CRUD、关联查询和事务管理。

### 14.1 Sequelize 基本使用
1. 建立连接
```ts
import { Sequelize } from 'sequelize'

export const sequelize = new Sequelize(process.env.DB_NAME!, process.env.DB_USER!, process.env.DB_PASSWORD!, {
  host: process.env.DB_HOST,
  dialect: 'mysql',
  logging: false,
  pool: {
    max: 10,
    min: 0,
    acquire: 30000,
    idle: 10000,
  },
})
```

2. 定义模型
```ts
import { DataTypes } from 'sequelize'
import { sequelize } from './sequelize'

export const User = sequelize.define('User', {
  id: {
    type: DataTypes.BIGINT,
    primaryKey: true,
    autoIncrement: true,
  },
  name: {
    type: DataTypes.STRING(50),
    allowNull: false,
  },
  email: {
    type: DataTypes.STRING(100),
    allowNull: false,
    unique: true,
  },
}, {
  tableName: 'users',
  timestamps: true,
})
```

3. 常见操作
```ts
await User.create({ name: 'Tom', email: 'tom@example.com' })

const list = await User.findAll({
  where: { name: 'Tom' },
  limit: 10,
  offset: 0,
})

await User.update(
  { name: 'Jerry' },
  { where: { id: 1 } }
)

await User.destroy({
  where: { id: 1 },
})
```

### 14.2 事务怎么做？
涉及多表更新、余额扣减、库存变更这类场景，一般都要走事务。

```ts
const transaction = await sequelize.transaction()

try {
  await User.create(
    { name: 'Alice', email: 'alice@example.com' },
    { transaction }
  )

  await Profile.create(
    { userId: 1, city: 'Shanghai' },
    { transaction }
  )

  await transaction.commit()
} catch (error) {
  await transaction.rollback()
  throw error
}
```

### 14.3 线上环境如何做数据迁移？
线上环境最重要的一点是：不要依赖 `sequelize.sync({ alter: true })` 直接改表。
开发环境可以图快，但线上要走可审计、可回滚的 migration。

常见流程是：

1. 用 `sequelize-cli` 管理 migration 文件
```bash
npx sequelize-cli migration:generate --name add-user-email-index
```

2. 在 migration 里写明确的 `up` / `down`
```js
'use strict'

module.exports = {
  async up(queryInterface, Sequelize) {
    await queryInterface.addColumn('users', 'phone', {
      type: Sequelize.STRING(20),
      allowNull: true,
    })
  },

  async down(queryInterface) {
    await queryInterface.removeColumn('users', 'phone')
  },
}
```

3. 发版时先执行 migration，再切业务代码
```bash
npx sequelize-cli db:migrate
```

### 14.4 线上迁移的注意点
1. 优先做向后兼容迁移
比如先加字段、再发代码使用新字段，最后再删旧字段，不要一步到位。

2. 避免高峰期执行重 SQL
像大表加索引、改字段类型、全表更新，都要评估锁表风险。

3. 数据变更和结构变更尽量拆开
先改表结构，再分批回填历史数据，避免一次迁移太重。

4. 迁移脚本要可重复、可回滚
至少要保证失败时知道怎么处理，而不是手工现场救火。

5. 在 CI/CD 中纳入迁移步骤
让迁移和发版流程绑定，避免“代码上去了，表还没改”。

### 14.5 如果是大表迁移，一般怎么做？
我一般会强调“灰度 + 双写 + 分批回填”这套思路。

比如新增一个字段或新表：
1. 先加新结构，不影响旧逻辑
2. 业务代码开始双写新旧字段
3. 后台脚本分批回填历史数据
4. 校验一致性
5. 读流量切到新字段
6. 确认稳定后再删除旧字段

这样做的核心目的是降低锁表风险和发布风险。

## 15. 项目重构收益怎么理解？
可以从构建时间、发布效率、首屏性能、稳定性、可维护性、接手成本这些维度来讲。
像把 Webpack 迁移到 Vite，如果流水线时间下降了 50%，就是非常具体的收益。如果组件边界更清晰、依赖升级更顺畅、线上问题定位更快，这些也都属于重构价值。
