# 工程化

## 1. Tree Shaking

Tree Shaking 是一种 静态分析并移除未使用代码的技术，主要用于减少最终打包体积。

基于 ES Module 的静态特性，构建工具（如 Webpack、Rollup、Vite）在编译阶段 分析 `import` / `export` 依赖关系，从而确定哪些代码是被使用的，哪些是未被引用的，然后在打包时将未使用的代码移除。

### 1.1 Tree Shaking 的核心流程

1. 构建依赖图：基于 ES Module 的静态导入特性（`import/export`），构建工具在构建阶段即可生成完整的 模块依赖图。
2. AST 静态分析：工具会将源代码解析为 AST（抽象语法树），并标记哪些导出（`export`）被使用。
3. 标记未使用的代码：构建工具遍历 AST，对每个 `export` 做标记：如果有引用 → used；如果无引用 → unused。
4. 删除未使用代码：在打包阶段，构建工具根据标记移除未使用的导出。UglifyJS / Terser 等压缩工具会根据标记的 dead code 进行消除。

### 1.2 为什么 Tree Shaking 依赖 ES Module

ES Module 的特点：静态依赖分析，`import` 和 `export` 语句在编译阶段就能确定模块依赖图。
CommonJS 的问题：`require()` 是动态调用，依赖无法在编译阶段完全确定，构建工具无法准确识别未使用代码。

### 1.3 构建工具如何实现 Tree Shaking

通常在生产模式下，Webpack、Rollup 或 Vite 都会自动开启 Tree Shaking 来优化最终体积。

### 1.4 如何检查 Tree Shaking 是否生效？

使用 Webpack 的 `stats` 分析工具，或者打包后查看是否移除了未使用代码。也可以通过 `Bundle Analyzer` 检查最终包体积和模块依赖。

### 1.5 Tree Shaking 一定能移除所有未使用的代码吗？

不一定。
如果模块存在副作用，比如修改全局变量、注册事件、执行初始化逻辑、引入 CSS 等，构建工具为了保证运行结果正确，就不会删除该模块。
此外，如果 Babel 把 ESM 转成 CommonJS，或者存在动态 `import()` / `require()`，也会影响 Tree Shaking 的静态分析能力。

副作用（side effects）：
一个模块被 import 后，你没有使用它导出的任何变量，它依然会执行一些对外部环境产生影响的代码。
因为构建工具无法确定“删掉这个模块会不会影响运行结果”，所以它就不敢删除。
设置 `sideEffects: false` 是 package.json 中给打包工具的优化提示，表示项目中的模块默认没有副作用，可以安全地进行 Tree Shaking。

## 2. Webpack 核心作用

Webpack 是一个用于现代 JS 应用程序的静态模块打包工具，它的核心作用可以概括为三点：
1. 模块打包：将项目中散落的 JS、CSS、图片等资源模块打包整合，保证依赖引用正确。
2. 编译兼容：利用 Loader 机制，Webpack 能够编译转换浏览器无法直接识别的文件类型，比如 `.ts`、`.less`、`.vue`。
3. 功能扩展：通过 Plugin 机制，Webpack 提供按需加载、代码压缩、环境变量注入等高级功能。

### 2.2 Webpack 的构建流程

首先是初始化阶段，Webpack 会读取配置文件并创建 Compiler 对象。
接着进入编译阶段，从 entry 入口文件开始递归解析所有依赖模块。
在解析过程中，Webpack 会通过 Loader 对不同类型的文件进行转换，比如将 CSS 或 TypeScript 转换成浏览器可识别的 JavaScript，同时通过 AST 分析构建依赖关系。
然后根据依赖关系生成 chunk，实现代码拆分。
最后进入输出阶段，将打包后的资源输出到指定目录。
在整个流程中，Plugin 会通过钩子机制介入各个阶段，对构建过程进行扩展和优化。

### 2.3 Loader vs Plugin

1. Loader 主要用于处理非 JavaScript 文件，本质是一个函数，它在模块加载时对文件内容进行转换，通过module.rules配置使用，例如 babel-loader、sass-loader，
2. Plugin 是用来扩展 Webpack 功能的，本质是一个类，通过监听 Webpack 的生命周期钩子来介入整个构建流程，通过插件机制绑定到Webpack实例上，比如代码压缩、生成 HTML、定义环境变量等。

Loader：
- `babel-loader`：把 ES6 转换成 ES5
- `ts-loader` / `esbuild-loader`：处理 TypeScript
- `sass-loader` / `less-loader`：样式预处理，将 SCSS/SASS/Less 代码转换成 CSS
- `file-loader`：把文件输出到文件夹中，在代码中通过相对 URL 去引用输出的文件 (处理图片和字体)
- `url-loader`：与 file-loader 类似，区别是用户可以设置一个阈值，大于阈值会交给 file-loader 处理，小于阈值时返回文件 base64 形式编码 (处理图片和字体)
- `i18n-loader`: 国际化

Plugin：
- `HtmlWebpackPlugin`：生成 HTML 并注入打包资源
- `DefinePlugin`：注入全局变量
- `BundleAnalyzerPlugin`：可视化打包体积分析
- `MiniCssExtractPlugin`：提取 CSS
- `CopyWebpackPlugin`：复制静态文件

### 2.4 Webpack5 优化

- 持久化缓存、资源模块替代 file-loader、Tree-shaking 增强、模块联邦、提升构建速度；
- 模块联邦：
模块联邦是 Webpack5 提供的一种运行时模块共享机制，可以从远程应用动态加载模块，实现跨项目共享代码，常用于微前端架构，相比 npm 的构建时依赖，它更加灵活但也带来版本和网络上的复杂性。

### 2.5 Webpack 的使用

1. 项目结构
```js
webpack-demo/
├── src/
│   ├── index.js
│   └── index.css
├── webpack.config.js
└── package.json
```

2. 安装依赖
```js
npm init -y

npm install style-loader css-loader --save-dev
```

3. 编写入口文件、 Webpack 配置文件
```js
const path = require('path')

module.exports = {
  mode: 'development',
  entry: './src/index.js',   // 从入口（entry）开始构建依赖图

    filename: 'bundle.js',

      {

          filename: path.resolve(__dirname, 'dist/login/index.html') //输出文件
      })

}
```

```js
npm run 自定义命令（定义在 package.json 中）
```

5. 最终输出为：
```js
dist/bundle.js
```

### 2.6 Webpack HMR

HMR，也就是热模块替换，是指在不刷新页面的情况下更新代码模块。它的实现原理是 Webpack Dev Server 会和浏览器建立一个 WebSocket 连接，当本地文件发生变化时，Webpack 对模块重新编译打包，通过`websocket`告知浏览器执行热更新逻辑。

浏览器接收到更新信息后，会`http`请求去服务器端获取新的模块资源，并通过 HMR API 将旧模块替换为新模块，而不会刷新整个页面。

### 2.7 提高 Webpack 打包速度

1. 优化loader配置，精准匹配文件，缩小文件范围
在使用`loader`时，可以通过配置`include`、`exclude`、`test`属性来精准地匹配哪些文件应用`loader`。

```js
module.exports = {
  module: {
    rules: [
      {
        // 如果项目源码中只有 js 文件就不要写成 /\.jsx?$/，提升正则表达式性能
        test: /\.js$/,
        // babel-loader 支持缓存转换出的结果，通过 cacheDirectory 选项开启
        use: ['babel-loader?cacheDirectory'],
        //使用include来指定编译文件夹只对项目根目录下的 src 目录中的文件采用 babel-loader
        include: path.resolve(__dirname, 'src'),
        //使用exclude排除指定文件夹
        exclude: /node_modules/,
      },
    ]
  },
};
```

2. 优化 resolve.alias 起别名
alias 给一些常用的路径起一个别名，当项目目录结构比较深的时候，一个文件的路径可能是`./../../`的形式，通过配置alias以减少查找过程。
alias 发生在 Loader 之前、打包之前、代码执行之前。

```js
module.exports = {
    ...
    resolve:{
        alias:{
            "@":path.resolve(__dirname,'./src')
        }
    }
}
```

3. 使用cache-loader 进行缓存
在一些性能开销较大的`loader`之前添加`cache-loader`，以将结果缓存到磁盘里，显著提升二次构建的速度。
注意：保存和读取这些缓存文件也会有一些时间开销，所以只对性能开销较大的`loader`使用此`loader`

```js
module.exports = {
    module: {
        rules: [
            {
                test: /\.ext$/,
                use: ['cache-loader', ...loaders],
                include: path.resolve('src'),
            },
        ],
    },
};
```

4. HappyPack 启动多线程
HappyPack 可以将 Loader 的同步执行转换为并行的，这样就能充分利用系统资源来加快打包效率了。
这是一个Webpack插件，它可以将模块的加载和构建过程分解为多个子进程，从而实现多线程构建。

```js
module: {
  rules: [
    {
      test: /.js$/,
      loader: 'happypack/loader?id=js',
      include: [resolve('src')],
      exclude: /node_modules/
    }
  ]
},
plugins: [
  new HappyPack({
    id: 'js',//与rule中指定的id一致
    // 开启四个线程
    threads: 4,//必须配置，用于指定开启几个 worker，建议设置成 os.cpus().length - 1
    verbose: true,//是否输出详细的日志信息
    loaders: ['babel-loader?cacheDirectory'],//如何处理 js 文件，如将其转成 es5 代码
  })
]
```

5. 合理使用 sourceMap
在开发环境下，因为需要调试源代码，一般会开启 sourceMap。
而在生产环境下，为了保护代码的安全且获得更好的性能，我们一般不开启 sourceMap。

1. 使用`Cheap`模式：开启Cheap模式可以大幅度减少构建时间，它只会标记行而不会标记列，因此精度较低，但对于代码调试已经足够。
2. 使用`eval`模式：开启eval模式可以进一步缩短构建时间，因为它会将Source map嵌入到eval中，从而避免了Source map文件的生成和加载。
3. 使用`inline`模式：将Source map嵌入到打包文件中，可以避免Source map文件的下载，但会增加打包文件的大小。
4. 使用`external`模式：将Source map文件分离到单独的文件中，可以避免打包文件过大，同时也便于对Source map文件进行管理。

## 3. Vite 的构建流程

Vite 的构建流程分为两个阶段：开发阶段和生产构建阶段。
在开发阶段，Vite 不会像 Webpack 一样进行整体打包，而是基于浏览器原生的 ES Module，实现按需编译。它启动一个本地开发服务器，然后利用 esbuild（是用go写的，主要用于 JavaScript 和 TypeScript 的编译、打包和压缩，速度比webpack快很多）对依赖进行预构建，把 CommonJS 转换成 ESM，同时合并模块以减少请求数。

浏览器在加载页面时，请求哪个模块，Vite 就实时编译并返回哪个模块。transform 过程中会调用插件体系，比如 .vue 文件会通过 Vue 的编译器转成 JS。 同时它通过 WebSocket 实现 HMR，只更新变更的模块，而不是整页刷新。

生产环境下，执行 build 时，Vite 会调用 Rollup，从 index.html 作为入口开始构建依赖图。然后进行模块分析和代码分割，比如动态 import 会被拆成多个 chunk。同时进行 Tree Shaking，移除未使用代码。最后对 CSS、图片等资源做优化，并生成带 hash 的静态文件输出到 dist 目录。

## 4. 构建工具：Vite vs Webpack
1. 构建方式不同
Webpack 是一个静态模块打包器。它的核心思想是将所有资源（包括 JS、CSS、图片等）视为模块，通过递归解析依赖，构建一个完整的依赖图。在开发环境下，Webpack 需要先打包好所有的资源，然后才能启动开发服务器，项目越大，启动速度越慢。

Vite 它是基于现代浏览器原生 ES 模块的支持，开发阶段利用浏览器直接请求模块，实现了按需编译。Vite 启动时非常快，不需要预先打包整个项目。当浏览器请求某个模块时，Vite 会动态地将该模块编译并返回。但生产环境仍需要打包优化，因此内部使用 Rollup 进行构建。

2. 热更新机制不同
Webpack 需要重新编译模块，虽然`webpack`现在有了缓存机制，但还是无法从根本上解决这个问题。

`Vite`项目中，监听到文件变更后，会用`websocket`通知浏览器，重新发起新的请求，只对该模块进行重新编译，然后进行替换。

3. 适用范围
Webpack 更适合于大型、复杂的企业级项目，或者需要高度定制化构建配置的项目。而 Vite 则非常适合于现代、中小型项目，尤其是使用 Vue、React 等主流框架的项目。

## 6. 模块化
模块是为 Node.js 打包 JS 代码的原始方式。
在 Node.js 中， 每个文件都被视为一个单独的模块。
模块化能提高代码复用性，按需加载，独立作用域；使用标准语法导入和导出使用。

### 6.1 CommonJS VS ESmodule
1. 语法和标准不同：CommonJS 使用 `require` 和 `module.exports`，是 Node 早期模块规范；ES Module 使用 `import` 和 `export`，是 ES6 官方标准。
2. 加载时机不同：CommonJS 是运行时加载，会先加载整个模块对象，再从对象上读取属性；ES Module 是编译时静态加载，会在编译阶段确定依赖关系，只加载需要的导出，因此支持 Tree Shaking。

### 6.2 模块导出导入
1. export（命名导出导入）
导出：`export 修饰定义语句`
导入：`import { 同名变量 } from '模块名或路径'`

- 可以导出多个变量/函数/类，每个导出都有自己的名字。
- 导入时必须使用相同的名字（可以使用 `as` 别名重命名）。
- 适合导出模块中多个功能或工具函数。

```js
// math.js
export const pi = 3.14159;
export function sum(a, b) { return a + b; }
export class Circle {}

// 导入
import { pi, sum, Circle } from './math.js';

// 可以重命名
import { sum as add } from './math.js';
```

2. export default（默认导出）
导出：`export default {}`
导入：`import 变量名 from '模块名或路径'`

- 每个模块只能有 一个默认导出。
- 导入时可以使用 任意名字，不必与导出名字一致。
- 通常用于模块的“主要功能”或“主对象”。

```js
// utils.js
export default function greet(name) {
  console.log(`Hello, ${name}`);
}

// 导入
import greet from './utils.js';  // 名字可以自定义
greet('Alice');

// 默认导出也可以是对象/类
export default class Person {}
```

## 7. 分包策略，减少打包体积
1. 路由级分包
```js
const Home = () => import('./Home.vue') // 每个页面一个 chunk
```
React 提供了内建的懒加载工具 React.lazy 和 Suspense。React.lazy 允许定义一个动态加载的组件，而 Suspense 组件可以指定加载指示器（如旋转的加载图标），在组件正在加载时显示。

```js
import React, { Suspense, lazy } from 'react';
import { BrowserRouter as Router, Route, Switch } from 'react-router-dom';

// 使用 React.lazy 和动态 import() 定义懒加载组件
const HomePage = lazy(() => import('./pages/HomePage'));
const AboutPage = lazy(() => import('./pages/AboutPage'));
const ContactPage = lazy(() => import('./pages/ContactPage'));

function App() {
  return (
    <Router>
      <Suspense fallback={<div>Loading...</div>}>
        <Switch>
          <Route exact path="/" component={HomePage} />
          <Route path="/about" component={AboutPage} />
          <Route path="/contact" component={ContactPage} />
          // ...其他路由
        </Switch>
      </Suspense>
    </Router>
  );
}
```

2. 第三方依赖拆包
```js
manualChunks: {
 react: ['react', 'react-dom'],
 vendor: ['lodash']
}
```

好处：长缓存（不会频繁变化的依赖） 提升缓存命中

3. 公共模块抽离
Webpack 通过`SplitChunkPlugin`可以将应用程序的公共库和应用程序代码分开，防止其中的一个库过大并阻止页面初始加载。

```js
module.export = {
  // 优化配置
  optimization:{
    SplitChunks:{
      // chunks 仅仅针对异步async 请求，我们也可以设置为all
      chunks:"all",
      // 当一个包大于指定的大小时，继续进行拆包
      maxSize:20000
    }
  }
}
// 根据 Module 使用频率分包
module.exports = {
  //...
  optimization: {
    splitChunks: {
      // 设定引用次数超过 2 的模块才进行分包
      minChunks: 2
    },
  },
}
```

4. 动态导入（按需加载）

5. 手动优化依赖分包

Vite 支持 build.rollupOptions.output.manualChunks：

```TypeScript
export default {
  build: {
    rollupOptions: {
      output: {
        manualChunks: {
          vue: ['vue'],
          vendor: ['axios', 'lodash-es'],
        },
      },
    },
  },
}
```

若不希望库自动拆得太散，可以手动划分合适的 chunk，常见做法是：
- vue 单独拆包，浏览器可良好缓存
- 公共工具依赖放入 vendor
- 特大型三方库按模块拆出独立 chunk
结合懒加载组件后，整个 bundle 更加结构化，进一步提升可缓存率。

## 8. CDN
CDN，也就是内容分发网络，是通过将静态资源部署到全球多个节点服务器上，让用户可以从距离最近的节点获取资源，从而减少网络延迟并提升加载速度。
在前端项目中，通常会将 JS、CSS、图片等静态资源上传到 CDN，而 HTML 仍由主站提供。这样不仅可以加快资源加载速度，还可以减轻源站服务器的压力，提高系统的稳定性和可用性。

需求：开发模式使用本地第三方库，生产模式下使用CDN加载引入。

1. 静态资源走 CDN，HTML 不走
```html
<!-- index.html（主站） -->
<script src="https://cdn.example.com/assets/app.8a3f.js"></script>
<link rel="stylesheet" href="https://cdn.example.com/assets/app.8a3f.css">
```

2. CDN + publicPath
```js
// webpack.config.js
module.exports = {
  output: {
    publicPath: 'https://cdn.example.com/assets/',
  },
}

// 打包后
<script src="https://cdn.example.com/assets/app.8a3f.js"></script>
```

3. CDN + Webpack 常见配置组合
分包 + CDN
```js
optimization: {
  splitChunks: {
    chunks: 'all',
  },
}

vendor.js  → CDN
app.js     → CDN
```

3. 动态加载 chunk 也走 CDN
```js
output: {
  publicPath: 'https://cdn.xxx.com/',
}
```

## 9. npm vs pnpm vs yarn
npm 是 Node 默认的包管理工具，采用扁平化 node_modules 结构，每个项目独立安装依赖，可能造成重复安装和磁盘浪费。
pnpm 使用全局 store + 硬链接机制，多个项目可以共享依赖，因此安装更快、占用更小。
yarn 是 Facebook 推出的，解决 npm 早期问题，采用并行安装和缓存机制，速度也较快，有 yarn.lock 锁定版本，依赖安装更一致。

### 9.1 硬链接 vs 软链接
硬链接就像文件的 “别名”，多个硬链接指向同一个文件数据，删除一个硬链接不影响其他，只有所有硬链接都删了，文件数据才会被删除，且硬链接不能跨磁盘分区。
软链接是 “快捷方式”，它自己是个小文件，记录着原文件的路径，原文件删了，软链接就会失效，软链接可以跨分区。

### 9.2 幽灵依赖
幽灵依赖就是代码里使用了某个包，但这个包没有写在自己的 package.json 中，而是依赖于其他包间接安装进来的。
npm 的依赖提升可能让它暂时能运行，但存在风险；pnpm 会禁止这种行为，从而避免幽灵依赖问题。

## 10.Monorepo 理解
Monorepo 是一种项目管理方式，把多个项目或包放在同一个仓库中统一管理。
它的优点是代码共享方便、依赖统一管理、提高版本发布效率，适合大型项目或组件库场景。
缺点是仓库体积大、权限管理复杂，需要借助工具如 pnpm workspace、Turborepo 等来管理和构建。

## 11. Node.js 为何能执行JS？
首先：浏览器能执行JS代码，依靠的是内置的V8引擎（C++程序）
其次：Node.js是基于 Chrome V8 引擎进行封装（运行环境）
区别：都支持 ECMAScript 标准语法，Node.js 有独立的 API，没有 BOM 和 DOM

## 13. 性能优化方案
1. 构建阶段
- 路由懒加载和代码分割
- Tree Shaking 删除未使用代码
- 第三方库按需引入
- 公共依赖拆包，提高缓存命中
- 打包压缩 JS、CSS、图片
- 产物加 hash，便于长缓存

2. 从输入 url 到返回资源
这一阶段对应的优化主要是网络层和资源分发层优化。
可以做的事情有：
- 缓存优化：配置强缓存和协商缓存减少重复请求，静态资源通常配合 hash 文件名和长缓存策略。
- CDN 优化：把 JS、CSS、图片这些静态资源放到 CDN，就近访问，降低时延。
- 传输优化
    - 开启 Gzip 或 Brotli 压缩，减少传输体积。
    - 使用 HTTP2 或 HTTP3 提升多资源并发传输效率。
- 请求层优化：减少不必要请求，合并接口请求，避免页面初始化时过多并发把主链路压满。

3. 返回资源到页面加载完成
- 解析 HTML：
    - 减小 HTML 体积
    - 关键资源优先：首屏关键 CSS 尽早返回，关键脚本不要阻塞 HTML 解析。
    - Script 加载优化：非核心脚本使用 defer 或 async，避免阻塞 DOM 构建。
    - 骨架屏 + 分块渲染：当首屏数据大、数据返回慢时，先渲染骨架屏，减少白屏时间，提升用户感知速度。
- 解析 CSS 和构建 CSSOM：
    - CSS 体积优化
    - 减少复杂选择器：降低样式计算成本，避免过深嵌套和过重匹配。
    - 样式资源缓存：静态 CSS 文件走缓存和 CDN。
- 生成渲染树阶段：
    - 控制 DOM 数量，虚拟列表只渲染可视区域内容
- 布局阶段：
    - 减少回流：不要频繁读取和修改会触发布局的属性。
    - 合并 DOM  
    - 使用 DocumentFragment：批量插入节点，减少中间状态的布局消耗。
    - 避免复杂布局反复计算：深层嵌套、频繁改尺寸、频繁改位置都可能导致布局成本升高。
- 绘制阶段：
    - 图片优化：选择合适图片格式，减少绘制和传输压力。
    - 常见格式使用场景：JPEG 适合照片和大图背景，PNG 适合透明图、图标、Logo，WebP 适合大多数线上图片场景，SVG 适合图标和简单矢量图，AVIF 适合追求更高压缩率的场景，GIF 一般只用于简单动图，很多时候可以用 video 或 Lottie 替代。
    - 图片压缩：构建阶段压缩图片，或者借助 CDN 自动转码。
    - 懒加载：非首屏图片使用 lazy load，减少首屏绘制压力。
    - 图表优化：大数据量图表不要一次性全量绘制。可以做：数据预聚合、数据抽样 sampling、缩放时按需加载局部数据 progressive，大数据量优先使用 Canvas 或 WebGL，少用 SVG
- 合成阶段：
    - 优先使用 transform 和 opacity 做动画：因为它们通常不会触发布局，性能更稳定。
    - 减少不必要图层：图层不是越多越好，过多也会增加内存和合成开销。
    - 控制高频交互更新频率：像 scroll、resize、input 这类事件容易导致频繁重绘和合成，使用防抖节流、requestAnimationFrame 等优化。

4. 渲染完成后，运行阶段
- 请求合并与缓存：多组件共享同一请求时只发一次。可以做 memory cache 或 LRU cache，react 中的 useQuery。请求失败可做重试和兜底。
- Web Worker：把排序、搜索、过滤、聚合这类重计算放到子线程，主线程专注 UI。

5. 监控与预警
- 页面性能指标:FCP、LCP、TTI、CLS
- 稳定性指标:JS Error、白屏、资源加载失败、接口异常
- 监控工具：Sentry、ARMS、自研埋点、Lighthouse、Performance API

FCP: First Contentful Paint，首次内容绘制，表示页面首次绘制任何非空白的DOM内容的时间点。
LCP: Largest Contentful Paint，最大内容绘制，表示页面首次绘制任何非空白的DOM内容的时间点。
TTI: Time to Interactive，首次可交互时间，表示页面首次可交互的时间点。
CLS: Cumulative Layout Shift，累计布局偏移，表示页面布局偏移的累计值。
