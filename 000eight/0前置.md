# 遇到的困难和解决方案
## 正式
在滴滴实习时，我负责一个批量任务页面的开发，接口会返回 runStatus 状态码，需要根据状态码展示中英文状态文案。

当时在使用AI开发的时候，遇到了两个问题：一是页面报错 "Must be called at the top of a setup function"，二是语言切换后状态文案不会更新。
    
屡次无法实现，后来换一种 AI 模型分析问题，发现是在请求完成后调用 useI18n() 和 t() 进行翻译。而 useI18n 属于 Vue Composition API 的 Hook，只能在 setup 顶层同步调用，放在异步回调中会丢失组件上下文。同时翻译结果在请求阶段就已经生成，因此语言切换时不会重新计算。

定位原因后，借助plan计划分析，重新调整了方案：在 setup 顶层获取 t，异步请求阶段只保存原始状态值，状态映射函数只返回国际化 Key，最终在模板渲染阶段再调用 t() 完成翻译。

这样既解决了页面报错问题，也实现了语言切换时状态文案自动刷新。

这次经历让我对 Vue Composition API 的使用边界，以及数据层和展示层职责分离的设计思路有了更深的理解。同时也让我意识到，AI 可以帮助快速定位问题和提供思路，但最终还是需要结合框架原理进行判断和验证。

## HR
在滴滴实习期间，我负责一个批量任务页面的开发，其中有一个需求是根据接口返回的状态，在页面上展示翻译成不同语言的文案。

开发过程中出现了一个比较棘手的问题：页面出现报错，并且在没有研究解决方案，直接调用 AI工具 无法正确解决，并且改动了已有的代码，可能导致其他功能无法正常使用。

后来换一种AI模型分析问题，通过日志和调试定位到问题出在国际化模块的使用方式上，并且借助AI的计划模式重新梳理了数据处理和页面展示的职责边界，把数据存储和文案展示拆开处理，既解决了报错问题，也保证了后续语言切换能够自动生效。

这件事让我收获比较大的一点是，遇到问题时还是要先定位根因，合理利用 AI 的计划模式提升效率，而不是完全放手让 AI 解决所有问题，最终还是需要结合实际业务场景做判断和决策。

# 在使用GPT或Cursor时有没有遇到过“幻觉”？是怎么解决的？ 为什么能生成代码、产生幻觉？
幻觉是指AI生成了看似合理但事实错误的内容。

大模型的底层基于Transformer架构，它通过自注意力机制（Self-Attention）学习词与词之间的依赖关系，从而具备上下文理解能力。
对前端代码生成来说，模型相当于在“预测下一个最合理的token”，因此能写出结构合理的代码，但它并不真正理解逻辑正确性。
