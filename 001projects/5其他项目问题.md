## 1. 监控项目
将“错误信息 + 用户行为 + 性能数据 + 操作回放”结合起来，实现问题的可观测性和可复现性，提升线上问题的定位效率和用户体验优化能力。
1. 错误信息，采集三类错误：
  -  同步错误：window.onerror
  -  Promise 错误：unhandledrejection
  -  资源错误：PerformanceObserver
2. 用户行为，记录用户操作轨迹（breadcrumb）：
  -  点击事件 
  -  路由跳转 
  -  网络请求（fetch / XHR）
3. 性能数据，基于 Web Vitals：
  -  LCP（加载速度） 
  -  FID（响应延迟） 
  -  CLS（页面稳定性）
4. 数据上报，核心目标：稳定 + 高效
  -  批量上报（减少请求） 
  -  定时上报 
  -  失败重试（指数退避） 
  -  多通道（fetch → Beacon API → image） 
5. 录屏回放，基于 rrweb
  -  记录 DOM 变化 + 用户操作 
  -  生成事件流 
  -  可回放用户操作过程 
亮点
1 EventBus 解耦：各模块独立，互不影响
2 防止死循环上报：通过 X-SDK-Internal 标记过滤 SDK 自身请求
3 隐私保护：数据脱敏，忽略敏感 DOM ，黑名单机制 
4 性能优化：rrweb 采样 + 增量，批量上报减少请求，非阻塞上报（Beacon）

非受控组件：指组件内部自行维护状态，使用者只需关注结果
- 注册表单，最后点提交才用数据
- 上传组件，只关心最终文件列表

- 上传时动态禁用按钮（达到上限）

### 2.2 设计组件库的思路
1. 规范约束
把组件 API 当作对外契约来设计，提前统一了 Props、Emits 和插槽的规范，并在设计阶段考虑了受控和非受控两种使用模式。
2. 主题色和样式
把样式单独拆成一个包，通过统一的命名空间实现样式隔离；
主题方面基于 CSS 变量设计了一套语义化变量体系，组件只依赖变量，不感知具体主题。
组件库的样式隔离和业务项目里的 scoped 是两套思路。大多数成熟组件库基本都不会用 scoped，而是用 CSS 命名空间（class 前缀） 来解决样式冲突。因为 scoped 会通过 data 属性生成属性选择器，影响样式覆盖能力，并且在 slot、teleport 等场景下可能失效。实际工程中组件库通常使用 CSS Namespace + BEM 命名规范 实现样式隔离，例如给所有组件统一加前缀，比如 el-、ant-、arco-，形成类似 arco-button、arco-button--primary 这样的 class 结构。这种方式可以保证组件样式不会和业务代码冲突，同时也允许业务侧通过更高优先级的 class 或 CSS Variables 对组件进行定制。
3. 单元测试
Vitest + Vue Test Utils
应测试的内容：
  - Props 对渲染和行为的影响，禁用态、加载态是否生效，样式或状态是否随配置切换
  - 用户交互触发的事件与状态变化
  - 异常或边界输入下的兜底行为
不应测试的内容：
  - 内部响应式状态的具体实现
  - 私有方法、计算属性的中间结果
  - 与浏览器实现强相关的细节（如具体 DOM 结构）
4. 实现按需引入
在构建上使用的是基于 Vite 的组件库构建方案，输出 ESM 模块。
每个组件都有独立的入口，使用方可以只引入需要的组件，构建工具可以基于 ESM 的静态分析能力进行 Tree-shaking，从而减少最终打包体积。
5. 组件文档和示例

### 2.3 Button 组件
1. 不同类型：
Button 组件通过 prop 实现不同类型的显示。定义了6种类型：default、primary、success、warning、danger、info。每种类型对应不同的颜色：
- 通过 ns.m(type) 生成类型修饰符类名（如 el-button--primary）
- 通过 CSS 为每种类型定义不同的背景色、边框色和文字色
- 定义了 hover、focus、active 三种交互状态的颜色变化
2. 不同尺寸
Button 组件通过 prop 实现不同尺寸的显示。组件支持3种尺寸：large、default、small。
3. 禁用状态
Button 组件支持两种禁用状态：disabled 状态、loading 状态：
- 通过 prop 控制按钮的禁用状态
- loading 时也会禁用按钮，防止重复点击
- loading 时显示加载图标，可以通过 slot 自定义

### 2.4 Upload 组件
1. Upload 组件通过监听拖拽事件实现拖拽上传功能。
实现逻辑：
- 拖拽事件：监听 dragover 拖进区域、dragleave 离开区域、drop 松手上传事件
- 拖拽状态：通过 dragover 状态控制拖拽区域的样式
- 文件获取：通过 e.dataTransfer.files 获取拖拽的文件
- 文件上传：调用 uploadFiles 方法上传文件
- 样式反馈：拖拽时改变拖拽区域的样式，提供视觉反馈
2. Upload 组件通过 limit、accept、fileSize 等 prop 实现文件数量、类型、大小限制。
3. Upload 组件实现上传进度显示
```js
import axios from 'axios'

function uploadFile(file) {
  const formData = new FormData()
  formData.append('file', file)

  axios.post('/upload', formData, {
    onUploadProgress(e) {
      const percent = (e.loaded / e.total) * 100
      console.log(percent)
    }
  })
}
```
4.  Upload 组件实现图片预览
Upload 组件通过 URL.createObjectURL 方法实现图片预览。
不需要上传到服务器，把本地 File / Blob 转换成一个浏览器可访问的临时地址URL，用来在浏览器中直接预览图片。
```Vue
<template>
  <div>
    <input type="file" accept="image/*" @change="onChange" />

    <div v-if="previewUrl">
      <img :src="previewUrl" style="width: 200px;" />
    </div>
  </div>
</template>

<script setup>
import { ref } from 'vue'
const previewUrl = ref('')

function onChange(e) {
  const file = e.target.files[0]
  if (file) {
    // 创建预览 URL
    previewUrl.value = URL.createObjectURL(file)
  }
}
</script>
```
### 2.5 Message 组件
1. 不同类型
Message 组件通过 prop 实现不同类型的显示。组件定义了5种类型：primary、success、warning、info、error。每种类型对应不同的颜色和图标。
2. 不同位置的显示
Message 组件通过 prop 实现不同位置的显示。组件支持6种位置：top、top-left、top-right、bottom、bottom-left、bottom-right。
消息堆叠：通过 lastOffset 计算上一个消息的底部位置，当前消息的 top 或 bottom 值为 lastOffset + offset
3.  自动关闭
定时器创建：组件挂载时调用 startTimer 方法，使用 useTimeoutFn 创建定时器，在 duration 时间后调用 close 方法关闭消息。
鼠标交互：鼠标悬停时清除定时器，鼠标离开时重新启动定时器
自动清理：在组件卸载时自动清理定时器，避免内存泄漏
4. 实现动态挂载和销毁
Message 组件使用 Vue 的 createVNode 和 render 函数实现动态挂载和销毁。
创建 VNode：使用 createVNode(MessageConstructor, props) 创建消息组件的 VNode 实例
渲染到容器：使用 render(instance, container) 将 VNode 渲染到指定的容器中
销毁 VNode：使用 render(null, container) 销毁 VNode 实例
清理工作：从 instances 数组中移除对应的实例，调整其他消息的位置
```js
import { createVNode, render } from 'vue'
const vnode = createVNode(MessageComponent, props)
const container = document.createElement('div')
render(vnode, container)
document.body.appendChild(container)
render(null, container)
document.body.removeChild(container)
```

## 3. 其他问题
## 3.1 前端调试思路
调试前端问题时，一般会先判断问题出在前端还是接口，再决定后续怎么排查。

第一步先看 `Network`。如果请求没发出去，或者参数、请求头、接口路径不对，那大概率是前端调用层的问题；如果请求发出去了，但接口报错或者返回数据异常，就优先和后端联调，先确认接口行为是否符合预期。

如果接口返回正常，但页面展示还是有问题，会继续在前端内部定位，常用的方法主要有两种：

1. `console.log()`
- 在关键链路打印请求参数、接口返回值、状态变化和分支判断结果
- 快速确认到底是哪一步的数据开始不符合预期

2. VSCode Debugger
- 在关键逻辑处打断点，逐步执行代码
- 重点看变量值、调用栈和条件分支是否符合预期

如果是异步相关的问题,会重点检查生命周期、依赖关系和状态更新时机，避免出现旧值、竞态覆盖或者组件卸载后还在更新状态的问题。

## 3.2 你遇到过印象深刻的 Bug 吗
### 3.2.1 `useI18n` 在异步回调里调用
印象比较深的是一次接口状态国际化展示的问题。页面需要根据接口返回的 `runStatus` 展示不同语言的状态文案，并支持中英文切换。

当时的表现有两个：
- 页面加载直接报错：`Must be called at the top of a setup function`
- 语言切换后，状态文案不会跟着更新

一开始先排查接口返回值和状态映射逻辑，确认不是接口字段缺失，也不是状态码本身有问题。然后继续看调用栈，发现问题出在异步请求完成之后，在普通函数里调用了 `useI18n()`。

查文档后确认，`useI18n()` 必须在组件 `setup` 顶层同步执行，不能在 `async` 回调、普通函数或者 `mapper/util` 文件里运行时调用，否则当前组件实例上下文已经不存在，就会直接报错。

最开始的思路，是在数据处理阶段直接把 `runStatus` 翻译成最终文案，但这样做有两个问题：
- 现有状态 `map` 是多个模块共用的，改动风险比较大
- 翻译发生在异步阶段，本质上还是没有解决调用时机不对的问题

最后是通过“把翻译延迟到渲染阶段”的方式解决的：
- 在 `setup` 顶层先调用 `useI18n()`，拿到 `t`
- 异步请求阶段只保存原始状态值，比如 `runStatus = 'running'`
- 状态映射函数只负责把状态码转成 i18n key，比如 `status.running`
- 最终在模板渲染时再执行 `{{ t(mapStatusToI18n(row.runStatus)) }}`

这样改完之后，两个问题都解决了：一是 `t()` 在渲染阶段执行，能够拿到正确的 i18n 上下文；二是语言切换或者数据更新触发重新渲染时，文案也会自动重新计算。

我对这个 Bug 印象很深，因为它本质上是一个生命周期和执行时序问题，不只是语法问题，而是展示逻辑放错了层次。

### 3.2.2 `el-select` 下拉面板宽度不生效
另一个印象比较深的 Bug，是一次 Element Plus 下拉框样式异常问题。表现是 `select` 输入框本体宽度可以通过 `scoped` 样式控制，但下拉面板宽度始终不生效。

一开始先从样式覆盖方向排查，比如选择器优先级、`scoped` 是否失效，但都不是根因。

后来通过浏览器看 DOM 结构和组件渲染方式，发现下拉面板并不在当前组件 DOM 树里，而是通过 `Teleport` 挂载到了 `body` 下。这样它就拿不到当前组件 `scoped` 生成的作用域属性，所以样式匹配不上。

最后的解决方式是：
- 给当前 `el-select` 单独指定一个 `popper-class`
- 输入框本体仍然用当前组件内的 `scoped` 样式控制
- 下拉面板的宽度样式写在非 `scoped` 样式里，并通过这个专属类名精确命中

这样既保证了样式能生效，也避免了影响其他下拉框。

## 3.3 git 
### 3.3.1 工作区 vs 暂存区
工作区是实际修改代码的地方，
暂存区是一个中间区域，用来保存即将提交的代码快照。
通过 git add 可以把工作区的修改放入暂存区，再通过 git commit 提交到仓库。

### 3.3.2 冲突
远程主分支与本地分支在 同一代码块上有不同修改，Git 无法自动合并，需要手动解决冲突。
确认本地修改是否覆盖了远程修改的功能，判断是否需要保留远程修改或两者合并。
- git rebase origin/main
- 遇到冲突时按手动合并流程处理
- 使用 git rebase --continue 继续

### 3.3.3 Reset 回退
如果出现问题，可以通过 reset 或 revert 快速回退到稳定版本。

### 3.3.4 多个commit 修改其中一个
```bash
git rebase -i HEAD~4

把要修改的 commit 改成 edit：
pick A

```

## 3.5 Axios二次封装
基于 TypeScript 对 Axios 做了一层封装，主要是把鉴权、错误处理和重试机制从业务代码中抽离出来，统一在请求层处理。

如果在业务代码里零散处理这些逻辑，会导致：
- Token 注入分散在各个接口
- 错误处理风格不统一（有的 toast，有的 silent）
- 接口失败后的重试、降级难以统一治理
- 类型不收敛，接口返回结构不稳定

实现上主要依赖 Axios 的拦截器：
-  在请求拦截器中统一注入 Token，在 request 发出前统一处理，业务侧不需要关心鉴权 
-  在响应拦截器中做错误分层处理，在 response resolve/reject 前统一处理，包括 HTTP 错误（网络错误、超时、4xx / 5xx）和业务错误（后端返回 code ≠ 0、鉴权失效、权限不足） 
- 同时对幂等请求加了失败重试机制，只在网络异常或超时场景触发，并通过重试次数控制避免请求风暴 

另外还处理了 Token 并发失效问题，通过 refresh token + 请求队列的方式，保证只发起一次刷新请求，其余请求等待后重放。

### 3.5.1 Axios 拦截器是同步还是异步的？
- 支持 Promise，形成链式调用
- 请求拦截器是同步的，响应拦截器是异步的

## 3.6 ECharts
### 3.6.1 ECharts setOptions 用过哪些配置
1. 基础图表结构  
最常用的是 `title`、`tooltip`、`legend`、`grid`、`xAxis`、`yAxis`、`series`。  
比如做柱状图、折线图时，一般先确定坐标轴、图例、提示框和主体数据系列。

2. 数据和系列配置  
`series` 是用得最多的，比如：
- `type`：柱状图、折线图、饼图
- `data`：图表数据
- `smooth`：折线平滑
- `barWidth`：柱宽
- `stack`：堆叠图
- `areaStyle`：面积图
- `label`：数据显示
- `itemStyle` / `lineStyle`：颜色和样式定制

3. 交互配置  
- `tooltip`：自定义悬浮提示内容
- `legend`：图例开关
- `dataZoom`：数据缩放，适合大数据量横向滚动
- `toolbox`：导出图片、还原、数据视图
- `emphasis`：hover 高亮效果

4. 布局和展示优化  
- `grid`：控制图表和容器边距，避免标签被截断
- `axisLabel`：坐标轴文字旋转、省略、格式化
- `boundaryGap`：类目轴两端留白
- `color`：统一配色
- `backgroundColor`：背景色

5. 动态更新场景  
如果接口数据是异步的，会在请求回来后再次调用 `setOption` 更新 `series.data`、`xAxis.data`。  
如果只是局部更新，一般只传变更部分，不会整份 `option` 都重建。

### 3.6.2 图表数据量大时怎么优化？
1. 大数据量使用：
  - sampling 降采样, 优先保证趋势表达，而不是逐点渲染。
  - progressive  渐进渲染，避免主线程长时间阻塞，提升首屏可交互时间。
  - dataZoom 视窗裁剪：不是渲染 1 万条，而是只渲染当前视窗的数据。

```js
series: [
  {
    type: 'heatmap',
    data,
    progressive: 1000,        // 每批渲染 1000 条
    progressiveThreshold: 2000 // 超过多少条才启用渐进渲染
  }
]
```

2. 避免重复 init：只初始化一次
ECharts 内部有 diff 算法，会只更新变化的 series 和数据，所以应该复用实例，而不是重新初始化。
- 通过 setOption 更新，只更新数据，不重绘结构
```js
chartInstance.setOption({
  series: [{ data: newData }]
})
```
- 组件销毁时 dispose：如果不 dispose，频繁进入页面会产生多个图表实例，占用内存并导致 resize 重复触发。
```js
chartInstance.dispose()
```

## 3.7 如何实现一个拖拽组件
底层是 HTML5 拖拽 API（draggable、dragstart、dragover、drop）实现。
使用 LogicFlow 的画布坐标系：
- 拖拽开始时写入节点类型，在 dragstart 事件中，把「要添加的节点类型」写入 dataTransfer，这样在 drop 时能拿到类型。
- 拖拽释放：坐标转换 + 添加节点，画布可能被缩放、平移，所以不能用「鼠标相对容器的像素坐标」直接当节点坐标，要用 LogicFlow 的 画布坐标。用 lf.getPointByClient(clientX, clientY) 将视口坐标转换为画布坐标，再 lf.addNode({ type, x, y, text })。

## 3.7.1 连线校验是怎么设计的？
使用 LogicFlow 提供的一个前置拦截事件 connection:allow，是一个连线建立前的校验钩子，当用户从一个节点拖出线，准备连到另一个节点时，真正创建边数据之前，会触发这个事件。

第一类是结构性校验，比如：
- 禁止重复连线
- 禁止节点自连接
- 限制最大出度
第二类是节点类型校验，比如我们审批流里：
- 开始节点只能连审批或条件节点
- 条件节点不能连回开始节点
- 结束节点不能有出边
第三类是业务语义校验，比如：
- 条件节点必须有两个出口
- 某些节点只能有一个入口

实现上，会在 connection:allow 事件中，根据 source 和 target 的类型，返回一个布尔值，表示是否允许连线。
```js
lf.on('connection:allow', (params) => {
  const { source, target } = params
  return true
})
```

## 3.8 基于 JSON Schema 的动态表单引擎
表单逻辑都写在代码里，业务规则一变就要改前端、发版，响应慢。
因此，可设计一个基于 JSON Schema 的动态表单引擎，由后端配置，前端统一渲染。
整个动态表单引擎的核心思路，就是让表单由配置来驱动。
- 前端拿到描述表单结构的配置，先把它解析成统一的字段模型，再根据模型里的组件类型循环渲染出对应的输入框、下拉框等控件。
- 同时，通过配置声明字段之间的依赖关系，前端实时监听数据变化，自动控制字段的显示与必填状态，并根据配置里的数值范围动态生成校验规则。
- 这样一来，表单的逻辑完全由配置决定，业务上只需要修改后端配置，前端无需发版即可生效。

## 3.9 主题化颜色方案
首先是用pinia去存一个属性，同时也存一份在localStorage上，然后在pinia上定义一个方法，在封装的主题切换组件、初始化时候去使用，颜色混合算法是生成衍生色的关键，在暗色背景下过亮的浅色会导致对比度失衡，需要切换基色。

1. 第一步是状态管理。使用 Pinia 来管理主题状态，包括主色 primary 和暗黑模式 isDark，同时把这个状态持久化到 localStorage。这样用户刷新页面或者下次访问时，主题仍然能保持。Pinia 中封装了方法：用于更新主题状态并同步修改 DOM 和 localStorage，初始化加载本地保存的主题等。
2. 第二步是样式应用。主题色通过 CSS 变量控制，比如 --el-color-primary，扩展多套主题只需在 theme.css 中定义多组变量（如 .dark-theme { ... }、.light-theme { ... }）。用户修改主题色或者切换暗黑模式时，在 updateTheme 方法里同时修改 DOM，使得全局样式响应式生效。同时，颜色混合算法是生成衍生色的关键，根据主色生成浅色或深色衍生色，保证暗黑模式下视觉对比正常，避免过亮或过暗的颜色导致对比度失衡。  
3. 第三步是组件交互。封装了一个 ThemeSwitch 组件，包含颜色选择器和暗黑开关。通过修改全局 CSS 变量（如 :root { --primary-color: #xxx; }）或切换 className 实现主题切换。用户操作时，会调用 Pinia 的 updateTheme 方法更新状态，状态变化立即反映到全局样式上，实现动态切换。  

## 3.10 面包屑的整体流程
1. watchEffect 监听当前路由变化，只要路由变化，自动重新计算；如果不是重定向页，就重新计算面包屑
2. 根据路径深度决定：
  - 普通层级路由用 route.matched（当前路由匹配到的父级到子级路由数组）
matched = route.matched.filter((item) => item.meta && item.meta.title)
  - 多级菜单路径：从权限路由表 permissionStore.defaultRoutes 里递归找出对应层级，把找到的父子路由按顺序压入 matched
3. 过滤掉不显示的项：如果这个路由明确标记了 noRedirect 或者它本身就是最后一级，那就只显示纯文本
4. 点击可跳转到对应路由：如果路由配置里有 redirect 就跳到 redirect，否则直接跳 path

## 3.11 单点登录（SSO）流程是怎样的？
访问时检查本地 ticket，若无则重定向至 SSO 认证中心。
用户认证成功后，SSO 携带 ticket 跳回前端；前端提取 ticket 存入本地，后续请求自动携带。
后端验证 ticket 有效性并返回用户信息。同时通过时间戳实现滑动会话（如 5 小时无操作需重新登录），确保安全。
