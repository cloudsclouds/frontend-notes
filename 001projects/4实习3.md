# 实习 4：Code Sprite AI IDE 助手

## 0. 项目速记
### Q1：这个项目是做什么的？
Code Sprite 是一个 VS Code 扩展，把 AI 聊天助手嵌入到 VS Code 中。后端运行在 VS Code 扩展宿主里，主要使用 TypeScript 实现；主聊天界面是基于 Vite 构建的 Vue 3 Webview。

项目通过子进程方式启动 Code Sprite，并在 VS Code 内围绕 AI 编程工作流建设了一整套能力，包括多标签会话、对话持久化、文件变更追踪与 diff 预览、权限控制与 yolo 模式、Skill/Plugin/MCP 生态集成、OpenAI 兼容代理路由、按标签或预设隔离 token，以及监控面板等。

### Q2：面试时怎么概括亮点？
1. 负责文件变更追踪和 diff 预览能力，覆盖 AI 触发的 write/edit 两类文件修改场景，基于文件快照和差异算法计算变更内容，让用户在应用修改前可以清晰看到新增、删除和修改区域。
2. 针对 bash 命令引入白名单与变更收敛策略，对高风险命令进行权限判断，并在对话结束后结合 `git status` 追踪实际落盘文件，提升 AI 执行命令后的可控性和可回溯性。
3. 参与 Skill 技能市场能力建设，包括用户上传技能包的结构校验、安全校验、元数据解析、埋点采集和内置技能自动安装，让技能可以在用户本地环境中稳定分发和运行。
4. 支持项目级和全局级 MCP 配置接入，并区分普通模式和 D2C 模式的运行环境，在隔离进程中加载专用 API 地址和技能配置，降低不同工作流之间的上下文和权限污染。

### Q3：这段经历可以怎么写到简历里？
- 参与 Code Sprite AI 编程助手建设，基于 VS Code Extension + Vue 3 Webview 实现多标签会话、对话持久化、文件变更追踪、diff 预览、权限控制、Skill/MCP 集成等能力。
- 负责 AI 文件修改追踪模块，针对 write/edit 两类操作维护修改前后文件快照，基于 Myers Diff/LCS 思路生成行级差异，并在 Webview 中展示新增、删除、修改内容，提升用户对 AI 改码结果的确认效率。
- 设计命令执行后的变更收敛机制，对 bash 命令进行白名单匹配和权限判断，并在会话结束后结合 `git status` 二次扫描实际变更文件，解决 shell 命令绕过文件 API 导致的变更遗漏问题。
- 参与 Skill 技能市场与内置技能分发能力建设，完成技能包上传校验、清单解析、安全检查、埋点采集和本地自动安装流程，支持按场景预置技能并降低用户配置成本。
- 接入项目级/全局级 MCP 配置与 OpenAI 兼容代理路由，支持按标签、预设隔离 token 和模型配置，并在 D2C 场景下通过独立进程与专用 API 地址隔离运行环境。

## 1. 文件变更追踪与 diff 预览
### Q1：为什么要做文件变更追踪？
AI 编程助手和普通聊天产品最大的区别是，AI 不只是回答问题，还会真的修改用户工作区里的文件。如果用户不知道 AI 改了哪些文件、每个文件改了什么，就很难放心接受结果。

所以这个模块的目标是：把 AI 产生的文件变更从“黑盒执行”变成“可追踪、可预览、可回滚、可审计”的过程。用户在对话中可以看到每次 write/edit 操作影响了哪些文件，也可以通过 diff 预览确认具体变更。

### Q2：write 和 edit 两种模式有什么区别？
`write` 更像是整文件写入，AI 会直接生成一份完整的新内容。它的处理方式是：

1. 写入前读取旧文件内容，如果文件不存在就标记为新增文件。
2. 写入后拿到新内容。
3. 对旧内容和新内容做 diff。
4. 记录文件路径、操作类型、变更摘要和 diff 结果。

`edit` 更像是局部修改，AI 通常会给出原始片段和替换片段。它的处理方式是：

1. 先根据目标片段在原文件中定位修改区域。
2. 应用替换后得到新文件内容。
3. 再统一进入 diff 计算流程。

虽然 write/edit 的触发方式不一样，但最后都会收敛成统一的 `beforeContent -> afterContent -> diffResult` 流程，方便前端展示和后续审计。

### Q3：diff 用的是什么算法？
可以说使用的是基于 Myers Diff / LCS 思路的文本差异计算。

它的核心目标是找出从旧文本变成新文本所需的最短编辑路径，也就是哪些行被删除、哪些行被新增、哪些行保持不变。相比简单逐行比较，这类算法能更好处理插入、删除导致的行号整体偏移问题。

在项目里一般会分两层展示：

- 行级 diff：先按行切分，计算哪些行新增、删除或保持不变。
- 字符级 diff：对于同一块修改区域，再做更细粒度的字符差异，高亮具体改动位置。

这样用户既能快速扫一眼文件整体变化，又能看到某一行里到底改了哪个变量名、参数或条件判断。

### Q4：diff 结果的数据结构可以怎么设计？
可以把每个文件的变更抽象成一个统一结构：

```ts
type FileChange = {
  filePath: string;
  changeType: 'create' | 'modify' | 'delete';
  source: 'write' | 'edit' | 'bash' | 'git-status';
  beforeContent?: string;
  afterContent?: string;
  hunks: DiffHunk[];
};

type DiffHunk = {
  oldStart: number;
  oldLines: number;
  newStart: number;
  newLines: number;
  lines: DiffLine[];
};

type DiffLine = {
  type: 'add' | 'remove' | 'context';
  oldLineNumber?: number;
  newLineNumber?: number;
  content: string;
};
```

前端只需要消费这个结构，就可以渲染类似 GitHub 的 diff 视图，包括行号、新增删除颜色、高亮块和文件列表。

### Q5：怎么避免 AI 修改文件后 diff 漏掉？
主要做了两层兜底。

第一层是工具调用链路内追踪。AI 通过 write/edit 工具修改文件时，会在工具执行前后主动记录文件快照，正常情况下这部分最准确。

第二层是会话结束后的工作区扫描。因为 AI 可能执行 bash 命令，比如 `npm run format`、脚本批量生成文件、移动文件等，这些变更不一定会经过 write/edit 工具。所以在对话结束后，会再执行一次 `git status` 或读取 Git 变更状态，把实际落盘但没有被工具链记录到的文件补充进变更列表。

这样可以覆盖两类路径：

- 显式文件工具修改：通过 before/after 快照追踪。
- shell 命令间接修改：通过 Git 工作区状态兜底追踪。

## 2. Bash 命令白名单与变更收敛
### Q1：为什么 bash 命令需要单独处理？
bash 命令的能力太强，既可能只是读文件、跑测试，也可能修改、删除、移动大量文件。如果完全放开，用户很难判断 AI 到底做了什么；如果完全禁止，又会影响 AI 编程助手的效率。

所以这里需要做分级控制：低风险命令可以自动执行或轻量确认，高风险命令需要用户授权，涉及文件写入的命令执行后还要补充追踪实际变更。

### Q2：白名单怎么设计？
可以把命令按风险分成几类：

- 只读类：`ls`、`pwd`、`cat`、`rg`、`git status`、`git diff` 等，风险较低。
- 构建测试类：`npm test`、`npm run build`、`pnpm lint` 等，通常允许，但需要关注是否会生成产物。
- 写入类：`npm run format`、代码生成脚本、`touch`、重定向写文件等，需要追踪结果。
- 高风险类：删除、重置、强制覆盖、系统级命令等，需要明确拦截或用户确认。

实现上不会只做字符串包含，而是会解析命令的主命令、参数和工作目录，再结合白名单规则判断是否允许执行。

### Q3：为什么执行完 bash 后还要看 `git status`？
因为 bash 命令对文件的影响可能是间接的。比如格式化命令不会告诉系统具体改了哪些文件，代码生成命令可能一次性创建多个文件。只靠命令本身很难准确知道实际变化。

所以在对话结束或命令执行后，通过 `git status --porcelain` 获取工作区真实变化，再和工具链已经记录的变更做 merge：

1. 已记录的文件直接保留详细 diff。
2. 未记录但出现在 Git 状态里的文件，补充为 bash 间接变更。
3. 对新增/修改文件再读取内容生成 diff。
4. 对删除文件记录删除状态和旧文件路径。

这样可以保证最终变更面板展示的是“真实工作区状态”，而不是只展示 AI 工具自己知道的那部分。

### Q4：这个模块怎么体现提效？
对用户来说，提效主要体现在三个方面：

- 不需要自己去终端里反复 `git diff`，对话过程中就能看到 AI 改了什么。
- 对 bash 间接产生的变更也能自动收敛，减少漏看文件的风险。
- 文件级变更列表和 diff 预览让用户可以快速判断是否接受 AI 结果，降低 review 成本。

## 3. Skill 技能市场
### Q1：Skill 是什么？
Skill 可以理解成一组可复用的 AI 工作流能力，通常包含说明文档、配置文件、脚本、模板或工具声明。它把某类高频任务沉淀成标准能力，比如前端代码审查、UI 设计建议、文档生成、D2C 页面生成等。

对 Code Sprite 来说，Skill 的价值是让 AI 助手从“通用聊天”变成“可扩展的专业工作台”。用户可以按自己的业务场景安装技能，也可以上传团队内部技能。

### Q2：技能市场做了哪些能力？
技能市场本身在另一个项目里，但可以把它包装成 Code Sprite 生态的一部分来讲，因为它最终服务的是同一套 Skill 分发和运行体系。

主要能力包括：

- 上传技能包：用户上传 zip 格式技能包。
- 结构校验：校验是否包含必要的 manifest、入口文件、说明文档等。
- 安全检查：检查危险脚本、异常路径、越权文件访问、可疑依赖等。
- 元数据解析：解析技能名称、版本、描述、作者、适用场景和权限声明。
- 埋点采集：记录上传、校验失败、安装、启用、调用等关键链路数据，用于分析技能使用情况。
- 本地安装：校验通过后下载安装到用户本地技能目录。
- 内置技能：通过全局配置自动拉取某些预置技能，让用户开箱即用。

### Q3：用户上传 zip 后为什么要做安全校验？
因为 Skill 本质上可能包含脚本和配置，如果不校验就直接安装到用户本地，会有安全风险。比如恶意脚本读取用户文件、路径穿越覆盖系统文件、依赖包里包含不安全逻辑等。

所以上传后会先在受控环境里解压和扫描，而不是直接执行。重点检查：

- zip 内是否存在 `../` 这类路径穿越。
- manifest 字段是否完整、版本是否合法。
- 是否声明了超出能力范围的权限。
- 是否包含高风险命令或敏感文件访问。
- 包体大小、文件数量、入口文件类型是否符合限制。

### Q4：埋点是怎么设计的？
埋点不是简单记录“点了按钮”，而是围绕技能生命周期设计：

- upload_start：开始上传。
- validate_success / validate_failed：校验成功或失败，失败时记录原因类型。
- install_success / install_failed：安装成功或失败。
- skill_enable / skill_disable：启用或停用技能。
- skill_invoke：技能被调用，记录技能 ID、版本、场景和耗时。

这样后续可以分析哪些技能安装率高、哪些技能校验失败多、用户在哪一步流失，以及内置技能是否真的被使用。

### Q5：怎么把“注入脚本发请求”讲得更专业？
不要直接说“向用户上传的 zip 注入 nodejs 脚本发送请求”，这个说法在面试里容易让人误解成不安全操作。

更建议说：

> 在技能包上传和安装链路中，设计了受控的校验与埋点采集机制。系统会在隔离环境中解析技能包结构和 manifest，并通过统一的 Node.js 校验脚本上报校验结果、失败原因和安装状态，用于后续分析技能质量和用户转化。

这样表达重点是“受控、隔离、校验、上报结果”，会更像正常工程方案。

## 4. 内置 Skill 与 D2C 隔离模式
### Q1：内置 Skill 是怎么做的？
内置 Skill 主要解决新用户冷启动问题。如果用户第一次打开 Code Sprite 就要自己找技能、下载技能、配置技能，成本会很高。

所以可以在全局配置里维护一组预置技能列表，包括技能 ID、版本、下载地址、校验摘要和适用场景。扩展启动或用户进入特定模式时，会检查本地是否已安装对应技能：

1. 读取全局技能配置。
2. 检查本地技能目录是否存在目标技能和版本。
3. 不存在或版本过旧时，从指定地址下载。
4. 校验包完整性和 manifest。
5. 安装到本地技能目录。
6. 注册到当前会话可用技能列表。

### Q2：D2C 模式为什么要和普通模式隔离？
D2C 模式一般会处理设计稿到代码生成这类任务，依赖的 prompt、技能、上下文、API 地址和权限都可能和普通代码助手不同。如果混在一起，容易出现配置污染，比如普通会话误用 D2C 的 API，或者 D2C 任务读取到普通会话的上下文。

所以会用独立进程或独立运行环境隔离：

- 独立的 API URL。
- 独立的 token 或代理配置。
- 独立的技能目录或技能白名单。
- 独立的上下文和缓存。
- 独立的日志与监控标识。

这样 D2C 和普通模式可以复用底层框架，但运行时配置彼此隔离。

### Q3：这种隔离有什么工程价值？
主要有三个价值：

- 稳定性：某个模式异常不会影响另一个模式。
- 安全性：权限、token、技能范围可以分开控制。
- 可观测性：日志和埋点可以按模式区分，方便定位问题。

## 5. MCP 配置接入
### Q1：MCP 在项目里解决什么问题？
MCP 解决的是 AI 助手接入外部工具和上下文资源的问题。通过 MCP，Code Sprite 可以用统一方式连接不同的工具服务，比如文件系统、设计稿服务、数据库查询、文档检索、内部平台 API 等。

如果没有 MCP，每接一个工具都要在扩展里写一套定制逻辑。接入 MCP 后，可以通过标准协议读取工具列表、参数 schema 和调用方式，让工具接入更统一。

### Q2：项目级 MCP 和全局 MCP 有什么区别？
全局 MCP 是用户维度的配置，适合所有项目通用的工具，比如个人常用文档检索、通用代码搜索、全局设计规范等。

项目级 MCP 是当前工作区维度的配置，适合和项目强绑定的工具，比如当前项目的接口文档、私有组件库、业务知识库、项目数据库等。

加载时可以按优先级合并：

1. 读取全局 MCP 配置。
2. 读取当前工作区 MCP 配置。
3. 按服务名或 ID 合并，项目级配置可以覆盖全局配置。
4. 校验 schema 和权限。
5. 注册到当前会话的工具列表。

### Q3：MCP 配置接入有什么亮点？
亮点不只是“支持 MCP”，而是做了配置分层和运行时注册：

- 配置分层：支持全局和项目两级配置，兼顾个人习惯和项目上下文。
- 动态发现：根据 MCP Server 暴露的 schema 动态加载工具能力。
- 权限控制：不同工具可以声明不同权限，和 yolo/确认模式联动。
- 会话隔离：不同标签页可以加载不同 MCP、token 和模型预设。
- 错误兜底：MCP 连接失败时不会阻塞主聊天链路，而是在工具面板提示异常。

## 6. OpenAI 兼容代理路由与 token 隔离
### Q1：为什么要做代理路由？
Code Sprite 可能接入不同模型服务，但很多模型都兼容 OpenAI API 格式。为了让上层聊天逻辑不用关心具体供应商，可以在扩展侧做一层 OpenAI 兼容代理路由。

上层只提交统一的 chat/completions 或 responses 风格请求，代理层根据当前标签页、模型预设、D2C 模式或用户配置，决定请求发到哪个 API URL、使用哪个 token、使用哪个模型参数。

### Q2：按标签或预设隔离 token 有什么价值？
多标签会话里，不同任务可能需要不同模型、不同 token 或不同代理地址。如果所有标签共用一份配置，就会出现上下文和计费混乱。

按标签或预设隔离后：

- A 标签可以使用普通代码助手模型。
- B 标签可以使用 D2C 专用模型。
- C 标签可以使用团队内部代理。
- 每个标签的 token、baseURL、模型参数互不影响。

这样用户可以同时处理多个 AI 工作流，不需要频繁切换全局配置。

## 7. 监控面板
### Q1：监控面板可以讲什么？
监控面板主要用于提升可观测性。AI 编程助手涉及模型请求、工具调用、文件修改、MCP 连接、技能加载、子进程状态等多个链路，如果出问题只靠日志很难定位。

面板可以展示：

- 当前子进程状态。
- 会话请求耗时、成功率和错误信息。
- token 使用情况。
- 工具调用次数和失败原因。
- MCP Server 连接状态。
- Skill 加载状态。
- 文件变更数量和 diff 生成耗时。

这类能力在简历里可以写成“建设监控面板和埋点链路，提升 AI 助手运行状态、工具调用和文件变更链路的问题定位效率”。

## 8. 项目最难的地方
### Q1：如果面试官问项目最难的地方，怎么说？
可以重点讲“AI 修改代码的可控性”。

AI 编程助手的难点不是单纯调用模型，而是模型执行动作后，用户能不能知道发生了什么、能不能确认风险、能不能回溯结果。尤其是文件修改既可能来自 write/edit 工具，也可能来自 bash 命令，还可能由格式化、代码生成这类间接命令产生。

我的处理思路是把所有变更都收敛到统一的文件变更模型里：

1. write/edit 工具执行前后记录文件快照。
2. 基于 diff 算法生成行级和字符级差异。
3. bash 命令执行前做白名单和权限判断。
4. 命令执行后通过 `git status` 扫描真实工作区状态。
5. 将工具链记录和 Git 状态合并，补齐遗漏文件。
6. 在 Webview 里展示文件列表、变更摘要和 diff 详情。

最终让用户可以在 VS Code 里直接完成“AI 执行、变更查看、结果确认”的闭环。

## 9. 一分钟口述版本
我实习期间参与的是 Code Sprite，一个嵌入 VS Code 的 AI 编程助手。它的后端运行在 VS Code 扩展宿主里，使用 TypeScript 实现，聊天主界面是 Vite + Vue 3 Webview。这个项目不是简单的聊天窗口，而是围绕 AI 编程做了多标签会话、对话持久化、文件变更追踪、diff 预览、权限模式、Skill/MCP 生态和模型代理路由。

我主要负责的是文件变更追踪和 diff 预览。因为 AI 会通过 write/edit 工具直接改文件，也可能通过 bash 命令间接改文件，所以我设计了一套统一的变更收敛流程：工具执行前后记录文件快照，基于 Myers Diff/LCS 思路计算行级差异；对于 bash 命令，会先做白名单和权限判断，执行后再结合 `git status` 扫描真实工作区，把没有经过工具链的文件变更补回来。这样用户不用自己反复看终端 diff，在对话里就能看到 AI 到底改了哪些文件、每个文件改了什么。

另外我也参与了 Skill 技能市场和 MCP 配置接入。技能市场这块主要做上传校验、安全扫描、元数据解析、埋点采集和内置技能自动安装；MCP 这块支持全局和项目两级配置，并且在 D2C 模式下通过隔离进程加载专用 API 地址、token 和技能配置，避免和普通会话互相污染。

## 10. 面试追问速记
### Q1：为什么不用直接展示 `git diff`？
`git diff` 只能反映 Git 工作区最终状态，但不能知道每次 AI 工具调用的来源、操作类型和上下文。项目里需要把变更和具体对话、工具调用、权限确认关联起来，所以工具链内的快照追踪是主路径，`git status/git diff` 更适合作为 bash 命令后的兜底补偿。

### Q2：如果用户文件很大，diff 会不会卡？
会做几类优化：

- 限制单文件最大 diff 大小，超出后只展示摘要。
- 优先做行级 diff，只有用户展开具体 hunk 时再做字符级 diff。
- diff 计算放到异步任务或 extension host 的非阻塞流程里，避免卡住 Webview。
- 对未变化文件通过 hash 或 mtime 快速跳过。

### Q3：如何处理二进制文件？
二进制文件不做文本 diff，只展示文件新增、删除或修改状态，并提示无法预览文本差异。判断方式可以基于文件类型、MIME、扩展名或读取前几个字节检测不可见字符比例。

### Q4：权限/yolo 模式是什么？
普通模式下，高风险操作需要用户确认，比如写文件、执行命令、调用敏感 MCP 工具等。yolo 模式更偏自动执行，会减少确认步骤，但仍然保留基础白名单、高危命令拦截和最终变更追踪，保证效率和安全之间有平衡。

### Q5：MCP 连接失败怎么处理？
MCP 连接失败不能影响基础聊天功能。一般会把 MCP Server 标记为不可用，在工具列表或监控面板展示失败原因，并允许用户重试连接。当前会话仍然可以继续使用模型和本地文件能力。
