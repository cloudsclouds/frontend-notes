# 实习 3：AI 应用低代码编排平台

## 0. 项目速记
### Q1：这个项目是做什么的？
这是一个基于可视化编排的 AI 应用低代码平台，主要支持 RAG 知识库、MCP 工具调用、复杂工作流编排和企业级权限管理。用户可以通过拖拽节点的方式，把用户输入、LLM、RAG 检索、条件分支、工具调用和输出节点串成一个完整 AI 应用。

### Q2：面试时怎么概括亮点？
1. 用 React Flow 做可视化工作流编辑器，支持节点拖拽、连线、条件分支、执行高亮和撤销重做。
2. 用 Zustand + Slice 模式管理节点、边、配置、运行态等复杂状态，通过细粒度订阅解决复杂画布的重复渲染问题。
3. 基于 MCP 思路设计统一工具注册与调用机制，让平台可以动态接入内置工具和业务方自定义工具。
4. 用 TypeScript + Zod + Prisma 做全链路类型安全，降低 AI 返回、第三方接口和前后端字段不一致带来的运行时风险。

### Q3：当前有哪些节点类型？
主要有 7 类：
- `start`：开始节点
- `userInput`：用户输入节点
- `llm`：大模型节点
- `rag`：RAG 检索节点
- `skill`：工具或技能节点
- `condition`：条件分支节点
- `output`：输出节点

## 1. 状态管理：Zustand
### Q1：为什么选择 Zustand，而不是 Redux？
这个项目的核心是可视化编辑器，需要管理节点数据、连接关系、选中状态、历史记录、执行状态等。如果用 Redux，Action、Reducer 和样板代码会比较多，开发成本偏高。

Zustand 更适合这个场景：
- API 更轻量，团队上手快。
- 支持 selector，组件可以只订阅自己关心的状态。
- TypeScript 体验比较好。
- 适合按 Slice 拆分复杂状态域。

在项目里，采用 Zustand + 中间件模式构建分层状态管理，并把状态拆成 User、App、Workflow、RAG、Skill 等 Slice，同时用持久化中间件同步部分状态到 localStorage，解决页面刷新后上下文丢失的问题。

### Q2：Zustand 和 React 渲染机制有什么关系？
React 判断组件是否需要更新，本质上依赖引用变化和 `Object.is` 比较。Zustand 在状态变化后会通知订阅者，React 再进入调度更新流程。

这里有几个关键点：
- Reconciliation：状态变化后，React 会比较新旧虚拟 DOM。
- Fiber：React 通过 Fiber 进行可中断、分优先级的调度。
- Bailout：如果状态引用没有变化，React 可能直接跳过渲染。

所以在 Zustand 中必须做不可变更新。如果直接改原对象，引用不变，订阅组件可能感知不到变化。

```tsx
// 错误：直接修改原对象，引用没有变化
state.nodes[0].data.label = 'new label'
set({ nodes: state.nodes })

// 正确：只替换变化节点的引用
set({
  nodes: state.nodes.map((node, index) =>
    index === 0
      ? { ...node, data: { ...node.data, label: 'new label' } }
      : node
  )
})
```

### Q3：如果两个不相关节点共享了同一个 store 字段，A 更新后导致 B 也重渲染，怎么避免？
核心是减少共享状态的订阅范围。会把状态拆细，不让组件订阅整个 store 或整个 `nodes` 数组，而是通过 selector 只订阅当前节点真正需要的数据。

比如节点组件只订阅：

- 当前节点的基础信息
- 当前节点的配置
- 当前节点的运行状态
- 当前节点关联的边数量或连接状态

同时把原本嵌套在 `nodes` 数组里的配置抽出来，维护成 `nodesConfigById`。这样更新某个节点配置时，只更新对应 `nodeId` 的配置对象，其他节点不会感知到这次变化。

## 2. React Flow 可视化编辑器
### Q1：React Flow 在项目里承担什么角色？
React Flow 主要负责图编辑器的基础能力，比如节点渲染、拖拽、连线、缩放、视口控制和节点位置管理。在它之上做了深度定制，包括：

- 自定义节点类型：LLM、RAG、工具、条件分支等。
- 自定义节点配置面板。
- 节点执行状态高亮。
- 条件分支连线和参数校验。
- 操作历史、撤销重做和画布保存。

需要强调的是，React Flow 只是画布层，真正的业务逻辑在我们自己的状态管理、编排校验和运行时调度里。

### Q2：React Flow 性能优化做了哪些？
一开始在节点数量变多时，拖拽和配置修改会出现卡顿，原因是更新单个节点时容易引起整个画布级联渲染。
主要做了这些优化：

- 状态拆分：节点基础信息、节点配置、运行状态分开存。
- 细粒度订阅：组件通过 Zustand selector 只订阅当前节点数据。
- 节点 memo：节点组件使用 `React.memo`，只在 ID、位置、连接关系、配置摘要变化时更新。
- 不可变更新：只替换变化节点的引用，避免整棵数据结构变化。
- 延迟计算：把节点内部不影响首屏交互的复杂计算放到 `requestIdleCallback` 或 Web Worker。
- 大画布优化：只对视口内和高频交互节点做重点渲染，减少无意义更新。

最终在 50+ 节点的复杂工作流下，拖拽、缩放和配置编辑都能保持比较流畅。

### Q3：你说解决了复杂场景下的重复渲染，具体怎么做？
这个问题的本质是 React Flow 的图状态和 Zustand 的全局状态叠加后，状态更新很容易扩散。比如只改一个节点配置，如果组件订阅的是整个 `nodes` 数组，就会导致整个画布更新。

主要从 3 层处理：

1. 状态模型重构：把节点基础信息、节点配置、运行态拆开，避免所有信息都塞进一个大数组。
2. 订阅粒度优化：节点组件通过 selector 按 `nodeId` 订阅自己的配置，而不是订阅全量节点列表。
3. 更新入口收敛：所有更新都通过统一 action，保证不可变更新和单向数据流，避免子组件直接改状态。

这样修改后，编辑某个节点配置只会影响当前节点和必要的连线状态，不会让无关节点跟着渲染。

### Q4：拖拽节点时偶尔出现位置跳动，怎么排查？
会从“复现、定位、修复、验证”四步做。

首先记录拖拽过程中的坐标，包括鼠标坐标、画布缩放比例、React Flow 内部 position、最终写入 store 的 position。很多跳动问题都和坐标系转换有关，比如页面坐标、画布坐标、缩放后的投影坐标混用了。

其次检查是否存在双数据源，比如 React Flow 内部维护一份节点位置，Zustand 又维护一份节点位置。如果拖拽过程中两边同时更新，就可能出现位置回写覆盖。

最后修复上通常会做两点：

- 拖拽过程中只让 React Flow 维护临时位置，拖拽结束时再统一写回 store。
- 位置更新做节流，避免高频 setState 导致状态顺序错乱。

验证时会重点看缩放、拖拽、自动布局、撤销重做、刷新回显这些场景。


## 3. 工作流运行时
### Q1：为什么要先讲 Runtime？
因为面试官可能会担心项目只是“用 React Flow 画了个流程图”。所以要主动说明：画布只是配置入口，真正的核心是运行时。是把画布配置转换成一份工作流 DSL。后端运行时会解析这份 DSL，构建依赖图，再按拓扑顺序执行节点。每个节点都有统一的输入、输出、状态和错误处理协议。

### Q2：整个工作流最终是怎么跑起来的？
流程大概是：
1. 前端画布生成节点和边的数据结构。
2. 保存时把它转换成工作流 DSL，包括节点类型、节点配置、输入输出映射和连线关系。
3. 后端读取 DSL，构建有向图。
4. 对图做合法性校验，比如是否有开始节点、是否有孤立节点、是否存在循环依赖。
5. 通过拓扑排序计算执行顺序。
6. 运行时按顺序执行节点，并把上游输出注入下游输入。
7. 执行状态通过接口或流式事件回传给前端，前端高亮当前节点并展示结果。

### Q3：编排节点之间的串联怎么同步到后端？
前端保存的不是 UI 截图，而是一份结构化 DSL。里面通常包括：

- `nodes`：节点 ID、节点类型、位置信息、配置参数。
- `edges`：起点、终点、条件分支、输入输出映射。
- `variables`：全局变量或上下文变量。
- `metadata`：版本号、创建人、更新时间等。

前端每次保存时会把这份 JSON 发给后端。后端不关心节点在画布上的展示样式，主要关心节点类型、配置和边关系。

### Q4：后端如何解析这个流程？
后端会把 DSL 解析成一张有向图。每个节点会被转换成一个可执行单元，比如 LLM Executor、RAG Executor、Tool Executor、Condition Executor。

解析过程主要做几件事：

- 校验节点类型是否合法。
- 校验每个节点配置是否符合 schema。
- 根据边构建邻接表和入度表。
- 检测循环依赖。
- 生成执行计划。

执行时，调度器只关心统一接口，比如 `execute(input, context)`，不同节点内部再实现自己的逻辑。

### Q5：拓扑排序、依赖分析和循环检测怎么做？
可以用 DFS 或 Kahn 算法。项目里会先根据边关系构建依赖图，然后做拓扑排序得到执行顺序。

如果在排序过程中发现某个节点又回到了访问中的状态，就说明存在环。比如 A 依赖 B，B 又依赖 A，这种流程不能执行，需要前端在保存或运行前提示用户。

依赖分析还可以做增量更新。比如只改了一条边，就只重新计算受影响节点的入度和下游路径，不必每次全量重建。

## 4. RAG 与上下文管理
### Q1：RAG 节点是怎么跑起来的？
RAG 节点本质上是一个检索增强节点。执行到 RAG 节点时，运行时会拿到上游输入，比如用户问题或某个中间变量，然后做这几步：

1. 对查询文本做预处理，比如去空格、补充上下文、提取关键词。
2. 调用 embedding 模型，把 query 转成向量。
3. 到向量库里做相似度检索，取 Top K 文档片段。
4. 对结果做重排和过滤，去掉低相关或重复内容。
5. 把最终片段拼成上下文，交给下游 LLM 节点使用。

### Q2：如何挑选 Top K？
Top K 要结合准确率、上下文长度和响应速度来平衡。
通常会先设一个默认值，比如 5 或 6。然后根据命中分数和阈值做动态裁剪：如果第 6 条以后分数明显下降，就不继续塞；如果前几条都很短且相关度高，可以适当多取一些。
最后还要考虑模型上下文窗口，不能为了多取文档导致 prompt 超长。

### Q3：上下文超长如何处理？
主要做 4 层控制：
- 检索层：限制 Top K 和单个 chunk 长度。
- 重排层：过滤低相关、重复、过旧的片段。
- 拼接层：按优先级拼上下文，重要内容靠前。
- 摘要层：对历史对话或长文档先做摘要，再放进 prompt。

如果是流式对话，还会把短期记忆和长期记忆分开：最近几轮对话直接保留，较早内容压缩成摘要，长期偏好或关键事实存到 Memory。

### Q4：如何精准获取之前上下文？
不能简单把所有历史都塞进 prompt，而是按任务相关性检索。
具体做法是：

1. 当前问题向量化。
2. 从历史消息、摘要和长期记忆中检索相关内容。
3. 结合时间、会话 ID、业务实体做过滤。
4. 用重排模型或规则重新排序。
5. 只把最相关的上下文注入当前 LLM 节点。

### Q6：复杂节点结构如何向量化？
复杂节点不能直接把整段 JSON 粗暴向量化。一般会先转成语义描述，比如节点名称、节点类型、参数含义、输入输出、业务说明，再向量化。

比如工具节点可以向量化成：写文件工具，用于把上游生成内容保存到指定路径，输入包括文件名、内容、编码方式，输出包括写入状态和文件地址。

这样向量检索时语义更清晰，也更容易匹配用户意图。


## 5. MCP 与工具调用
### Q1：MCP 是什么？为什么引入？
MCP 全称是 Model Context Protocol，可以理解成大模型调用外部工具的标准化协议。它通过 schema 描述工具的能力、输入参数和输出结构，让模型或平台可以用统一方式发现和调用工具。

引入 MCP 主要是为了解决扩展性和解耦问题。传统 Function Calling 往往和具体工具写死在代码里，新增工具需要改核心逻辑。MCP 把工具抽象成标准能力，平台只需要实现通用调用层，就可以动态接入工具。

### Q2：MCP 工具抽象机制做了什么？
把每个工具抽象成标准对象，主要包含：

- 元信息：名称、描述、能力标签、版本、权限范围。
- 输入结构：参数 schema、必填项、默认值、校验规则。
- 输出结构：返回字段、错误码、结果类型。
- 调用逻辑：同步或异步执行、超时、重试、错误处理。
- 扩展机制：支持内置工具注册，也支持外部工具按协议接入。

这样工具层从“每个工具各写各的”变成“统一注册、统一配置、统一调用、统一审计”。

### Q3：你们是怎么基于 MCP 实现动态工具调用的？
整体流程分 3 步：

1. 工具注册：MCP Server 暴露工具描述，包括名称、参数 schema、返回结构和权限要求。
2. 工具发现：平台拉取 schema，前端根据 schema 自动生成配置 UI，比如输入框、选择器、开关。
3. 工具调用：工作流执行到工具节点时，调度器根据工具名称和参数，通过 MCP Client 调用对应工具服务。

关键点是整个过程 schema 驱动，不写死具体工具逻辑。新增一个工具，只要注册到 Tool Registry，平台就能识别并使用。

### Q4：JSON 注册如何解析成工具？
JSON 注册文件会先经过 schema 校验，确认工具名、版本、参数、权限、输出结构都合法。校验通过后，系统会把 JSON 转成内部 ToolDefinition，并注册到 Tool Registry。

执行时，调度器不会直接依赖某个工具类，而是通过 `name + version` 从 Registry 查到工具定义，再根据参数 schema 校验入参，最后调用对应 handler 或远程 MCP Server。

### Q5：Tool 注册机制怎么说？
可以简单说两步：
1. 定义工具 schema 和 handler。
2. 通过统一接口注册到 Tool Registry。

Registry 内部维护一个 Map，比如 `name -> toolDefinition` 或 `name:version -> toolDefinition`。执行时调度器只通过工具名查找工具，不直接依赖具体实现，这样工具和工作流运行时是解耦的。

### Q6：新增一个写文件工具怎么实现？
会先定义工具 schema，比如：

- `fileName`：文件名
- `content`：写入内容
- `encoding`：编码方式
- `overwrite`：是否覆盖

然后实现 handler：校验路径是否合法，检查用户是否有写入权限，执行写文件操作，返回文件地址或写入结果。

最后把它注册到 Tool Registry，并在前端根据 schema 自动生成配置表单。用户把“写文件工具”节点拖到画布后，就可以把上游 LLM 输出映射到 `content` 参数。

### Q7：写文件节点如何接入链路？
它本质上是一个工具节点。前端配置时选择“写文件工具”，并配置参数映射，比如把 LLM 节点的输出绑定到 `content`。

运行时执行到该节点时，会从上下文里取上游输出，组装成工具入参，调用 Tool Executor。写入成功后，节点输出文件 URL 或写入状态，下游节点可以继续使用。

### Q8：自定义工具怎么保证安全性？
主要从 6 层控制：
- 注册时校验 schema 和元信息。
- 配置工具权限边界，比如只能访问指定资源。
- 执行时做身份鉴权和租户隔离。
- 设置超时、限流、熔断。
- 做调用日志和审计追踪。
- 对高风险工具增加人工审核或白名单机制。

### Q9：工具版本升级怎么处理？
在工具定义中加入版本字段，并在注册中心维护版本信息。

- 支持同名工具多版本共存。
- 调用时可以显式指定版本，也可以走默认稳定版本。
- 不兼容变更发新版本，而不是直接覆盖旧版本。
- 通过灰度切换观察稳定后，再下线旧版本。

这样可以降低工具升级对已有工作流的影响。

### Q10：如果某个工具执行很慢怎么办？
会从调度层和执行层处理。

调度层设置超时时间、重试策略、限流和熔断；执行层对耗时任务引入异步任务队列，先返回任务 ID，再通过轮询或事件通知拿结果。

同时要接入监控，记录工具耗时、失败率和超时率，方便定位是工具本身慢，还是网络、依赖服务或参数导致的问题。

### Q11：AI 编排平台里，工具调用是谁决定的？只是可视化编排吗？
不是单纯可视化编排。工具调用有两种模式：

- 显式编排：用户在画布里明确放了工具节点，运行时按流程执行。
- 智能决策：Agent 或 LLM 根据工具 schema、用户意图和上下文判断是否调用工具。

我们这个平台的重点是把两种方式结合起来。可视化工作流保证可控性和可解释性，LLM 决策能力提升灵活性。企业场景里通常更重视可控，所以关键链路会采用显式编排。


## 6. Skill 技能系统

### Q1：Skill 系统解决什么问题？
Skill 是可复用的 AI 能力模块，比如意图识别、实体提取、对话管理、信息抽取、文档总结等。不同业务场景可以组合不同 Skill，形成完整的 AI 应用流程。

### Q2：Skill 和 Tool 有什么区别？
Tool 更偏外部能力调用，比如查数据库、写文件、调用 API；Skill 更偏业务能力或 AI 能力封装，比如“提取简历信息”“总结会议纪要”“判断用户意图”。

简单说：

- Tool 解决“调用外部系统”的问题。
- Skill 解决“复用业务能力”的问题。

在工作流里，Skill 节点也可以调用 Tool，但它会封装更多业务逻辑。

## 7. 全链路类型安全
### Q1：全链路类型安全是怎么落地的？
从 3 层做：

1. 前端层：使用 TypeScript 做静态类型约束，保证开发阶段字段和组件入参正确。
2. 接口层：使用 Zod 对请求和响应做运行时校验，尤其防止 AI 返回、第三方接口返回不符合预期。
3. 数据层：使用 Prisma 定义数据库 schema，并生成服务端类型。

这三层结合后，可以形成从数据库到接口再到前端 UI 的类型闭环。

### Q2：TS + Zod + Prisma 如何协同？遇到过什么问题？
Prisma 是数据库模型的来源，负责生成服务端模型类型；API DTO 用 Zod 定义，既做运行时校验，也导出 TypeScript 类型；前后端通过共享包复用这些类型和 schema。

遇到过的问题是：后端模型加了字段，但前端没有同步更新，导致页面展示异常。后来我们做了 3 件事：

- 强制使用共享包，禁止前端手写后端类型。
- CI 检查类型兼容性，后端修改模型后自动构建共享类型。
- Zod 校验失败上报 Sentry，聚合异常日志。

这样可以更早发现前后端数据结构不一致的问题。


## 8. 稳定性与异常兜底
### Q1：你是怎么保证系统稳定性的？
A：会用“校验 + 容错 + 隔离”来概括。

- 校验：所有用户输入、模型返回、第三方接口结果都经过 Zod 或 schema 校验。
- 容错：前端渲染异常数据时有默认值、空态和错误提示，不让页面直接崩溃。
- 隔离：工作流节点之间用统一上下文传递数据，单个节点失败不会直接拖垮整个系统。
- 安全：通过 JWT 鉴权和路由守卫保证用户只能访问自己的资源。
- 监控：记录工具调用、接口错误、Zod 校验失败和工作流执行失败。

### Q2：异常兜底机制怎么设计？
分节点级、流程级和页面级。

节点级：每个节点执行失败后记录错误状态、错误原因和输入参数摘要，可以选择重试或走 fallback。

流程级：如果关键节点失败，整个流程终止；如果非关键节点失败，可以跳过或返回默认值。

页面级：前端展示错误节点、高亮失败路径，并提供查看日志、重新执行、复制错误信息等能力。

### Q3：如何区分网络错误和后端错误？
网络错误通常是请求没有拿到有效响应，比如超时、断网、DNS 或连接失败；后端错误是拿到了响应，但状态码是 4xx 或 5xx。

前端可以这样处理：

- 没有 response：提示网络异常或连接超时。
- 401 / 403：提示登录过期或无权限。
- 400 / 422：提示参数错误或配置错误。
- 500：提示服务异常，并记录 requestId 方便排查。

如果是工具调用，还要把错误归类成参数错误、权限错误、超时错误、依赖服务错误和未知错误。

## 9. NestJS 后端相关
### Q1：NestJS 如何做切面 AOP？
NestJS 里可以通过 Interceptor、Guard、Pipe、Filter 实现类似 AOP 的能力。

- Guard：做鉴权和权限判断。
- Pipe：做参数校验和转换。
- Interceptor：做日志、耗时统计、响应包装、缓存。
- Filter：统一异常捕获和错误响应。

比如工具调用日志就可以放在 Interceptor 里，记录请求参数摘要、执行耗时、调用结果和错误信息。

### Q2：NestJS 如何做 JWT 鉴权？
登录成功后后端签发 JWT，里面包含用户 ID、角色、租户等信息。前端后续请求在 Authorization Header 中携带 `Bearer token`。
NestJS 后端通过 Passport JWT Strategy 解析 token，并在 Guard 中校验 token 是否有效、用户是否存在、是否有权限访问当前资源。校验通过后，把用户信息挂到 request 上，业务接口就可以拿到当前用户上下文。


## 10. 竞品与自研决策
### Q1：和 Coze 这类平台的差异怎么说？
可以从定位上说，不要硬说功能全面超过。

Coze 更偏通用 AI Bot 和生态化工具，适合快速搭建标准化应用。我们项目更偏企业内部低代码编排，重点是私有化、权限治理、业务系统集成和可控执行链路。

差异可以总结为：

- 更轻量：不追求大而全，优先覆盖企业内部高频流程。
- 更可控：工作流显式编排，节点输入输出和执行路径可追踪。
- 更易集成：围绕企业已有系统做工具接入和权限适配。
- 更适合私有化：数据、知识库、工具权限都可以放在企业内部环境。

### Q2：为什么要自研，而不是直接用竞品？
主要是企业场景对数据安全、权限隔离、私有化部署和业务系统集成要求比较高。如果直接用通用平台，很多内部系统、审批流程、知识库权限和审计要求很难完全适配。

自研的价值不是重复造一个 Coze，而是做一个更贴合内部业务的轻量编排平台。核心收益是可控、可扩展、可私有化，并且可以逐步沉淀企业自己的工具和 Skill 资产。

### Q3：这个项目未来前景怎么说？
未来可以往 3 个方向扩展：

1. 更强的 Agent 能力：从固定流程编排，逐步支持模型自主规划。
2. 更完善的工具生态：沉淀内部工具市场，让业务方低成本接入工具。
3. 更强的治理能力：包括权限、审计、版本、灰度、成本统计和效果评估。

## 11. 面试高频追问清单
### Q1：一句话讲清楚你的技术难点？
最大的难点不是把节点画出来，而是让复杂工作流在可视化编辑、运行时执行、工具扩展和状态同步之间保持一致，并且在节点变多时仍然不卡、不乱、不难维护。

### Q2：如果面试官问“你主要负责哪块”，怎么答？
我主要负责前端可视化编排相关工作，包括 React Flow 画布定制、节点配置面板、Zustand 状态管理、执行状态展示，以及工具 schema 驱动的配置 UI。同时也参与了工作流 DSL、MCP 工具注册、类型安全和异常兜底方案的设计。

### Q3：如果面试官追问“你做得最有技术含量的一点是什么”？
可以讲重复渲染优化。因为它既涉及 React 渲染机制，又涉及 Zustand 状态设计，还和 React Flow 的节点数据结构有关。重点说清楚“从大对象订阅改成按节点 ID 订阅”“配置从 nodes 数组拆到 map 结构”“只更新变化节点引用”这几件事。

### Q4：如果面试官问“怎么证明优化有效”？
可以说通过 React DevTools Profiler 和浏览器 Performance 面板对比优化前后。优化前修改一个节点配置会触发多个无关节点渲染，优化后只有当前节点和必要父组件更新。拖拽时也观察 FPS、commit 次数和长任务数量。

## 12. Redis 在 FlowAI Studio 中的核心应用场景
1. AI工作流任务缓存与状态加速
FlowAI Studio的核心业务是用户自定义AI工作流，例如文本转视频、多模型串联推理、智能图文生成、批量AI处理等。单条工作流包含多个节点（模型调用、参数配置、条件分支、结果输出），完整执行链路耗时从数百毫秒到数分钟不等。
若每次刷新页面、重试任务、查看进度都从数据库查询任务数据，高频查询会导致数据库压力激增，同时响应延迟过高，严重影响用户体验。

通过Redis Hash结构存储工作流核心数据，包含任务ID、执行状态、进度百分比、当前运行节点、参数配置、临时输出结果等。任务执行过程中，实时更新Redis缓存数据，用户前端查询进度、刷新任务状态直接读取Redis内存数据，响应耗时压缩至10ms以内。
同时设置缓存过期时间，已完成、已失败的任务自动过期释放内存，避免资源占用，完美适配AI工作流实时进度查询、高频状态访问的场景。

2. AI任务队列与优先级调度
FlowAI Studio支持多用户同时提交AI生成任务，高峰期会出现大量并发任务（视频渲染、批量推理、高清生成）。若任务无序执行，会出现资源抢占、低优先级任务阻塞核心任务、系统过载崩溃等问题。
Redis落地方案：利用Redis List结构实现基础任务队列，接收用户提交的所有AI工作流任务，实现任务有序排队；针对会员、紧急任务、批量任务的差异化需求，采用ZSet有序集合，通过分值设置任务优先级。
例如：付费会员任务分值更高，优先调度执行；普通用户低优先级任务后置；批量后台任务低分值兜底执行。同时依托Redis原子操作，避免任务重复执行、漏执行，保障AI工作流调度的稳定性，解决高并发任务拥堵问题。

3. 用户会话与权限临时存储
FlowAI Studio支持用户在线编辑工作流、保存草稿、多端登录、临时权限配置（团队协作、工作流共享）。用户的登录会话、临时编辑状态、共享权限等数据读写频繁、生命周期灵活，无需持久化存储到数据库。
Redis落地方案：通过Redis String结构存储用户登录Token、会话信息，设置过期时间实现自动登出；通过Hash结构存储用户临时编辑的工作流草稿、未保存的节点配置，用户实时编辑、暂停后再次进入可快速恢复状态。
同时利用Set结构存储用户临时权限列表，快速校验用户是否拥有某条工作流的编辑、查看、执行权限，相比数据库查询，权限校验效率提升数十倍，保障平台协作流畅度。

4. 接口限流与平台防护
FlowAI Studio对外开放AI工作流API接口，支持开发者对接自有业务，同时存在大量用户高频调用模型生成、视频渲染接口。恶意刷接口、高频重复调用会导致AI算力资源耗尽，造成平台服务卡顿、宕机。
Redis落地方案：基于Redis String的自增命令（INCR）实现分布式限流，针对单用户、单IP、单API接口设置单位时间最大调用次数。例如限制单用户每分钟最多提交10次AI生成任务，超过阈值直接拦截请求，返回限流提示。
同时结合Redis过期特性，自动重置限流计数，无需手动清理数据，低成本实现平台接口防护，保障AI算力资源合理分配，避免恶意请求冲击系统。

5. 热点AI模板与资源缓存
FlowAI Studio内置大量通用AI工作流模板（短视频生成、海报制作、文本推理、智能剪辑等），大部分用户会直接使用热门模板快速创建任务，这类热点资源访问频率极高。
Redis落地方案：将热门工作流模板配置、模型参数、默认节点规则等静态高频数据缓存至Redis，用户加载模板、新建工作流时直接读取缓存数据，无需重复查询数据库、解析配置文件。
通过缓存预热机制，平台启动后自动加载TOP50热点模板，进一步提升首屏加载速度，大幅降低数据库查询压力，提升平台整体吞吐量。

6. Redis落地核心注意事项
1. 合理设置缓存过期时间：AI任务状态、草稿数据、限流计数必须配置过期策略，避免大量临时数据常驻内存，导致Redis内存溢出；核心工作流配置数据可设置永不过期，保障稳定性。
2. 做好缓存更新与淘汰：工作流模板、权限配置更新后，及时更新或清空对应缓存，避免出现缓存与数据库数据不一致，导致用户加载旧配置、权限失效等问题。
3. 规避缓存穿透与击穿：针对不存在的AI任务ID、无效接口请求，设置空值缓存；热点模板资源采用永不过期策略，搭配集群部署避免缓存击穿。
4. 保障高可用：AI平台任务不允许大面积中断，生产环境必须采用哨兵或集群模式，避免单机Redis故障导致任务调度、状态查询全部失效。
