# 项目架构与职责

## 1. 为什么选择 VS Code Extension + Webview 的架构？
VS Code Extension Host 具备文件系统、编辑器、终端、Git 和命令注册等能力，适合承载 AI 工具执行以及本地资源访问；Webview 更适合实现聊天、多标签、Diff 列表和 Skill 市场等复杂交互界面。

两端通过消息协议通信。Webview 只负责展示和用户交互，涉及文件、命令、凭证和权限的操作放在 Extension Host 中处理，避免前端页面直接获得过高的本地权限。

## 2. Webview 和 Extension Host 如何通信？
Webview 通过 `postMessage` 发送带有 `type`、`requestId` 和 `payload` 的消息，Extension Host 根据消息类型分发到对应处理器，完成后再用相同的 `requestId` 返回结果。

对于模型流式输出或长时间工具调用，还需要定义增量事件、完成事件和错误事件。调用结束后清理监听器和未完成请求，避免多标签场景出现串消息或内存泄漏。

## 3. 多标签会话如何避免状态互相污染？
每个标签都要有稳定的会话 ID，消息记录、模型请求、工具调用、取消控制器和文件变更都归属到对应会话。Extension Host 返回事件时携带会话 ID，Webview 只更新目标标签的状态。

切换标签不等于中止原任务。后台标签可以继续执行，但它产生的流式消息和工具结果不能写入当前标签；关闭标签时则需要根据产品规则取消任务或转为后台任务。

## 4. 你个人负责到什么程度？
我重点负责文件变更追踪、Skill 市场与安装、安全扫描和 UI 自动化测试 Skill，对这些模块参与了需求分析、方案设计、开发联调和问题修复。底层模型能力、整体产品架构以及其他模块是团队协作完成的。

回答这类问题时，我会明确哪些是独立实现、哪些是参与设计、哪些是与同事联调，不把整个 AI 助手都描述成个人完成。

# 文件变更追踪与 Diff

## 1. 为什么 AI 编程助手必须做文件变更追踪？
普通聊天只产生文本，但 AI 编程助手会真正修改用户工作区。如果用户不知道改了哪些文件、改动来自哪个工具，也不能审核或回滚，就很难信任自动执行能力。

所以变更追踪的目标不是单纯展示 `git diff`，而是把一次会话中的工具调用、实际落盘文件、Diff 内容和审核结果关联起来，让变更可追踪、可解释、可确认、可恢复。

## 2. Edit、Write 和 Bash 的变更来源有什么区别？
`Edit` 是局部替换，工具本身知道目标文件和修改片段；`Write` 是整文件写入，也能在执行前后记录文件内容；`Bash` 的影响最难确定，因为格式化、代码生成和脚本可能间接修改多个文件，命令文本并不能完整代表最终结果。

因此 Edit 和 Write 可以在工具链内部直接记录，Bash 除了执行前的命令分析，还需要在执行后结合 Git 工作区状态扫描实际变化，最后统一转换成相同的文件变更结构。

## 3. 整个变更追踪流程是怎样的？
可以概括为五步：

1. 工具执行前记录会话、工具类型、目标路径和必要的旧内容。
2. 执行 Edit、Write 或 Bash，并记录执行结果。
3. 对明确的目标文件读取新内容；对 Bash 再通过 Git Status 扫描实际变更。
4. 合并、去重并过滤无关文件，对文本文件计算行级 Diff。
5. 将变更结果回传 Webview，展示文件列表、Diff 和审核回滚入口。

这样工具链内的精确记录是主路径，Git 状态扫描负责补齐工具无法直接感知的间接变更。

## 4. 为什么不能直接展示 `git diff`？
`git diff` 反映的是工作区相对 Git 基线的最终差异，但无法说明某个改动由哪次 AI 工具调用产生，也可能把用户在会话前已经存在的修改一起算进去。另外，未跟踪文件、二进制文件和非 Git 工作区都需要单独处理。

因此需要把工具执行前后的上下文作为主记录，再用 Git Status 或 Git Diff 做实际落盘校验和 Bash 场景兜底，而不是把 Git 输出直接等同于本次 AI 改动。

## 5. 如何避免把用户原有修改误算成 AI 的修改？
在 AI 执行前先记录工作区基线，包括已有的变更文件集合和必要的内容摘要；执行后再次扫描工作区，比较前后状态，只把本次新增或发生二次变化的部分关联到当前工具调用。

对 Edit 和 Write，可以直接使用执行前后的文件内容计算本次差异。对 Bash 这种影响范围不确定的操作，则用“执行前基线 + 执行后 Git 状态 + 命令影响范围”共同判断，降低全局快照产生的无关文件误报。

## 6. Git Status 白名单过滤具体过滤什么？
白名单不是简单按文件名写死，而是限定允许纳入追踪的状态和路径范围。首先解析 Git Status 的状态码，识别新增、修改、删除、重命名和未跟踪文件；然后排除构建缓存、依赖目录、日志等明确无关的文件；最后校验路径必须位于当前工作区内。

白名单只能降低噪声，不能代替工具级记录。过滤规则过宽会产生误报，过严会漏掉真实修改，因此还要保留异常提示和可观测日志。

## 7. LCS 行级 Diff 的原理是什么？
先把旧文件和新文件按行切分，利用最长公共子序列找出两份文本中顺序保持不变的行。公共子序列之外的旧行视为删除，新行视为新增，再把连续变化组织成 Diff hunk。

相比按相同行号直接比较，LCS 能正确处理在文件中间插入或删除内容导致的整体行号偏移。它适合生成行级 Diff，但时间和空间复杂度需要关注，不能不加限制地处理超大文件。

## 8. LCS 的复杂度是多少？大文件怎么处理？
经典动态规划实现的时间和空间复杂度都是 `O(n * m)`，当新旧文件行数很大时成本会明显上升。实际工程中可以使用空间压缩、Myers Diff 等更适合文本差异的算法，也可以限制单文件大小和最大行数。

对于超大文件，优先展示文件级变更摘要，按需计算具体 hunk；对于压缩文件、图片等二进制内容不做文本 Diff，只展示新增、删除或修改状态。

## 9. 文件重命名、删除和未跟踪文件怎么处理？
删除文件需要保留执行前内容，并标记为 `delete`；未跟踪文件标记为 `create`，旧内容为空；重命名优先使用 Git 提供的 rename 信息，记录旧路径和新路径。如果无法可靠判断是重命名，则按删除加新增展示，避免错误合并。

所有路径都要先标准化并校验工作区边界，不能直接信任模型或命令返回的相对路径。

## 10. 回滚是怎么做的？
回滚需要依赖执行前保存的内容或可逆补丁。对于修改和删除，可以用旧内容恢复；对于新增文件，可以在用户确认后删除；如果文件在 AI 修改后又被用户手动改过，不能直接覆盖，应先检测当前内容是否仍与记录的 AI 修改结果一致。

发生冲突时应停止自动回滚并提示用户查看 Diff，避免为了恢复 AI 改动而覆盖用户后续工作。Git 可以作为辅助，但不能默认用全局 reset，因为它可能影响不属于本次 AI 操作的修改。

## 11. 多个工具连续修改同一个文件，Diff 怎么归属？
每次工具调用都记录独立的 `before` 和 `after`，用于查看单步变化；会话层再把同一文件的多次修改按时间聚合，展示从会话初始状态到当前状态的最终 Diff。

这样既能回答“最终改了什么”，也能追踪“哪一步引入了这行代码”。回滚时要明确是回滚单次操作还是整个会话，二者不能混用。

## 12. 变更追踪中最容易出现什么竞态问题？
典型问题是两个工具并发修改同一文件，后执行的工具可能基于旧内容覆盖先执行结果；另一个问题是扫描 Git 状态时，用户或格式化程序仍在写文件，导致拿到中间状态。

可以按工作区和文件建立写入队列，对同一文件串行执行；每次写入前校验版本、内容哈希或修改时间；状态扫描则在工具完成后触发，并对仍在变化的文件做短暂收敛和再次确认。

# Skill 市场与内置安装

## 1. Skill 在这个项目里是什么？
Skill 是可安装、可复用的 AI 能力包，可以包含说明、提示词、工具配置、脚本和资源，用来把某类任务沉淀成标准工作流。Skill 市场负责发现、展示、安装和管理这些能力，内置 Skill 则用于给特定场景提供开箱即用的默认能力。

## 2. Skill 市场包含哪些核心模块？
主要包括技能列表和详情展示、搜索与排序、安装卸载、版本和状态管理、第三方扩展接入、内置 Skill 自动安装，以及安装和使用过程中的埋点统计。

Extension Host 负责下载、校验、解压和写入本地目录，Webview 负责展示状态和触发操作，两端通过统一的 Skill 元数据结构同步结果。

## 3. 一个 Skill 的安装流程是什么？
先获取 Skill 元数据和安装包，下载到临时目录；随后校验包结构、manifest、版本、完整性和安全扫描结果；校验通过后再写入正式 Skill 目录并注册到能力列表；任一步失败都清理临时文件并返回明确错误。

正式安装最好采用临时目录加原子替换，避免下载或解压中断后留下“看似已安装但内容不完整”的半成品。

## 4. 内置 Skill 自动安装如何避免每次启动都重复执行？
启动时比较配置中的 Skill ID、版本和本地安装记录。版本一致且完整性校验通过时直接复用；缺失或版本落后时才进入下载和安装流程。

还需要处理并发启动和多个窗口同时安装的问题，可以通过安装锁或单例任务合并请求，避免同时写入同一目录。

## 5. 第三方 Skill 和内置 Skill 有什么区别？
内置 Skill 的来源和版本由平台控制，可以随产品预置或升级；第三方 Skill 的来源更复杂，不能默认信任，需要更严格的结构校验、安全扫描、权限声明和用户确认。

运行时也应根据来源设置不同权限，而不是只要安装成功就获得和内置 Skill 相同的文件或命令能力。

## 6. Skill 埋点应该记录哪些事件？
围绕完整漏斗记录曝光、详情查看、安装开始、安装成功或失败、启用、调用、调用成功或失败、卸载等事件。公共字段包括 Skill ID、版本、入口位置、会话场景、耗时和失败原因，敏感代码和用户文件内容不能上报。

有了这条链路，才能区分“没有被看见”“有人看但不安装”“安装后不会用”和“调用失败”等不同问题。

## 7. 如何用埋点优化 Skill 排序？
不能只按调用次数排序，否则老 Skill 和曝光量大的 Skill 会天然占优。更合理的是结合曝光点击率、安装转化率、安装后的实际调用率、成功率、近期活跃度和用户反馈，并对新 Skill 保留一定探索流量。

具体权重应通过实际数据和实验调整，面试时如果没有参与排序算法，不应声称实现了复杂推荐系统，可以重点讲指标设计和为什么不能只看绝对次数。

## 8. Skill 安装失败怎么保证可恢复？
安装过程要有明确状态，例如 downloading、validating、installing、installed 和 failed。所有写入先发生在独立临时目录，只有完整流程成功才替换正式版本；失败时清理临时内容并保留旧版本。

错误信息需要区分网络失败、结构不合法、安全扫描未通过、版本冲突和磁盘写入失败，便于用户重试和开发定位。

# 静态安全扫描与路径沙箱

## 1. 为什么采用“正则粗筛 + Babel AST 深度扫描”？
正则扫描速度快，适合先从大量文件中识别 `eval`、`child_process`、文件系统和网络请求等可疑关键词，快速缩小深度分析范围；但正则不了解语法结构，容易被注释、字符串或别名干扰。

Babel AST 能判断调用表达式、导入来源和参数结构，准确度更高，但解析成本也更大。两阶段方案用正则保证覆盖和效率，再用 AST 降低误报并提取更完整的风险上下文。

## 2. AST 扫描的基本流程是什么？
先根据文件类型解析 JavaScript 或 TypeScript 代码生成 AST，再遍历 `ImportDeclaration`、`CallExpression`、`MemberExpression`、`NewExpression` 等关键节点，识别高风险模块的导入和调用。

命中规则后记录风险类型、文件、代码位置、调用方式和风险级别，最后聚合成 Skill 级扫描结果。对于 Vue 单文件组件，需要先提取 `script` 和 `script setup` 部分，再交给对应解析器处理。

## 3. 主要扫描哪些高风险行为？
重点包括动态执行代码，如 `eval`、`Function` 和 `vm`；进程与命令执行，如 `child_process.exec`、`spawn`；敏感文件读写和工作区外路径访问；未声明的网络请求；环境变量和凭证读取；以及安装阶段自动执行的脚本。

风险命中不一定直接等于恶意行为，应结合 Skill 声明的能力、参数是否可控和实际调用上下文分级处理。

## 4. 如何识别重命名导入或别名调用？
不能只匹配函数名。例如 `import { exec as run } from 'child_process'`，后续调用的是 `run()`。AST 扫描需要建立导入源与本地标识符的映射，再在调用节点中解析该标识符真正对应的 API。

对于 `const cp = require('child_process')`、解构赋值和简单变量传递，也可以通过作用域绑定继续追踪。涉及复杂动态赋值时，纯静态分析存在边界，需要转为高风险提示或交给运行时权限控制。

## 5. AST 扫描能完全解决混淆和动态调用吗？
不能。计算属性、字符串拼接、运行时下载代码、深度混淆和间接函数传递都可能绕过静态规则。AST 比正则更准确，但仍然只是静态风险发现，不是完整安全边界。

因此还需要包来源校验、权限声明、路径沙箱、命令审批和运行时隔离。面试时要明确扫描能力的边界，不能说“用了 AST 就绝对安全”。

## 6. 如何控制误报和漏报？
规则需要包含风险级别和上下文。例如仅导入 `fs` 可以记为低风险，读取工作区内普通文件和读取 SSH Key 的风险不能相同；出现在注释或测试夹具中的关键词也不应直接阻断安装。

通过人工复核样本、已知恶意样本和正常 Skill 回归集评估准确性。误报较多的规则增加 AST 上下文约束，漏报则补充别名、调用链和新的高风险 API 规则。

## 7. 路径安全沙箱是怎么做的？
先确定 Skill 允许访问的根目录，对输入路径进行标准化和绝对路径解析，再检查最终路径是否仍位于允许根目录内，拦截 `../`、绝对路径和编码绕过。仅做字符串前缀判断不可靠，例如 `/work/a` 和 `/work/abc` 就可能被误判。

还要考虑符号链接。访问前应解析真实路径并再次校验边界；创建新文件时则需要校验最近存在的父目录，避免通过软链接跳出沙箱。

## 8. 为什么静态扫描之后还需要运行时权限控制？
静态扫描判断的是代码可能做什么，运行时权限控制决定它此刻能不能做。即使扫描没有发现问题，Skill 在运行时获得动态参数后仍可能访问敏感路径或执行危险命令。

所以文件、命令、网络和 MCP 工具调用都应经过统一权限层，根据风险自动允许、要求用户确认或直接拒绝，并记录审计日志。

# UI 自动化测试 Skill

## 1. 这个 Skill 解决什么问题？
AI 修改前端代码后，开发者通常还要手动判断影响页面、编写测试步骤、打开浏览器操作并核对结果。这个 Skill 希望把这些环节串起来：分析 Git Diff，生成与变更相关的测试用例，通过 Chrome DevTools MCP 操作真实页面，校验结果，再把测试结论回写到当前任务。

它的价值不是替代全部测试，而是缩短“代码修改完成到获得页面反馈”的路径，尤其适合表单、列表、弹窗和路由跳转等可观察的 UI 行为。

## 2. 完整执行链路是什么？
首先读取 Git Diff，提取变化文件、组件、路由和关键交互；然后结合项目上下文生成前置条件、操作步骤和预期结果；确认开发服务可访问后，通过 Chrome DevTools MCP 打开目标页面、定位元素并执行点击、输入和跳转；最后读取 DOM、控制台、网络请求或截图进行校验，并把通过、失败和证据回写到会话。

每一步都保留结构化状态，失败时能区分是用例生成错误、环境不可用、元素定位失败、操作超时还是断言失败。

## 3. 为什么从 Git Diff 生成测试，而不是扫描整个项目？
全项目扫描范围大、成本高，也容易生成与本次修改无关的用例。Git Diff 能提供本次变化的文件、函数和代码片段，把分析范围收敛到最可能受影响的功能。

但 Diff 只能说明改了哪里，不能完整说明影响面，所以还要结合 import 关系、路由配置、组件调用方和已有测试补充上下文。

## 4. 如何从代码文件映射到需要测试的页面？
优先从路由配置查找直接关联页面；如果修改的是子组件，则沿 import 或引用关系向上查找使用它的页面；如果修改的是公共组件或工具函数，则可能对应多个页面，需要按风险和使用频率选择代表性场景。

无法可靠映射时，不应该让模型猜一个 URL 直接执行，而是列出候选页面或要求补充运行入口。

## 5. 测试用例的数据结构怎么设计？
可以包含用例 ID、来源变更、目标页面、前置条件、操作步骤、预期结果、风险等级和执行结果。每个步骤再记录动作类型、元素定位信息、输入值、等待条件和断言。

结构化用例比纯自然语言更容易稳定执行，也方便把失败定位到具体步骤并重新运行。

## 6. 页面元素如何定位才更稳定？
优先使用可访问角色、可见名称、稳定的 `data-testid` 或业务语义属性，尽量避免依赖易变化的层级 CSS 选择器。定位结果不唯一时要继续缩小范围，不能默认点击第一个匹配元素。

如果项目缺少稳定标识，可以在测试结果中提出补充可测试性属性，而不是用坐标点击掩盖问题。

## 7. 如何判断测试通过？
预期结果要转换成可验证信号，例如目标元素出现或消失、文本和状态变化、URL 跳转、请求成功、控制台无新增错误等。必要时保留截图作为辅助证据。

截图相似只能说明视觉接近，不能替代业务断言；同样，请求返回 200 也不代表页面状态正确，需要根据用例选择合适的验证组合。

## 8. 如何降低自动化测试的不稳定性？
不用固定 `sleep` 猜页面何时完成，而是等待明确条件，例如元素可见、网络空闲、加载状态结束或特定响应返回。元素操作前检查是否存在、可见和可交互，失败时保留当前页面、控制台和网络信息。

对确定属于环境波动的失败可以有限重试，但业务断言失败不能靠反复重试变成通过，否则会掩盖真实问题。

## 9. 登录态、测试数据和环境差异怎么处理？
测试开始前明确环境、账号权限和数据前置条件。登录态可以复用受控浏览器会话或通过测试账号建立，但不能把凭证写进生成的用例和日志。

用例尽量使用可重复的数据，并在结束后清理副作用。若环境或数据条件不满足，应返回“阻塞”而不是误判为产品功能失败。

## 10. 测试结果如何回写？
回写内容包括关联变更、执行环境、用例步骤、通过或失败状态、失败位置以及必要的控制台、网络和截图证据。摘要用于快速判断，详细证据用于复现。

回写不能只给一句“测试失败”，否则开发者还需要重新执行整条链路才能定位问题。

# 综合与压力追问

## 1. 这段实习最难的地方是什么？
我认为最难的是在 AI 自动执行效率和本地开发安全之间取得平衡。AI 需要访问文件、执行命令和安装 Skill 才能真正完成任务，但权限越大，误修改、路径越权和危险命令的风险也越高。

我的处理思路是分层控制：执行前通过命令规则、权限声明和静态扫描识别风险；执行中通过路径沙箱和权限确认限制能力；执行后通过文件变更追踪、Git 状态和 Diff 审核确认实际影响。这样不是依赖某一个规则保证安全，而是形成执行前、执行中、执行后的完整链路。

## 2. 为什么不用全局文件快照来追踪变化？
全局快照实现直接，但大型仓库扫描成本高，而且会把用户操作、构建产物和其他进程造成的变化混入本次 AI 任务，产生大量误报。

更合适的是以工具调用记录为主，Edit 和 Write 精确追踪目标文件，Bash 再通过命令分析和 Git 状态补偿未知影响范围，只对候选文件读取内容和计算 Diff。

## 3. 如何证明这些工作产生了价值？
变更追踪可以看误报率、漏报反馈、Diff 打开率、审核或回滚使用率以及处理耗时；Skill 市场可以看曝光到安装、安装到调用、调用成功率和留存；安全扫描可以看不同规则的命中、误报和拦截结果；自动化测试可以看用例生成成功率、执行成功率、平均耗时以及发现问题的数量。

如果项目中没有完整量化某项指标，我会说明当时采用的验证方法和观察结果，不把主观感受包装成精确收益。

## 4. 如果安全扫描误报，阻止了正常 Skill 安装怎么办？
先按风险等级区分处理：明确危险行为直接阻断，中风险行为要求用户确认并展示命中位置，低风险行为只告警。然后通过规则 ID 和扫描上下文定位误报原因，补充作用域、参数来源或调用链判断，并用正常样本和风险样本回归。

不能为了降低误报简单关闭规则，因为这会把问题从可用性转成安全漏洞。

## 5. 如果 Bash 执行后 Git Status 没有变化，能说明命令安全吗？
不能。命令可能修改 Git 忽略文件、工作区外文件、系统配置，或者只进行了网络和进程操作。Git Status 只能帮助确认仓库内的版本状态，不是 Bash 安全判断工具。

因此执行前仍要解析命令并做权限判断，执行范围还要受工作目录、路径和命令白名单限制，Git 状态只是执行后的文件变更证据之一。

## 6. 你会如何测试变更追踪模块？
单元测试覆盖 LCS Diff、状态码解析、路径过滤、重命名、二进制和超大文件；集成测试分别执行 Edit、Write、创建、删除和 Bash 间接修改，验证实际工作区与变更记录一致；竞态测试覆盖同一文件连续修改、用户中途修改和工具异常退出。

回滚测试尤其要验证不会覆盖 AI 操作之后的用户新修改，这是比“能恢复旧文件”更重要的正确性边界。

## 7. 如果重新做一次，你会改进什么？
变更追踪方面，我会进一步统一所有工具的事务和事件模型，完善大文件增量 Diff 与冲突回滚；Skill 平台方面，会强化版本签名、安装原子性和权限声明；安全方面，会把静态扫描结果与运行时权限策略联动；自动化测试方面，会增加项目级页面映射、稳定定位规则和失败证据收集。

同时会更早设计可观测指标，因为只有持续记录耗时、失败原因、误报和转化漏斗，后续优化才有可靠依据。

# 面试前必须核实

- Git Status 白名单的真实过滤维度和具体规则。
- LCS 是否为自研实现，还是基于现有库二次封装。
- 回滚保存的是完整旧文件、逆向补丁，还是依赖 Git。
- Skill 包的真实格式、manifest 字段、安装目录和升级策略。
- Babel AST 实际覆盖的语法、危险 API 和 Vue/TypeScript 文件处理方式。
- 路径沙箱是否处理了软链接、编码和大小写差异。
- Chrome DevTools MCP 实际使用了哪些操作和校验能力。
- 四个模块各自能公开的真实数据指标、线上问题和个人贡献边界。
