# BioNote AI
## 项目总述
### 1. 这个项目介绍一下，有哪些核心亮点，负责哪些内容？
这个项目是一个面向生物信息科研团队的协同文档与智能助手平台。在项目里主要负责前后端开发和 AI 链路设计，覆盖了实时协同编辑、流式问答、长上下文记忆管理、RAG 检索增强问答，以及文档内 AI 辅助创作的任务编排。

## 简历串讲
### A. 实时协同编辑：Yjs + WebSocket
> 在协同编辑上，基于 Yjs + WebSocket 搭建了 CRDT 协同架构，
> 把文档操作建模成增量 update，同步到各客户端，实现了多人实时编辑、冲突自动合并；
> 同时结合 Awareness 机制实现了在线状态和光标同步，也实现了快照持久化和版本管理。

#### 0. TipTap 编辑器是什么？
Tiptap 是一个富文本编辑器，和 Yjs 有官方适配的插件，能直接把编辑器的操作映射成 Yjs 的共享状态修改，不用自己写复杂的转换逻辑。

#### 1. yjs 是什么，为什么要使用 yjs？
Yjs 是一个基于 CRDT 的实时协同编辑框架，它已经把文档状态同步、冲突合并、离线编辑、增量更新、最终一致性这些问题封装好了，所以不用从零实现冲突解决算法，而是把更多精力放在编辑器接入、权限控制、快照持久化等问题上。

#### 2. 实现“多人同时编辑”的流程。
1. 每个客户端打开文档后，会初始化一个本地的 Yjs 文档实例，把编辑器 Tiptap 绑定这个实例上；然后从数据库拉取文档最新快照；再建立协同连接，根据版本号从服务端拉取最近的 yjs 增量更新日志，把这些更新应用到本地 yjs 文档实例；

2. 用户本地编辑时，编辑器操作会转成对 Yjs 共享状态的修改，Yjs 生成增量更新；

3. 客户端通过 WebSocket 把 update 发给服务端；服务端广播给同一文档房间里的其他客户端；其他客户端收到更新后，合并到自己的本地文档状态中。

4. 因为 Yjs 基于 CRDT，所以即使 update 乱序到达，或者用户离线后重新上线，或者多人同时修改，最终所有客户端都会收敛到同一个状态。

#### 2.1 首次进入文档时，怎么保证所有人看到的是同一个版本？
由后端查询数据库，提供文档的最新快照内容作为基准版本。
客户端进入房间后，先加载这个快照，再建立协同连接，根据版本号从服务端拉取最近的 yjs 增量更新日志，把这些更新应用到本地 yjs 文档实例。这样可以保证新加入的用户不会拿到过时状态。

#### 2.2 文档持久化怎么做？
服务端按照定时保存或事件触发的方式（比如每10分钟、或者操作了50次），将最新全文持久化回数据库里中。
历史版本使用版本表保存快照，方便用户回滚。

#### 3. 为什么用 WebSocket，而不是 HTTP 轮询或者 SSE？ 
因为协同编辑需要高频、双向、低延迟通信。
HTTP 轮询实时性差，开销也大；
SSE 虽然适合服务端单向推送，但它本质是单向的，客户端还要单独发消息。
WebSocket 建连后是全双工长连接，既适合传文档增量更新，也适合传在线状态、光标、心跳这些实时协作消息。

#### 3.1 WebSocket 如何实现
WebSocket 通过在 HTTP 握手后升级为 TCP 长连接协议 `Connection: Upgrade` `101 Switching Protocols`，在同一个连接上允许客户端和服务器独立、同时发送数据，从而实现真正的全双工通信。

#### 4. WebSocket 里传的是什么内容？
- 二进制内容：这是最核心的内容，主要是 Yjs 的 update，也就是文档的增量变更。
- JSON 文本内容：主要是控制消息和协作状态消息，比如首次同步、重连同步、awareness 在线状态、光标位置、心跳和错误提示；

#### 4.1 Yjs update 的格式是什么？传输的是什么内容？
它会包含文档变更所需的内部结构信息，比如 客户端 ID、操作依赖关系、时间戳、增量内容等，最终通过二进制编码在客户端和服务端之间传输，通常就是 `Uint8Array`，编码过程本身就会压缩数据体积，所以比 JSON 更省带宽。

Yjs 的二进制编码还有校验机制，服务端收到消息后会先验证格式，若解析错误会丢弃该消息，客户端重连时会重新同步完整状态；否则，解码后再应用到本地。

##### 4.2 为什么不用每次都存全量内容？
因为协同编辑是高频场景，如果每次用户敲一个字都把整个文档全量写回数据库，存储和网络成本都会很高，还会影响实时性。 

而 Yjs 的增量操作数据量小，服务端可以定时或按事件触发全量保存，从而减少存储和传输成本，还能通过增量日志保证离线重连时的状态合并，最终一致性也由 CRDT 算法保障。

#### 4.3 在高并发场景下，Websocket 广播会不会产生延迟或丢包，如何处理？
依赖 WebSocket 底层的 TCP 可靠传输来尽量减少丢包，但应用层仍然要考虑断连、重连和消息补偿。
此外还会开启心跳机制检测连接状态；
如果用户量增加，可以给每个文档房间维护独立的消息队列，减少广播拥塞和乱序风险。

#### 5. Yjs 底层为什么能解决冲突？如果多人同时改同一段内容，最后怎么决定谁生效？
冲突的解决依赖 CRDT 的设计，CRDT 的设计目标就是让多个操作最终收敛一致。

Yjs 底层是基于双向链表的，给每个操作分配唯一标识，并记录操作之间的依赖关系，不同客户端产生的修改都可以作为独立增量存在。所以，不管操作是顺序、乱序还是离线产生的，或是多个用户同时修改同一段内容，它都依靠数据结构和操作依赖来做确定性合并，最终保证所有客户端状态一致。

双向链表能同时记录每个操作的前驱和后继依赖，这样即使中间某个操作乱序到达，也能通过前后依赖关系找到正确的插入位置。

#### 6. CRDT 和 OT 有什么区别？
两者都是为了解决协同编辑冲突，但思路不同：
- CRDT：通过数据结构自动合并，不太依赖中心转换，天然支持离线而且不需要服务端密集计算。
- OT：依赖服务器转换操作，逻辑复杂，需要把操作转换成当前状态可执行的形式，对网络延迟较敏感。

#### 7. 断网期间写的内容会不会丢？如何判断用户离线？离线期间编辑怎么做？重新上线后怎么恢复状态？
不会丢。

通过 WebSocket 连接状态变化和心跳机制判断。
当连接断开、光标无变化、超时未响应或服务端检测到心跳失败时，就可以把该用户标记为离线，并从在线用户列表和光标列表中移除。

离线时，用户的修改先写到本地 Yjs 文档里，通常存在浏览器的本地存储里，底层仍然会生成独立的 yjs 增量，只是暂时发不出去。
等网络恢复后，客户端会重新加入对应房间，通过 Yjs WebSocket 的同步机制，先向服务器请求缺失的操作日志，
再用 CRDT 算法自动合并本地离线操作与远端最新状态，确保冲突被正确处理后同步到客户端。

#### 8. 光标同步是怎么做的？光标同步为什么不直接放进文档状态里？
光标同步一般是通过 Yjs 的 awareness 机制来做，每个客户端会把自己的光标位置、选择范围、用户 ID、颜色这类临时状态通过 WebSocket 广播出去，其他客户端收到后再渲染出来。  

它和文档内容同步是分开的，因为光标是“临时协作状态”，不是文档持久内容。如果把它们直接写进文档内容，会增加同步复杂度，也会使数据体量变大。

#### 8.1 如果用户网络不稳定，光标位置频繁变化，WebSocket 会不会一直广播无效的光标消息？
Awareness 模块会对光标消息做节流处理，比如 300 毫秒内只发送一次最新位置，减少无效广播。

#### 9. 历史栈记录的是什么？协同编辑下本地 undo 怎么避免影响别人？如果要撤销的内容被别人改了怎么办？
项目里用的是 Tiptap，它自带 history 机制，主要管理本地编辑的 undo / redo，放在前端内存里，页面刷新后历史栈会丢失。

`undoStack` 记录已执行但可撤销的操作，`redoStack` 记录被撤销后可重做的操作。

但在协同编辑场景下，本地 undo 只撤销当前用户自己产生的操作，不直接撤销远端同步内容。
实现上通常使用 `origin` 把本地操作和远端 update 区分开。
如果要撤销的内容已经被别人改过，就先做位置映射和状态校验，能安全撤销就执行最小范围撤销，否则提示用户或让用户确认。
撤销成功后，这次操作也会作为新的增量 update 再同步出去，保证所有客户端最终状态一致。

#### 9.1 为什么撤销重做适合用命令模式？
因为命令模式会把一次操作封装成一个独立对象，这样不仅能执行它，还能记录它、撤销它、重放它。

撤销重做的关键在于要保存操作历史，并且每个操作都要有明确的执行和逆操作逻辑。命令模式正好适合这种场景，所以编辑器、低代码平台、表单编排系统里都很常见。

#### 10. 多人同时编辑时，怎么保证性能？
- 操作层做合并，减少频繁小事务带来的重渲染开销。
- 传输层只传增量，不传全量，并且把正文状态和光标状态分离。  
- 渲染层避免频繁更新 DOM，长文档可以结合分块渲染：比如按章节或段落拆分或虚拟滚动。
- 服务端可以按文档房间做顺序处理或广播治理，减少高并发下的拥塞和乱序压力。

#### 11. 批量操作、增量命令和 Yjs update 的区别
- 多个命令可以合并进同一个 transaction，一次性提交，它们会成为一条历史记录，undo 时可整体回退（粘贴大段文本、整块格式化）。
- transaction 提交后，会被编码成 Yjs 的增量 update，在协同端之间同步。

#### 11.1 如果批量操作中途失败怎么回滚
会优先做预检和事务式提交，尽量避免半执行状态；
如果已经部分生效，就通过执行前快照或反向补偿把文档恢复回去。

#### 11.2 事务的大小有没有限制？
通常可以设置一个合理的事务大小限制，比如单次批量操作不超过 1000 个字符或 100 行内容，避免单个事务过大导致同步时阻塞或性能下降。如果超过限制，可以自动拆分成多个小事务处理。

#### 12. 如果文档中包含图片、表格等复杂内容，协同编辑时这些内容的同步和冲突处理和纯文本有区别吗？
图片、表格这类复杂内容通常会被拆分为多个基础操作，比如图片的插入位置、src；表格的行列增减、单元格等，Yjs 会为这些子操作分别生成唯一 ID，冲突时还是按 CRDT 的规则合并，但需要业务层对复杂内容的展示做适配。

比如表格合并单元格，Yjs 会记录合并的范围和顺序，若同时有其他用户拆分单元格，CRDT 会根据操作 ID 确定最终状态，业务层再根据合并后的操作数据渲染表格。

#### 13. 删除为什么不是直接删？
yjs 删除本质是墓碑标记，不会立即物理删除。原因是别的客户端可能还没同步到，仍引用该节点。

通常是当所有在线客户端都确认收到并应用了这个删除操作，或者经过一段时间后没有客户端再引用这个节点时，Yjs 会自动清理墓碑标记，释放内存。

#### 14. 房间鉴权怎么做？谁能进同一个文档房间？
通常会在建立 WebSocket 连接时，先校验 token、文档权限和用户角色。  
服务端决定这个用户是否能加入当前文档房间，以及是只读还是可编辑。  
如果是只读用户，前端会禁用编辑能力；服务端收到这类用户发来的增量更新时，也不会继续广播。  

### B. 大文件上传链路
#### 1. 大文件上传链路是怎么设计的？
- 上传前，前端先计算文件 hash，请求后端做预检；如果文件已经存在，就直接秒传成功。
- 如果需要上传，后端会先创建上传任务，生成 `taskId`，并返回直传 `MinIO` 需要的上下文信息，比如 `objectKey` 标识文件在对象存储里的位置，访问地址，签名地址或临时凭证，后续的下载、预览、都是围绕这些元信息来做的。
- 前端把文件切成多个分片，按一定并发度直接上传到 `MinIO`；同时向业务后端上传记录分片状态、校验上传进度，并在全部分片完成后触发最终合并；
- 这样即使用户断网、刷新页面，可以基于任务状态做断点续传。

#### 2. 前端怎么切片？
- 前端通常使用 `Blob.slice()` 或 `File.slice()` 按固定大小截取文件，生成多个分片对象。
- 每个分片一般会带上：`taskId`、文件 hash、分片序号、分片总数，以及分片内容本身。
- 这样后端就能知道当前任务的哪一片已经上传成功，也方便后面做断点续传和最终合并。  
- 同时前端还会控制并发数，避免一次性发起过多请求，把浏览器和服务端都压垮。

#### 2.1 大文件切片时，切片大小、并发数怎么确定比较合适？
如果切片太小，请求数会特别多，服务端压力也会变大；如果切片太大，一旦某一片失败，重传成本又很高。  
通常会把切片控制在几 MB 到十 MB 左右，并发数控制在三到六个左右，再根据网络情况动态调整。  

#### 3. 怎么实现秒传？
秒传的核心是先做文件指纹比对。  
上传前，前端会先计算文件 hash，然后带着文件名、大小、hash 等信息请求后端做预检。  
如果后端发现这个文件已经完整存在，就可以直接返回“已存在”。

#### 3.1 文件指纹一般怎么计算？整文件 hash 会不会卡？
通常会区分两类：
- 整文件 hash：适合做秒传判断，确认“是不是同一个文件”
- 分片 hash：适合做断点续传和完整性校验，确认“这一片是不是已经上传过”

如果直接在主线程里计算大文件 hash 可能会卡顿，可以放到 Web Worker 里做，避免阻塞页面交互。

#### 4. 断点续传具体怎么做？如果上传中途失败或者页面刷新，怎么恢复任务？
后端在开始上传前先创建 `taskId`，把这个任务设计成一个可恢复状态机，包含待上传、上传中、已完成几种状态；同时记录每个分片的上传结果。  
前端也会把 `taskId`、文件基本信息、分片总数保存在本地 `localStorage` 中。
如果上传中途中断，或者页面被刷新，前端重新进入页面后，会先读取本地保存的任务信息，再拿 `taskId` 去查询后端当前任务状态和已完成分片列表，只补传缺失的分片，等所有分片都成功之后，后端再统一校验分片状态，调用对象存储的分片合并能力生成最终文件。

#### 5. 服务端如何校验分片的完整性和正确顺序？
后端通常会同时校验完整性和顺序。  
完整性上，前端可以给每个分片算 hash，后端在分片上传完成后做记录或抽查校验，不一致就要求重传；
顺序上，每个分片都会带 `chunkIndex`，后端会按编号记录，最终合并时按编号顺序调用对象存储的分片合并能力。  

#### 6. 为什么不用一次性上传？
因为一次性上传大文件的失败成本太高，一旦网络中断或者浏览器刷新，就可能整文件重传，用户体验差。  
而且大文件长时间占用一个连接，也会增加服务端处理压力。  

### C. SSE 流式问答
> 前端采用 `fetch + ReadableStream` 来接收服务端的增量输出，解决了半包粘包、逐 token 渲染性能、请求中断、异常恢复等问题。

#### 1. 为什么在问答里选 SSE？
因为这个场景是服务端持续生成，前端持续消费，主要是单向推流，所以 `SSE` 很合适。  
它基于 HTTP，接入成本低，也比较适合大模型这种逐 token 输出的场景。
相比 WebSocket 双向通信，性能更好。

#### 2. SSE 为什么不用 EventSource，而用 fetch 自己读流？
- `EventSource` 虽然简单，但可控性不够。对请求能力受限，自定义 `Header`、`POST` 参数不灵活，而问答接口需要携带复杂参数。
- 如果做请求级中断（`AbortController`）、统一错误处理、流式协议精细解析，`ReadableStream` 更适合做底层控制。

#### 3. SSE 里的粘包、半包怎么处理？SSE 数据不是一条条完整到达的，怎么保证解析正确？
流式响应的内容，一次收到的 chunk 不一定正好是一条完整消息，可能一条消息被拆成两半，也可能一个 chunk 里拼了多条消息。

response.body 是一个 ReadableStream，代表后端的流式输出。通过 response.getReader() 获取 reader，循环调用 reader.read() 获取 chunk

处理思路就是前端维护一个缓冲区，持续累积数据
- 每次从流里读到新的 chunk，先用 `TextDecoder` 按流式方式解码。
- 把新文本追加到 buffer 里。
- 再按 SSE 的分隔符去切一条条完整事件，不能解析的半截内容先留在 buffer，等下一次 chunk 来了再继续拼。
- 合并后再 JSON.parse 解析。
- 对 `[DONE]` 或自定义结束事件 `event: end` 做终止收尾。

#### 4. fetch + ReadableStream 逐 token 渲染怎么做？怎么避免重渲染风暴？
如果模型吐一个 token，前端就立刻 `setState` 一次，页面会频繁重渲染，性能会很差。
一般会做两层处理：
- 第一层是数据层先缓冲，把流里收到的 chunk 先做解析，放进内存队列，用来解决 SSE 的半包/粘包问题；
- 第二层是渲染层合批更新，分帧消费，通过 `requestAnimationFrame` 批量把内容刷到界面上，用来减少 setState + Markdown 解析频率，避免 token 全量解析触发高频重排和重绘。

#### 4.1 Markdown 在流式过程中是不完整的，半截代码块怎么办？
流式中经常出现未闭合结构，比如先出现三个反引号，过一会儿才把代码内容和结束符吐完，如果每来一点内容就完整解析一次 Markdown，容易出现错误样式。

处理思路是：
- 增量阶段先做轻量展示，不追求每个时刻都完全正确
- 对代码块、表格这类结构化内容，尽量等它闭合后再做更稳定的解析
- 流结束后再做一次完整的最终解析，保证最后展示结果正确

#### 4.2 Markdown 是用什么做的？
使用 markdown-it 处理 Markdown、HTML、换行、emoji，把 Markdown 文本 转成 HTML；
Markdown文本解析成AST，再转换成HTML，最后渲染DOM树

#### 4.3 长文本性能优化
如果回答内容很长，处理思路主要有三层：

- 不逐 token 直接渲染，而是先缓冲，再按 `requestAnimationFrame` 合批更新，减少频繁 setState；
- 对长回答做分块渲染，前面已经稳定的内容尽量不要反复重新解析，只更新最后还在增长的那一块；
- 像代码高亮、公式渲染这种重处理操作，尽量放到内容相对稳定后再做，避免每次增量更新都全量重算。

#### 4.3 XSS 怎么防？
因为大模型输出本质上是不可信输入，所以不能直接把它当 HTML 插到页面里。处理思路是：
- 不直接用 `v-html` 或 `innerHTML`。
- 先把 Markdown 解析成 HTML，再走一层白名单清洗，只保留安全标签和属性，禁止危险标签和属性。
- 对链接做额外限制，禁止 `javascript:`、`data:` 这种危险协议。
- 最后再配合 `CSP` 做一层浏览器侧兜底。

CSP是一种浏览器安全策略，通过 HTTP 响应头或 meta 标签声明页面允许加载和执行的资源来源，用于防御 XSS 等攻击。常见指令有 script-src、style-src、img-src、connect-src 等。例如配置 script-src 'self' 后，浏览器只允许执行当前站点的脚本，外部恶意脚本会被拦截。

#### 5. 流式输出时怎么支持中断？
前端会把当前请求和 `AbortController` 绑定。用户点击停止时，前端先 abort 当前请求，停止继续读流。  
后端做断开感知连接；及时取消上游模型请求，并清理这次任务占用的上下文和资源。

#### 6. 流式过程中如果 JSON 解析失败或网络抖动怎么办？
把异常分三类处理：
- 可恢复（短时抖动、局部解析失败）：保留已生成内容，提示“连接波动，可重试续答”。
- 不可恢复（鉴权失败、模型报错）：立即终止并展示明确原因。
- 用户中断：区分为正常业务状态，不记为系统错误。

#### 7. 重连重试怎么做？怎么避免重复拼接？
- 前端监听流异常、超时和网络状态变化
- 按指数退避策略发起重试，比如 1s、2s、4s
- 设最大重试次数，避免无限重连
- 如果判断是鉴权失败、参数错误这类不可恢复问题，就直接终止

为了避免重连后把前面的内容又拼一遍，前后端之间会维护一个稳定游标，比如 chunk 序号。  
重连时前端把上次成功消费到的位置带给后端，后端只继续返回后面的增量。

#### 8. 如何避免“光标抖动”和滚动体验差？
如果每来一点内容就强行滚到底，用户一旦想回看上文，就会被不断拽回去。

- 只有用户在底部附近时才自动跟随滚动
- 用户手动上滑后暂停自动滚动
- 新内容用锚点恢复，而不是每次 `scrollToBottom` 暴力拉到底

### D. L1 / L2/ L3 三层记忆
> 在多轮问答里，如果把所有历史都塞进 prompt，成本会变高，而且真正重要的上下文容易被淹没；如果压缩得太狠，会丢失很多细节。
> 所以把记忆拆成三层：
> - `L1` 保存最近几轮原文，比如当前任务、最近一次修改意见，用来保证当前推理细节不丢；
> - `L2` 用 `Rolling Summary` 压缩阶段性信息，比如目标、已确认决策和未解决问题，用来控制长对话成本；
> - `L3` 保存长期稳定的用户偏好、项目背景和已经反复确认过的事实，用来支持跨轮次、跨会话复用。

#### 1. L1 的“滑动窗口”怎么设计？窗口多大？
`L1` 是基于 token 的滑动窗口，窗口大小控制在 `1k` 到 `4k token` 左右，具体要看模型上下文长度和任务复杂度，超出窗口后会有选择地往下沉。

#### 3.1 L1 滑出后怎么决定写进 L2 还是 L3？
需要看这条信息是阶段性信息，还是长期稳定信息。

- 如果是当前任务相关、阶段性上下文、未解决事项，就写进 L2。
- 如果是长期稳定的用户偏好、身份背景、明确确认过的事实，并且置信度足够高，就写进 L3。

#### 4. 为什么 L2 要用 Rolling Summary，而不是固定摘要？
因为固定摘要是某一段对话总结完就不再更新了，但真实的多轮问答里，状态一直在变化。如果摘要不更新，容易丢掉最新决策，或者和当前对话脱节。

`Rolling Summary` 的核心思路是增量更新：
- 保留上一版摘要
- 吸收新增对话里的关键信息
- 生成一版新的阶段摘要

#### 4.1 Rolling Summary 会不会越滚越偏？怎么防止摘要漂移？
Rolling Summary 存在漂移风险，因为它本质上是持续压缩，误差会逐轮累积。
防护思路是：
- 采用结构化摘要，固定保留目标、约束、决策和未解决项，而不是一段自由文本；
- 每次更新时，输入上一版摘要和新增原文，输出新摘要，同时保留变更记录和来源引用；
- 对数字、时间、否定句、关键决策做一致性校验，发现异常时回退原文复核。

#### 5. L3 长期记忆怎么写入？是不是每次都写？L3 会不会“记错”用户？
`L3` 只写高价值、长期稳定、可复用的信息，比如用户偏好、长期目标、已经明确纠正过的事实。

一般会先做一层过滤：信息是否长期稳定、是否用户明确确认过、后续会不会反复用到、当前置信度是否够高

如果只是一次随口提到、上下文不完整，或者本身就不确定，不会直接写进 `L3`。

记录结构：fact, scope, confidence, source_turn, updated_at, ttl，可以使用结构化 KV。

#### 5.1 怎么检索 L3？生成回复时三层记忆怎么一起参与？
生成前，不是把 `L1`、`L2`、`L3` 全拼进去，而是按问题类型去组合。

流程是：
- 新消息先进入 `L1`
- `L1` 超阈值（token）触发摘要，通过 Rolling Summary 进入 `L2`
- 从 `L2`/`L1` 中抽取“稳定且可复用事实”写入 `L3`
- 每轮生成前做组装：`L1、L2、L3` 不是简单拼接，而是按问题类型动态加权：`L1` 负责最近原文和细节，`L2` 负责当前阶段的滚动状态，`L3` 负责长期偏好和稳定事实。

#### 5.2 如果用户前后说法冲突了，怎么处理？L2 和 L3 冲突时怎么办？
要先判断，用户是在明确修正之前的说法，还是只是当前场景下的临时覆盖。

- 如果是明确修正，就以新的说法为准，同时把旧记忆降权、标记过期，必要时更新 `L3`
- 如果只是临时场景变化，那就优先当前会话里的 `L1 / L2`，但不一定改写 `L3`
- 如果还不确定，就先保留多个版本，用时间戳、置信度和作用域来决定当前轮优先用哪条。

当前会话状态通常优先级更高，长期记忆更多是默认背景，而不是压过用户当前表达。

#### 5.3 L3 如何避免无限增长？
- 第一，写入过滤，不是所有信息都进 L3；
- 第二，去重合并，语义相近的记忆会合并，不会一直重复存；
- 第三，做时间衰减和过期机制，比如长期没命中的记忆自动降权，或者超过一定时间后过期清理，避免无限增长。

#### 6. L1、L2、L3 分别存放在哪里？
- L1 读写频率高，要求延迟低，Redis 很适合做短期记忆缓存；
- L2 也放在会话级持久化存储中，Redis 用来保存 Rolling Summary 和当前任务状态；
- L3 是长期稳定信息，通常需要按用户维度查询、更新和审计，放在 PostgreSQL 这类关系型数据库更适合管理结构化摘要。

#### 7. 怎么评估这套记忆机制有效？
从四类指标看效果。
- 第一是连续性，比如长对话里上下文丢失率、指代消解正确率。
- 第二是个性化，比如用户偏好命中率、重复询问率下降。
- 第三是成本，比如平均 token、P95 延迟、存储成本。
- 第四是质量，比如人工盲评的一致性和幻觉率。

### E. RAG 检索增强问答
> RAG 知识增强链路，核心目的是减少专业场景下的幻觉。
> 先对文档做解析和切分，再进行向量化入库；
> 检索阶段采用 `BM25 + 向量检索` 的混合召回；
> 然后通过重排挑出最相关的片段。
> 最后让大模型基于内容生成答案，并把来源回填给用户。

#### 1. 为什么要做 RAG，而不是直接微调模型？
因为通用大模型在专业问答里容易出现幻觉，`RAG` 的思路是先把外部知识检索出来，再让模型基于这些证据去生成答案。

微调更适合固定任务格式、风格统一、领域能力强化这类场景，如果知识更新频繁，微调的成本会比较高，而 `RAG` 更新知识库会更灵活。  

#### 2. 检索链路是怎么做的？每一步分别解决什么问题？
整条链路拆成四步：
- 文档解析和切片：解决原始文档太长，不能直接喂给模型的问题；
- 向量化和索引：解决“怎么快速找到语义相关内容”的问题；
- 混合召回：解决既要术语精确匹配，又要语义召回的问题；  
- 重排和来源回填：解决最终给模型的证据要少而准，而且还要可解释的问题。

#### 3. 分片策略是什么样的？
分片策略不能太粗，也不能太碎。  
如果 chunk 太大，语义会混在一起，召回不精准，后面的重排成本也会高；如果 chunk 太小，又容易把上下文切断，导致语义不完整。

所以一般会按语义去切：
- 普通文本优先按段落、句子递归切分，确保每个分片在 256-512 token之间，且不拆分完整句子。
- Markdown 文档优先按标题层级切，再结合代码块、列表块这些结构化内容进一步拆分，保证每个分片保留标题上下文和完整语义块。

分片之间通常还会保留少量 `overlap`，因为硬切分容易把一句完整结论或者一个上下文依赖切断。  
保留少量重叠后，边界信息不容易丢，召回稳定性会更好。  
但 overlap 也不能太大，不然会带来冗余存储、重复召回和重排成本上升。

#### 3.1 针对格式化文本，除了按标题和块分片，有没有处理过特殊格式，比如表格、公式或者代码块？
- 处理表格时，将表头和对应行数据合并成“表头：值”的文本片段；
- 处理公式保留 LaTeX 原格式。
- 处理代码块，按语法树解析，优先按函数、类这些语法单元切分，每个分片控制在1000到1500字符，同时保留函数签名和注释。

#### 4. Embedding 模型是怎么选的？
选通义千问做 Embedding，因为它对中文和中英混合内容支持比较好，在专业文本场景下语义表示比较稳定，同时在效果、延迟和成本之间平衡得比较好。

#### 5. 向量数据库用的什么？
使用 `Redis Stack`，自带了 `RedisSearch` 和 `RedisJSON` 这些模块，能直接存储向量，还支持 `HNSW` 索引和余弦相似度这些常用的向量检索功能。

#### 5.1 文档更新后，向量怎么增量更新？会整篇重建吗？
一般不会整篇文档全部重建。  
而是先识别哪些段落真的发生了变化，只对变化分片重新切分、重新生成向量。
同时，旧版本里失效的 chunk 也要一起删除或者标记失效，避免检索时把已经不存在的旧内容再召回来。  

#### 6. 为什么要混合召回，而不是只用向量检索？
因为专业文档里既有语义相关性，也有很多术语、缩写、数字和专有名词。  

- 只用向量检索，有时候会把语义接近但术语不对的片段召回上来，对术语、数字、专有名词不够稳定；
- 只用BM25关键词检索，优点是对关键词、术语特别准，但用户换个说法可能检索不到。

混合召回可以平衡两者，提高召回质量，融合时采用RRF方法：对每个分片，分别取BM25排名和向量排名，按1/(排名+k)计算分数后相加，最后按总分取Top结果，能稳定平衡关键词匹配和语义相关性。

#### 7. 混合召回后为什么还要重排？重排策略是什么？
混合召回拿到的一批候选片段里，通常会混进重复内容、边缘相关内容，甚至有些片段虽然能召回，但不是最适合回答当前问题的证据。

所以还要做一层重排：
- 先去重，保留长度更长或来源更权威的片段
- 再用交叉编码器对候选片段和当前问题做更细的相关性打分
- 最后只保留少量最相关的片段给模型

#### 7.1 混合召回数量和最终 topk 如何取值
混合召回阶段会把 `topK` 设得相对大一些，通常 `BM25` 和向量检索各取 `20` 到 `50` 条，合并去重后再做重排；最终送给大模型的 `topK` 会收敛到 `5` 条左右。

#### 8. 在检索时，如果用户查询的是长文本问题，比如多轮对话后的复杂问题，向量索引还能准确召回相关分片吗？
通常不会直接用原话，尤其在多轮对话里不能直接拿用户原句去检索。  

可以先对长查询进行语义压缩，把当前问题结合最近几轮上下文，改写成一个更完整、可检索、去歧义的查询，再拿这个查询去做混合召回。  
或者用多向量检索，把长查询拆成多个子问题向量，分别召回后合并结果。  

#### 9. 在RAG系统里，怎么评估检索到的文档和用户问题的相关性？
召回率看是否能把所有相关分片都找出来，准确率看召回的分片中真正相关的比例。
除了这两个，还可以用 `NDCG` 评估排序质量，或者人工标注 `Top5` 分片的相关性打分。

#### 9.1 除了检索指标，会看最终问答效果吗？
- 检索层看 `Recall`、`Precision`、`NDCG` 这些指标
- 生成层看回答有没有真正基于证据、有没有无依据扩写、用户是否接受这次回答。

#### 10. 如果检索不到答案，怎么处理？
如果检索不到足够证据，模型不能硬答。  
更稳妥的做法是明确告诉用户，当前知识库里没有找到足够依据，或者只能基于现有资料给出一个保守回答。

#### 10.1 多文档冲突时，怎么避免模型“硬编一个统一答案”？
通常会结合来源权威性、发布时间、文档类型这些信息做排序；
如果冲突仍然存在，就把冲突显式告诉用户，而不是强行把它们揉成一个结论。

#### 11. 来源回填是如何做的？
在文档切片入库的时候，就给每个 chunk 绑定好元信息，比如文档 ID、文档标题、chunk ID、段落位置、页码或者标题层级。
检索和重排之后，最终送给模型的不是纯文本，而是携带来源标识的证据片段。
模型生成答案后，前端再根据来源标识把答案和来源卡片分开展示，把对应的文档标题、原文片段、页码或段落位置展示出来，用户点击后跳转到原文对应位置。

### F. 文档内 AI 辅助创作
> 这个模块是实现了让 AI 直接在文档上下文里完成总结、续写、润色、翻译、结构化整理和 Mermaid 图生成这些任务，整体上设计的是一个轻量多智能体编排思路：简单任务走 `Fast`，复杂任务走 `Swarm`。  
> 
> 整体上由 `Router` 路由智能体 / `Planner` 规划智能体 / `Orchestrator` 总控智能体 / `Worker` 执行智能体 / `Critic` 评审智能体 / `Merger` 汇总智能体 这些角色协作完成，把复杂任务拆开执行，再做质量检查和结果合并。

#### 1. 为什么要做文档内 AI 辅助创作，而不是单独聊天？
因为用户的真实需求是在文档编辑场景里直接修改内容。把 AI 能力嵌进文档里，可以让用户在同一个工作流中完成编辑和改写。
如果做成独立聊天框，用户还要自己复制内容、再把结果贴回文档里。
而文档内 AI 辅助创作可以直接读取当前选区、块结构和上下文，并把结果按位置回填到文档里。

#### 1.1 Fast 和 Swarm 是怎么区分的？什么任务走哪条链路？
通过 `Router` 判断任务复杂度和意图类型，再决定走 `Fast` 还是 `Swarm`，主要看输入长度、是否需要外部知识检索、是否需要多步骤规划、是否涉及结构化输出等等。

- 像润色一句话、续写一小段、翻译一段内容，这种目标明确、链路简单的任务，通常走 `Fast`
- 像“先总结，再补结论，最后再生成 Mermaid 图”这种多步骤、有依赖关系的任务，更适合走 `Swarm`

#### 2. 多智能体是怎么分工的？
我们设计了 `Router` 路由智能体 / `Planner` 规划智能体 / `Orchestrator` 总控智能体 / `Worker` 执行智能体 / `Critic` 评审智能体 / `Merger` 汇总智能体 这样的链路。

- `Router` 负责识别用户意图，判断走哪条执行链路；
- `Planner` 负责拆解复杂任务，组织成 有向无环图，决定哪些子任务可以并行执行
- `Orchestrator` 负责总控，维护 traceId、执行模式、降级策略这些编排信息
- `Worker` 负责具体执行子任务，比如总结、续写、翻译、Mermaid 生成
- `Critic` 负责检查输出质量，判断要不要修正
- `Merger` 负责把多个子结果汇总成最后结果

#### 2.1 Planner 拆解任务后，依赖关系怎么表示？
Planner 不只是简单把任务切成几段，而是会把任务组织成一个 DAG，也就是有向无环图。
- 有依赖的任务按顺序执行，避免上下文不完整
- 没依赖的任务可以并行执行，提高整体吞吐
- 最后 Merger Agent 可以按依赖关系把结果有序汇总

#### 3. ReAct 和 Reflection Loop 在这里是怎么用的？
`ReAct` 是让先分析任务、决定下一步动作、拿到中间结果，再继续往下执行，也就是“思考 - 行动 - 观察”的循环。

`Reflection Loop` 则是在结果出来后，由 `Critic` 去检查质量，如果发现问题，就把问题反馈回去，让对应的 Worker 再修一轮。  

#### 3.1 为什么 Reflection Loop 要设阈值？
因为反思循环不能无限跑，不然时延会很高，编辑器场景下用户体验会很差，一般要设两类阈值。

- 一类是次数阈值，比如最多反思 2 到 3 轮；
- 一类是收益阈值，比如连续两轮分数提升很小，就直接停止。

如果已经接近时间预算，或者连续修正也没明显变好，就直接返回当前最好结果，必要时带降级标记。  

#### 4. Blackboard Pattern 是什么？智能体之间如何通信？在高并发下如何保证数据一致性？
`Blackboard Pattern` 黑板模式，它的核心思想是：
- 多个 Agent 把中间结果写到一个共享工作区里，共享工作区里的数据块会带任务标识、产出者、状态等，比如在这个项目里，`Planner` 规划智能体拆出来的阶段结果、`Worker` 执行智能体 的中间产物、`Critic` 评审智能体 的检查结论；
- 后续 Agent 再按需要读取当前任务下最新、可用的中间结果，继续完成自己的子任务；
- 最终采用哪个结果，还是由 `Orchestrator` 总控智能体 和 `Merger` 汇总智能体 按任务链路统一收口

#### 4.1 共享工作区的数据结构大概是什么样的？
共享工作区里的数据一般会按数据块管理。每个数据块会带：
- `taskId`：属于哪次任务
- `producer`：由哪个 Agent 产出
- `status`：比如 pending、running、done、failed
- `payload`：真实的文本、结构化结果或 Mermaid 草稿
- `timestamp`：写入时间

这样后续 Agent 在读取时，可以知道这块数据是谁产出的、是否完成，也方便 `Critic` 评审智能体 和 `Merger` 汇总智能体 做回溯与审计。

#### 4.2 黑板模式的共享工作区如果数据量过大，会如何优化存储和访问效率？
如果共享工作区的数据量继续变大，可以往分层存储和索引优化方向演进。  
比如近期高频访问的中间结果放在内存里，历史数据做归档；读取时优先按任务 ID、状态需要的数据块，减少无效遍历。

#### 5. 在多智能体协作中，如果某个 worker agent 执行子任务超时，系统会如何处理？
系统会为每个子任务设置超时阈值。某个 Worker 超时后，通常由 `Orchestrator` 总控智能体 或调度层判断这个任务是否可重试：
- 如果可重试，就重新调度给空闲 Worker，或者降级成更简单的执行方式
- 如果不可重试，或者重试后仍然超时，就终止这个子任务，并把结果交给 Critic 和 Merger 判断是否还能返回部分可用结果

#### 5.1 如果某个子任务失败，整体一定失败吗？有没有降级策略？
不一定，会分情况处理，把它设计成“局部失败可降级”，尽量保证用户先拿到可用结果。

- 如果失败的是非关键子任务，比如 Mermaid 生成失败，但正文摘要已经完成，那可以降级成“先返回正文结果，不返回图”
- 如果失败的是可替代子任务，可以回退成单 Agent 直接生成
- 如果 Reflection Loop 连续多轮都收敛不好，就返回“部分结果 + 风险提示”，而不是无限重试

#### 6. Mermaid 图是怎么生成的？
由总结或计划 agent 提炼文档里的核心模块、流程、依赖关系。
Mermaid Worker 根据抽取出的结构，把语义关系映射成 Mermaid 语法。
Critic 会检查 Mermaid 是否存在问题；如果有问题，就进入 Reflection Loop，让 Mermaid Worker 重新修正。
返回结构化结果给前端。
把 Mermaid 单独拆成一个 Worker，会更容易做专门的语法检查和定向修正，也更利于接 `Critic` 做质量校验。

#### 7. 响应式协议如何定义回填位置？前端拿到后怎么回填？
后端会返回结构化协议，至少包含：
- 操作类型，比如 `insert`、`replace`、`append`
- 起始位置和结束位置，或者块 ID、锚点信息
- 真正要回填的内容
- 必要时还会带内容类型，比如普通文本还是 Mermaid

前端在发起任务时，会先记录当前选区、块 ID 或锚点位置。  
拿到协议后，再按不同操作类型执行插入、替换或追加；
如果是 Mermaid，就创建对应的 Mermaid 块节点；如果是普通文本，就走编辑器事务插入。  
最后再把这次变更同步到编辑器中。

#### 5.1 前端怎么知道这次多 Agent 到底做了什么
后端除了返回回填位置，还会返回一份编排元信息，比如：
- `traceId`：任务唯一标识
- `executionMode`：执行模式
- `routeDecision`：路由决策
- `planSummary`：规划总结
- `workerStats`：执行统计
- `criticScore`：质量评分
- `degraded`：降级标记

前端可以把这些信息展示成一张“最近一次 AI 协作卡片”，让用户看到这次是 Fast 还是 Swarm、路由到了哪个主意图、用了几个 Worker、有没有降级。

#### 6. 怎么证明这套设计有效？会看哪些指标？
一般会从两类指标看。
- 第一类是用户效果指标：用户返工率有没有下降，用户采纳率有没有提升，生成内容的格式错误率有没有下降
- 第二类是工程链路指标：平均处理时长，Reflection Loop 触发率，降级比例，哪类 Worker 最容易超时。

#### 7. 文档内 AI 辅助创作时，如何处理用户实时编辑文档导致的回填位置失效问题？
当 AI 开始处理任务时，前端会把文档编辑区域禁用掉，用户就不能改内容了，同时会显示 “AI 处理中，请稍候” 的提示，等任务完成或者取消了，才会重新允许用户编辑。

#### 8. 如果用户在 AI 处理任务时强制刷新页面，结构化协议的回填信息会丢失吗？
不会完全丢失。前端会把任务标识和必要的回填上下文临时存到本地；后端也会保留这次任务的状态和最近一次回填结果。  
页面刷新后，前端会先恢复本地任务信息，再根据 `taskId` 去后端查询任务状态和协议结果，然后再结合文档当前状态完成回填。
