# 封装组件
## 封装 FollowTable 组件
1. 封装组件的背景是这样的，原生的 sticky 定位在处理嵌套容器滚动的时候，会出现吸顶失效的问题。
为了保证在复杂场景下的稳定性，放弃了纯 CSS 方案，采用 JavaScript 监听滚动事件，通过选择滚动容器、计算元素位置、复制表头来实现吸顶。

虽然成本稍高一些，但能够解决原生方案在复杂场景下的稳定性问题。

2. 另一个问题是，在做多表格页面的时候，发现当用户对最后一个表格进行筛选，数据变少时，页面总高度会突然收缩，导致底部内容跳动，体验很差。

为了解决这个问题，我在组件初始化时，专门计算了最后一个表格到底部的距离，并将其锁定。无论表格数据如何变化，都强制保持着底部间距不变，从而实现了视觉上的防抖动。

# 100+接口
这个报表页面的首屏需要渲染多个接口，如果全量并发会阻塞浏览器，使用promiseAll全部成功不允许失败，串行又太慢，难点在于部分列的数据依赖前一列的查询结果。

因此，我设计了一个并发池，这个并发池主要是通过一个任务队列和一个计数器来实现的，计数器就是记录当前正在执行的任务数量，具体实现的方式是拿到一个任务的时候，先去并发池里找这个计数器是否小于当前的一个限制并发数，如果小于的话说明任务可以执行，就可以继续发送请求，否则的话把它放在任务队列里面。当这个任务执行完成的时候，会在 finally 中执行释放这个计数器，并从任务队列里面拉去下一个任务进行执行。

在处理依赖任务的时候，利用 async、await串行等待前置的任务请求返回，保证数据准确。
对于请求失败的情况，做了兜底处理，就是展示默认横线，防止页面奔溃。

# 虚拟列表
针对长列表渲染导致的页面卡顿，引入了虚拟渲染技术，只渲染可视区域的节点，大幅减少了 DOM 操作，显著提升了滚动流畅度。

原理是计算可视窗口，监听滚动，用滚动距离除以固定行高，计算出起始索引，再结合窗口高度计算出结束索引，只渲染这一小段，配合上下留白撑高度，减少页面的卡顿。

为了防止滚动频繁出发重排，使用了RAF节流渲染，能让计算逻辑紧跟着浏览器的刷新频率。

## 不定高怎么实现？
引入位置缓存机制。初次渲染时先给每一项一个预估高度，避免列表一开始出现明显抖动；渲染完成后，再通过 `ResizeObserver` 监听真实高度，并回写到缓存里，逐步修正每一项的位置信息。

## 最后一项动态增加怎么办？
当最后一项内容变长时，会触发重新测量并更新它后面所有元素的偏移量，同时重新计算总高度和可视区范围，保证滚动条长度和页面展示保持一致，不会出现内容覆盖或空白区域。

## position 缓存是怎么用的？
position 缓存会记录每一项的 `top`、`bottom` 和 `height` 等信息，后续滚动时直接基于缓存做区间计算，不需要反复读取 DOM 布局。这样既提升了性能，也方便在局部高度变化时只更新受影响的数据。
- DOM 节点复用

## 为什么虚拟列表能降低内存占用？
因为页面上始终只保留可视区域附近的少量 DOM 节点，而不是把所有数据项都渲染出来。这样可以显著减少 DOM 数量、事件绑定和浏览器布局计算压力，页面数据量越大，收益越明显。

## 如何快速定位可视区域？
通过二分查找快速定位起始索引，避免从头遍历整个列表。因为每一项的位置信息都存进了缓存里，所以可以直接根据滚动偏移量找到当前应该展示的区间，时间复杂度从线性降低到对数级。

## 如何避免滚动抖动？
主要通过三点处理：
1. 使用 `requestAnimationFrame` 做分帧更新，让滚动计算和浏览器刷新同步。
2. 用位置缓存减少重复计算，避免每次滚动都重新测量全部节点。
3. 对高度变化做局部修正，只更新受影响的区间，降低重排范围。

## 高度怎么测量？
通过 `ResizeObserver` 获取单项真实高度；如果列表项首次还未完成渲染，则先用预估高度占位，等真实高度稳定后再统一修正缓存。这样既保证首屏速度，也能兼容动态内容、图片加载等场景。

# Slot 时间槽模型
针对日/周视图和连续时间选择这类排班场景，基于 Slot 时间槽模型的统一实现。核心思路是把整天或整周的时间轴切分成固定粒度的时间槽，比如 30 分钟一个 Slot，再用同一份数据结构去描述日视图、周视图和连续时间选择组件。前端渲染时只要基于 Slot 计算起止位置、占用区间和展示宽度，就能统一支持不同视图。

在交互上，我把用户拖拽、点击选区、跨天选择等操作都映射成 Slot 区间的变化，然后在前端先做一次冲突检测。比如某个时间段已经被别的用户占用，或者当前选择和已存在的预约/排班发生重叠时，系统会立即高亮冲突区间并提示不可提交。为了支持多用户区间可视化，我还会把不同用户的时间块按颜色区分，配合横向排列和重叠处理，让同一时间段里谁占用了哪个 Slot 一眼就能看清楚。

## Q&A
**Q：为什么要用 Slot 时间槽模型，而不是直接用时间点渲染？**  
A：因为排班和预约场景里，时间通常不是一个孤立的点，而是一个区间。Slot 模型可以把时间统一离散化，方便做拖拽选择、冲突检测、占用统计和跨视图同步，计算和渲染也更稳定。

**Q：日视图、周视图和连续时间选择是怎么统一的？**  
A：它们底层都映射成同一套 Slot 数据。日视图和周视图只是在展示范围上不同，连续时间选择则是把起止时间转换成连续的 Slot 区间，本质上都是对同一份时间轴做切片和定位。

**Q：冲突检测是怎么做的？**  
A：前端在用户选中时间区间后，会先把当前区间和已有的预约、排班数据做区间重叠判断。只要满足起止时间交叉，就认为存在冲突，直接阻止提交并高亮冲突位置，避免用户提交后再被后端打回。

**Q：多用户区间可视化怎么保证看得清楚？**  
A：我会按照用户或者资源维度给时间块做颜色区分，并通过分层布局处理重叠区间。对于同一时间段内多个用户的占用情况，会尽量保持块状信息完整展示，同时配合 tooltip 或弹窗补充具体信息，减少视觉混乱。
