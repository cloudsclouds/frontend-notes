# 封装组件
## 封装 FollowTable 组件
### 1. 背景介绍
- 封装组件的背景是原生的 sticky 定位在处理嵌套容器滚动的时候，会出现吸顶失效的问题。
- 当表格内容高度小于滚动容器高度，原生固定表头可能不会触发吸附，而在报告类页面，用户经常需要截图某一行数据，并保留表头上下文。
- 为了保证在复杂场景下的稳定性，放弃了纯 CSS 方案，采用 JavaScript 监听滚动事件，通过选择滚动容器、计算元素位置、复制表头来实现吸顶。

另一个问题是，在做多表格页面的时候，发现当用户对最后一个表格进行筛选，数据变少时，页面总高度会突然收缩，导致底部内容跳动，体验很差。
为了解决这个问题，在组件初始化时，计算了最后一个表格到底部的距离，并将其锁定。无论表格数据如何变化，都强制保持底部间距不变，从而实现了视觉上的防抖动。

### 2. 为什么不用纯 CSS `sticky`，而是要克隆表头？
因为这里不是单一滚动容器，而是嵌套滚动和多表格混合的报告页面。原生 `sticky` 在祖先容器存在 `overflow` 等情况时容易失效。自己维护一个吸顶表头虽然实现更重，但行为更可控，跨页面复用也更稳定。

### 3. FollowTable 里两个主要难点是什么？
- 样式丢失：克隆节点虽然会保留原来的 DOM 结构和 class，但如果表头样式依赖 Vue 的 scoped 作用域，克隆后的节点可能无法稳定命中原有样式。解决：将表头的公共样式抽成可复用的非 scoped 样式或公共 class，让原表头和克隆表头共享同一套样式来源。
- 列宽偏差：整数宽度和渲染时序导致 1-2px 错位。解决：改用浮点数计算，并使用 `nextTick`、`ResizeObserver` 等时机触发同步，在首次渲染完成、窗口 `resize`、筛选导致列宽变化、全屏切换后，确保布局稳定后再测量，避免读到过渡态宽度。

### 4. 计算可见范围的公式是什么？
通过计算滚动容器的 `scrollTop` 与表格初始位置的差值，判断当前滚动是否已经超过表头，也就是 `offset > 0`，同时确保没有滚出表格底部，也就是 `offset < tableHeight - headerHeight`，从而决定是否显示 sticky 表头。
- `scrollTop`：滚动容器已经滚动了多少距离。
- `tableHeight`：表格容器的高度。
- `headerHeight`：表头的高度。
- `offset`：滚动容器与表格初始位置的差值。

# 100+ 接口并发渲染
## 1. 背景介绍
这个报表页面的首屏需要渲染多个接口，如果串行太慢，全量并发会阻塞浏览器，使用 `promiseAll` 全部成功不允许失败，并且难点还有部分列的数据依赖前一列的查询结果。

因此，设计了一个并发池，这个并发池主要是通过一个任务队列和一个计数器来实现的，计数器就是记录当前正在执行的任务数量，具体实现方式是拿到一个任务的时候，先去并发池里找这个计数器是否小于当前的限制并发数，如果小于的话说明任务可以执行，就可以继续发送请求，否则的话把它放在任务队列里面。当这个任务执行完成的时候，会在 `finally` 中执行释放这个计数器，并从任务队列里面拉取下一个任务进行执行。

在处理依赖任务的时候，利用 `async`、`await` 串行等待前置的任务请求返回。
对于请求失败的情况，做了兜底处理，就是展示默认横线，防止页面崩溃。

## 2. 这 100+ 接口的数据流程是怎样的？
第一阶段是全局数据加载，先请求一次全局依赖的数据得到表格框架，这一步是单次请求。

第二阶段是每一行的基础信息加载。这里采用的是“行间并发、行内串行”：
- 行间并发指的是多行数据可以同时发请求，控制最大并发数，避免一次性发出过多 HTTP 请求导致接口压力过大。
- 行内串行是因为一行里的数据存在依赖关系，需要按顺序获取，所以在一行内部通过 `await` 串行执行，保证数据顺序正确。

第三阶段是指标数据加载。这一部分又做了一个优化，把 HTTP 请求和数据处理解耦：
- HTTP 请求仍然通过并发池控制并发数量。
- 请求返回之后的数据解析和 `map` 构建是在本地同步执行，不占用并发池资源。
 
## 3. 并发池的 `limit = 6` 是如何确定的？可以动态调整吗？
- 基于 HTTP/1.1 下浏览器对同源域名的默认并发限制通常是 6，设为 6 能最大化利用浏览器能力而不触发排队。
- 在 HTTP/2 环境下或根据接口平均响应时间 RT，可以动态调整。例如监测到请求大量超时，可临时降低 limit；若 RT 极短，可适当调高。

## 4. 为什么不用 `Promise.allSettled`？
`allSettled` 只能解决“单个失败不影响整体收集结果”的问题，但不能解决“同时发太多请求导致首屏卡顿、接口排队、依赖任务无法排序”的问题。这个场景真正的核心矛盾不是失败收集，而是并发节流和依赖编排，所以还是需要并发池。

## 5. 有没有做取消请求或者防止重复请求？
如果用户切换筛选条件、时间范围或者离开页面，需要取消失效请求，避免旧数据回写覆盖新状态。结合请求标识、版本号或者 `AbortController` 来处理。

## 6. 项目最难的地方
项目里相对比较难的是报表页面的多接口并发渲染模块，因为它同时涉及请求并发控制、接口依赖关系。
主要的问题是，首屏需要请求大量接口，如果全部并发会阻塞浏览器；但如果完全串行，请求耗时又太长。而且，部分列的数据还依赖前一个接口的结果，不能简单地一起发。
通过“并发池 + 依赖任务串行”的方式解决。独立请求放进任务队列里，用计数器控制同时执行的数量；有前后依赖的任务，则用 `async/await` 串行等待上游结果。对于失败请求，再做兜底展示，显示默认横线，避免局部异常把整个页面拖垮。

# 虚拟列表
## 1. 背景介绍
针对长列表渲染导致的页面卡顿，引入了虚拟渲染技术，只渲染可视区域的节点，大幅减少了 DOM 操作，显著提升了滚动流畅度。
原理是计算可视窗口，监听滚动，用滚动距离 scrollTop 除以固定行高，计算出起始索引，再结合窗口高度计算出结束索引，只渲染这一小段，配合上下留白撑高度。
为了防止滚动频繁触发重排，使用了 RAF 节流渲染，能让计算逻辑紧跟着浏览器的刷新频率。
通过 ResizeObserver 监听容器大小变化，动态更新 visibleCount。

## 2. 为什么虚拟列表能提升性能，瓶颈到底在哪？
长列表真正贵的不是循环本身，而是大量 DOM 节点带来的布局、绘制、内存占用和滚动时重排成本。虚拟列表把“全量渲染”变成“按窗口渲染”，本质上是在减少浏览器需要维护的真实节点数。

## 3. 自研和用库怎么取舍？
- 自研：高度定制化，可根据特定业务需求精确调整实现细节，更轻量，避免引入不必要的功能和代码。
- 库：快速集成，使用方便，适合通用场景。

## 4. 不定高怎么实现？
引入位置缓存机制。初次渲染时先给每一项一个预估高度，避免列表一开始出现明显抖动；渲染完成后，再通过 `ResizeObserver` 监听真实高度，并回写到缓存里，逐步修正每一项的位置信息。
- 预估：初始化时会根据预设行高建立元素位置缓存数组，用一个平均高度先撑开滚动条，渲染后测量真实高度。`totalHeight = list.length * estimatedItemHeight`
- 测量：动态修正位置，维护一个前缀和数组，用于计算每一项的 `top`，以及 `scrollTop` 对应的 index。`positions[i] = positions[i - 1] + heightMap[i]`
- 二分查找：计算 `scrollTop` 对应的 `startIndex` 索引时，需对前缀和进行二分查找，复杂度变为 `O(logN)`。

## 5. 如何快速定位可视区域？
通过二分查找快速定位起始索引，避免从头遍历整个列表。因为每一项的位置信息都存进了缓存里，所以可以直接根据滚动偏移量找到当前应该展示的区间，时间复杂度从线性降低到对数级。

## 6. 如何避免滚动抖动？
主要通过三点处理：
- 使用 `requestAnimationFrame` 做分帧更新，让滚动计算和浏览器刷新同步。
- 用位置缓存减少重复计算，避免每次滚动都重新测量全部节点。
- 对高度变化做局部修正，只更新受影响的区间，降低重排范围。

## 7. 为什么要加缓冲区，而不是只渲染严格可视区域？
如果只渲染刚好可见的那些项，快速滚动时很容易在边缘出现白屏或闪烁。加上上下一定数量的 buffer，可以提前准备即将进入视区的节点，让滚动更连续。

## 8. 动态计算容器高度适配全屏，具体怎么做的？为什么不用 `height: 100%`？
原因是报表页面通常包含 Header、Toolbar、Pagination 等固定高度元素，且支持全屏模式。纯 CSS `100%` 难以精确扣除这些动态变化的头部高度，容易导致出现双滚动条或内容被遮挡。
- 实现：使用 `ResizeObserver` 监听容器。计算公式为 视口高度 - 顶部偏移量（`getBoundingClientRect`）- 固定 UI 预留高度。
- 优势：能够精确适配不同分辨率和全屏切换，保证列表区域始终填满剩余空间且只出现一个滚动条。

# Slot 时间槽模型
## 1. 背景介绍
针对日/周视图和连续时间选择这类排班场景，基于 Slot 时间槽模型的统一实现。核心思路是把整天或整周的时间轴切分成固定粒度的时间槽，比如 30 分钟一个 Slot，再用同一份数据结构去描述日视图、周视图和连续时间选择组件。前端渲染时只要基于 Slot 计算起止位置、占用区间和展示宽度，就能统一支持不同视图。

在交互上，把用户拖拽、点击选区、跨天选择等操作都映射成 Slot 区间的变化，然后在前端先做一次冲突检测。比如某个时间段已经被别的用户占用，或者当前选择和已存在的预约发生重叠时，系统会高亮冲突区间并提示不可提交。为了支持多用户区间可视化，把不同用户的时间块按颜色区分，配合横向排列和重叠处理。

## 2. 日视图、周视图和连续时间选择是怎么统一的？
它们底层都映射成同一套 Slot 数据。日视图和周视图只是在展示范围上不同，连续时间选择则是把起止时间转换成连续的 Slot 区间，本质上都是对同一份时间轴做切片和定位。

## 3. 冲突检测是怎么做的？
前端在用户选中时间区间后，会先把当前区间和已有的预约、排班数据做区间重叠判断。只要满足起止时间交叉，就认为存在冲突，直接阻止提交并高亮冲突位置，避免用户提交后再被后端打回。
